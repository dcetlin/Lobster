## Stage 1: Vision Alignment — Formed Before Seeing Implementation

**Theory of change:** vision.yaml principle-4 ("wire what exists before building more") names "the missing arrows between existing systems" as the velocity multiplier. The journal → TODO pipeline is exactly that: the vault-processor, self_action_items.db, los-action-scanner, and ACTIVE TODOS.md all exist. The missing arrow was: nothing extracted `- [ ] ...` items from vault journal files. This PR adds the arrow.

**What would have to be true for this to be the right path:** The los-action-scanner was the intended mechanism for feeding ACTIVE TODOS from journal content (not a dormant idea), the vault journals actually contain `- [ ] ...` items worth extracting, and the downstream pipeline (DB, extractor API, vault-processor) is functional enough to receive the new inputs. The PR's dry-run verification (250 items found across 26 files) confirms assumption 2 and 3. Assumption 1 is confirmed by the existence of the script and task file predating this PR.

**Cheaper test of the underlying assumption:** The dry-run was the right test. It was run. Stage 1 is satisfied.

**What this forecloses:** The scanner scans ALL .md files. Once items from READMEs, Tania's creative docs, and system files are in self_action_items.db, the downstream pipeline cannot distinguish their origin at the status-update layer (los-action-scanner may surface them as Dan's commitments). This is not permanently foreclosed (source filtering or directory scoping can be added), but items already written to the DB before scope refinement persist. The `source_name` encodes vault-relative path (e.g., `journal:tania-creative-domains`) which makes origin traceable but does not currently gate any downstream behavior.

**Opportunity cost:** WOS executor is stopped. This PR touches the LOS pipeline, which is independent of WOS execution. No conflict with current_constraint.

**Alignment verdict: Confirmed** — with one noted concern (broad scope, flagged explicitly by the engineer and acknowledged in the PR body as intentional but possibly too broad).

## Stage 2: Quality Review

### What this does

1. **vault-journal-scanner.py** (new Type B cron-direct script): scans all vault .md files for `- [ ] ...` items, persists via the existing `extract_action_items` API, tracks processed files by mtime to avoid re-reading unchanged files, writes state atomically.

2. **upgrade.sh migrations 126 + 127**: registers los-action-scanner in jobs.json (Migration 126), registers vault-journal-scanner in jobs.json and adds the cron entry (Migration 127).

3. **tests/unit/los/test_vault_journal_scanner.py**: 30 tests covering extraction, dedup, state management, dry-run, exclusions.

### Against named oracle patterns

**`is_job_enabled` gate (learnings PR #1011):** Present and called first in `main()`. Pattern followed.

**Mirror-constant pattern (learnings PRs #696, #800, #967, #970, #973, #974, #980):** The test uses `importlib.util` to load the scanner as a module, then accesses constants via `scanner.CONSTANT_NAME`. No local re-declaration of production constants in the test file. Pattern avoided.

**Bare `python3` in bash (learnings PRs #804, #821, #830):** Migrations use `uv run python3`. Pattern followed.

**False completed-test checkbox (learnings PRs #1011, #1238):** The PR's test checkbox cites `tests/unit/los/test_vault_journal_scanner.py`, which appears in the diff as a new file with 30 tests covering the introduced module. Not a recycled pre-existing test suite. Pattern followed.

**Multi-fire notifications (learnings PRs #896, #1034):** No notifications emitted by this script. mtime-based state tracking prevents re-processing unchanged files on each hourly run.

**Migration number collision (learnings PRs #1000, #1105):** Only one open PR at time of review. Migrations 126 and 127 are the next slots after 125 (last merged). No collision.

**Canonical inbox write utility bypass (learnings PR #1034):** Not applicable — the scanner writes to self_action_items.db directly, not to the inbox.

**`ADMIN_CHAT_ID` env-var form (learnings PR #1122):** Not applicable — no ADMIN_CHAT_ID in this script.

### Encoded Orientation (constraint-3)

This PR adds a new cron-direct scheduled job. It does not change behavioral defaults, system constraints, agent identity, or decision-making rules in a durable way. The `is_job_enabled()` gate preserves runtime on/off control. No prior logged decision required.

### Specific engineer concerns addressed

**Migration heredoc syntax:** `uv run python3 - <<'HEREDOC' arg1 arg2` is valid bash. The heredoc is stdin; positional args follow the heredoc delimiter and are passed as `sys.argv[1]`, `sys.argv[2]`. This pattern has been stable since bash 2.x. The `_JOBS_FILE` local variable declared in Migration 126 is in scope for Migration 127 (both in the same `run_migrations()` function). Correct.

**Broad scope (all .md files):** Technically sound — exclusions for `.git`, `.obsidian`, `.trash`, and `ACTIVE TODOS.md` are correctly implemented. The scope-breadth concern is a signal-quality question, not a correctness bug. The `source_name` encodes vault-relative path (e.g., `journal:tania-creative-domains-jewelry-focus`) making origin traceable in the DB. The dedup-by-content-hash prevents duplicate rows from multi-file repetition. The downstream pipeline will receive items from non-journal files; that is the stated intentional design.

**State file path:** `~/lobster-workspace/data/vault-journal-scanner-state.json`. Directory exists on this instance. `save_scanner_state` also calls `state_path.parent.mkdir(parents=True, exist_ok=True)` as a belt-and-suspenders guard. Sound.

**8 existing duplicate DB items:** Explicitly out of scope. Correct.

### Issues found

**Minor — `files_scanned` counter semantics mismatch with log message:** The final log message `"Scan complete: %d file(s) scanned"` uses `files_scanned`, but `files_scanned` only increments for files that had checkboxes (not for files visited and found empty). Files with no unchecked items are still marked in state (so they are not re-read) but do not increment `files_scanned`. The PR body states "26 files, 250 items found" from the dry-run — this 26 comes from the opening `"Found %d markdown files"` log line, not from `files_scanned`. The final summary would report a smaller number. Log-clarity issue only, not a correctness bug.

**Minor — `sys.modules` registration missing in test loader:** The `_load_scanner()` function uses `importlib.util` without registering the module in `sys.modules` before `exec_module`. The golden-patterns.md `importlib re-export bridge` pattern requires this for `@dataclass` forward reference resolution. vault-journal-scanner.py has no dataclasses, so this does not cause failures. Pattern deviation, not a defect. Not a blocker.

**Not an issue — `updated_state` populated in dry-run:** `scan_vault()` populates `updated_state` even in dry-run mode. `main()` correctly gates `save_scanner_state` on `not args.dry_run`. The returned updated_state in dry-run is a no-op because the caller doesn't persist it.

### Verdict rationale

The two gaps this PR closes (los-action-scanner never registered, no vault scanner) are real structural gaps in an otherwise assembled pipeline. The implementation is clean: pure functions for extraction, side effects isolated at the scan_vault boundary, atomic state writes, mtime-based incremental processing, and dedup via content hash. Tests cover the key behaviors. The migrations use the correct pattern (`uv run python3`, heredoc-with-args, idempotency guard, tmp-then-rename). The `is_job_enabled` gate is present. No mirror constants in tests. No false test checkboxes.

The two minor issues (log message semantics, sys.modules omission) are advisory only and do not affect correctness.
