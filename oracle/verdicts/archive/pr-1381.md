## Stage 1: Vision Alignment

**Prior entering review:** This implementation is solving the wrong problem, or solving the right problem in a direction that forecloses better paths.

The theory of change: `wos_execute_router.py` was spawning Claude subprocesses via `subprocess.Popen` directly, bypassing the Lobster dispatcher's session management, agent tracking (session_store), and routing controls. The canonical inbox dispatch path already exists in `executor.py`. Path 2 of the migration plan replaces the Popen spawn with a single delegating call to `_dispatch_via_inbox`.

What would have to be true for this to be wrong: the inbox dispatch path would have to be unproven, or some critical behavior (session tracking, `wos abort`, forensic logging) would have to depend on the Popen path in a way that cannot be deferred.

Foreclosure risk examined: `wos abort` uses `executor_pid` set only by the Popen path. After this PR, all new dispatches produce null `executor_pid`, making abort silently return "no running process found." This is a real capability regression. The migration plan names it explicitly and specifies the follow-on: fall back to session store lookup by `task_id="wos-{uow_id}"`. The WOS executor is currently paused (`execution_enabled=false` per `vision.yaml` current_constraint), meaning no UoWs are dispatched into this path right now. The degradation affects zero live UoWs during the pause period.

What this change makes easier: session store tracking becomes authoritative (inbox-dispatched agents register via the Task tool path); MAX_AGENTS_GATE becomes reliable (Popen-spawned agents registered inconsistently); dispatcher routing controls apply to all WOS subagents. What it makes harder: per-execution forensic log files (`orchestration/logs/{run_id}.log`) are no longer written — Task tool spawns do not produce these. The migration plan notes this separately under "Log files" risk.

Alignment verdict: Confirmed. The change serves `principle-4` (wire what exists), aligns with the APPROVED design-wos-router.md decision, and the known tradeoffs are explicitly documented in the migration plan.

**Pattern applications:**

From learnings.md `PR #914` ("Synchronous subprocess call inside a dispatch routing function violates the dispatcher's 7-second rule"): this entry was the active prior confirming the Popen path in the router was the correct thing to remove. It made me weight the structural improvement more heavily — the Popen path in the router was a 7-second-rule violation surface even when `start_new_session=True` is used, because the Popen call itself (directory creation, file open, process spawn) can block for non-trivial time. The PR fixes this by making dispatch a pure inbox write.

From golden-patterns.md `seam-first abstraction` (2026-03-30): `_dispatch` as a thin wrapper with a clear docstring is a named seam. The wrapper is the right form — it gives the module a single named dispatch point that future callers can mock, and it allows the underlying mechanism to change again without touching `_route_single_message`. The seam-first pattern constrained my evaluation: I did not treat the wrapper as redundant overhead; I treated it as the correct boundary placement.

From learnings.md `PR #1220` ("Crash-suppression without replacement-path wiring converts loud failure to silent capability gap"): this constrained my evaluation of the `wos abort` degradation. The old code wrote `executor_pid`; the new code does not. I verified that `handle_wos_abort` has no session-store fallback — confirmed by reading lines 1031-1037 of `dispatcher_handlers.py`. This is a known silent degradation, not a crash suppression. The difference: the migration plan explicitly names it as a follow-on step, the executor is paused, and the abort path returns a clear "no PID stored" message rather than silently no-oping. Degradation is visible to the user who invokes `wos abort` — not invisible. The PR #1220 pattern did not flag this as a blocker because the failure mode is loud (user-visible message) not silent.

## Stage 2: Quality Review

**Mode: VERIFICATION.** The artifact has external adjudicators (pytest). 30 tests pass.

**What the PR does:**
1. Removes `_dispatch_via_popen` (131 lines: subprocess.Popen, start_new_session, per-execution log file, registry PID write).
2. Adds `_dispatch` (20 lines: thin wrapper around `_dispatch_via_inbox` from executor.py, forwards `agent_type`).
3. Threads `agent_type` from the routing decision through `_route_single_message` → `_dispatch` → `_dispatch_via_inbox`.
4. Removes `subprocess` and `uuid` imports.
5. Adds `orchestration.executor` to the mock dict in `_get_router_module()`.
6. Replaces `TestDispatchViaPopen` (4 Popen-specific tests) with `TestDispatch` (3 inbox-delegation tests).
7. Adds 2 new tests for agent_type forwarding.

**What would break without the key decisions:**
- If `agent_type` had not been threaded through, all inbox-dispatched UoWs would use `"functional-engineer"` regardless of what `route_wos_message` returned. The `lobster-meta` agent type would never be dispatched for philosophical UoWs.
- If `_dispatch_via_inbox` had been called directly in `_route_single_message` without the `_dispatch` wrapper, the module would have lost its mock seam and the existing test infrastructure would have required more invasive changes.

**Failure modes examined:**
- `_dispatch_via_inbox` raises `OSError` if inbox directory cannot be created. The PR correctly changes the test error from `RuntimeError("subprocess died")` to `OSError("inbox write failed")` — consistent with the documented exception type.
- The `_dispatch` wrapper logs `uow_id`, `msg_id`, and `agent_type` on success — adequate observability.
- `orchestration.executor` added to mock dict: the test loads the module via importlib with `sys.modules` patched. The `MagicMock(_dispatch_via_inbox=mock_inbox_dispatch)` form in `TestDispatch._load_real_module_with_mock_inbox` correctly injects the mock at the attribute level of the mocked module, which is how `from orchestration.executor import _dispatch_via_inbox` resolves.

**What this makes easier / harder:** Session store becomes authoritative for tracking; MAX_AGENTS_GATE becomes reliable. Per-execution forensic logs are no longer written — noted in migration plan, acceptable deferral.

**No new patterns to encode in learnings.md or golden-patterns.md.** The migration is structurally clean and matches the expected Path 2 outcome from the migration plan.
