### What the diff does

Three hunks in `src/mcp/inbox_server.py`:

1. **Text synthesis block (line ~5304):** Adds `elif msg_type == "wos_prescribe"` to the synthesis block that prevents `(no text)` from reaching the dispatcher. Synthesizes `wos_prescribe: uow_id=X, summary=Y` where summary is `msg.get("uow_summary", "?")[:60]`. The wos_execute analog uses only uow_id; prescribe adds summary (60-char cap). The extra field is appropriate — prescription messages carry a summary and surfacing it aids dispatcher orientation.

2. **Display block (line ~5348):** Adds `elif msg_type == "wos_prescribe"` display label `[WOS PRESCRIBE]`. Mirrors the wos_execute `[WOS EXECUTE]` label. Correct.

3. **dispatcher_hint block (line ~5373):** Adds `if msg_type == "wos_prescribe"` hint pointing to `route_wos_message()`. Uses `if` not `elif`, which is consistent with how the wos_execute hint is written (also `if`). The hint text differs slightly from wos_execute — wos_execute says "Do not read prose — use the structural route" while wos_prescribe says "Spawns prescription subagent." Both are actionable. No concern with the difference.

One hunk in `src/mcp/message_types.py`:

4. **INBOX_SYSTEM_TYPES additions:** Adds 7 new WOS types including `wos_prescribe`. The others (`wos_escalate`, `wos_done`, `wos_surface`, `steward_trigger`, `wos_uow_completed`, `wos_capacity_available`) were absent from the registry. Adding them closes the `mark_processing` warning path at line 5799 — messages of unknown type log a warning but are not rejected. The additions are registrations, not handlers; none of the 6 additional types gets a dispatcher_hint or text synthesis in this PR. This is correct — only wos_prescribe was the broken-prescription root cause.

### Structural observations

**No test added for wos_prescribe text synthesis/dispatcher_hint.** The wos_execute pattern was tested via `TestWosExecuteMessageFormatting` in `test_dispatcher_hint.py`. This PR adds the analogous wos_prescribe behavior but does not add a `TestWosPrescribeMessageFormatting` class. This is a gap. However: (1) the existing 16 tests in test_dispatcher_hint.py exercise the same code path through a concrete wos_execute message; (2) the wos_prescribe implementation is a structural mirror of wos_execute with one additional field; (3) the PR's stated test plan acknowledges this gap is covered by the existing 91 WOS tests. The gap is real but the risk is low — the pattern is established and the new code is minimal. This is advisory, not a blocker.

**The `if` vs `elif` consistency in the dispatcher_hint block.** The existing wos_execute hint uses `if msg_type == "wos_execute"` (not `elif`), and the new wos_prescribe hint follows suit with `if msg_type == "wos_prescribe"`. This is correct — these are independent `if` checks, not a chain. If they were `elif`, the second hint would not fire when checking a non-wos_execute message. The pattern is correct.

**The 6 additional INBOX_SYSTEM_TYPES entries have no dispatcher_hint wiring.** `wos_escalate`, `wos_done`, `wos_surface`, `steward_trigger`, `wos_uow_completed`, `wos_capacity_available` are now registered as known types but receive no special handling in `handle_check_inbox`. This is the current state of wos_execute before PR this fixed it. These types will show as generic messages (default `text = msg.get("text", "(no text)")`) unless they carry a text field. This is noted as potential future scope, not a blocker for this PR — the issue being fixed is `wos_prescribe` specifically.
