## Stage 2: Quality Review

**Scope question 1 — `list(status="executing")` vs broader ACTIVE:**

`Registry.list(status="executing")` filters on the exact DB string `"executing"`. `list_executing()` (a separate convenience method) returns `active + executing + ready-for-executor`. The PR correctly uses the narrow query. At stop time, `wos:executing` labels are applied only to UoWs that entered `EXECUTING` status (when the executor dispatches the UoW, `stamp_issue_executing` is called). UoWs in `active` (accepted by steward but not yet dispatched) or `ready-for-executor` (queued for dispatch) do not have `wos:executing` labels. The narrow scope is semantically correct.

**Scope question 2 — `LOBSTER_WOS_REPO` env var default:**

The env var is not set in any production config file and is not in the current environment. However, `os.environ.get("LOBSTER_WOS_REPO", "dcetlin/Lobster")` is the established pattern used identically in `executor.py` (2 call sites), `wos_completion.py` (2 call sites), and `wos-health-check.py`. The prior oracle decision archived at `oracle/legacy/decisions.md.archive:2371` explicitly accepted this risk: "acceptable for a single-instance deployment; it should be noted as a configuration requirement in any multi-instance scenario." This PR follows the established pattern without changing the risk profile.

**Scope question 3 — partial-recovery path registry sharing:**

In the partial-recovery path (execution_enabled=True, some jobs disabled), the diff inserts the label swap block between the existing `reg = registry if registry is not None else _Registry()` line and the subsequent `reg.log_control_event()` call. A single `reg` instance is used for both the swap's UoW query and the control event write. No second connection is opened. No conflict with the existing registry pattern — the sequence is: instantiate once → query executing UoWs → call label swap with issue numbers → log control event. The registry is accessed in the expected order.

**Cosmetic gap — color comment inaccuracy:**

`WOS_PAUSED_LABEL_COLOR = "e4e669"` is described as "grey to indicate suspended machine work" in the comment. The hex value `e4e669` decodes to R=228, G=230, B=105 — yellow-green, not grey. This is a comment inaccuracy with no behavioral impact. Noted for completeness; not a blocker.

**Failure modes:**

- A single gh CLI failure per issue is counted and logged as WARNING; the loop continues. The `(success_count, failure_count)` return is surfaced in the operator response. Correct.
- `_ensure_wos_paused_label_exists` failure is non-blocking — the swap proceeds even if the label-ensure step fails, with a warning logged. This is correct: if the label already exists from a prior call, the ensure step may fail or return False, but subsequent `gh issue edit --add-label wos:paused` calls will succeed if the label exists on the repo. If the label truly doesn't exist and creation failed, the per-issue swap will also fail — counted in `failure_count`.
- The operator always sees the swap result in the response (even 0/0), providing visibility into whether the operation had scope.

**What patterns this introduces:** Pure function + `(success_count, failure_count)` tuple return for bulk gh CLI operations. This is consistent with the existing `stamp_issue_*` function family in `wos_issue_lifecycle.py`. The pattern is worth encoding in golden-patterns.
