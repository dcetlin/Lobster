## Stage 1 (pre-implementation, adversarial prior)

Locked in before reading the diff: my prior was that this is either (a) solving a non-problem — repo-tracked narrative docs sitting inertly in `~/lobster/workstreams/` cost nothing and the "canonicity" framing is aesthetic tidiness masquerading as architecture — or (b) solving the right problem in a way that quietly loses data, since bulk deletions of content directories are exactly the kind of change where "migrated first, I promise" claims don't get checked.

Against (a): CLAUDE.md's own "Key Directories" and "Workstreams Convention" sections (both already committed, both predate this PR) are explicit and unambiguous: `~/lobster/` is "code only, no personal data," and "all strategic tracking lives in `$LOBSTER_WORKSPACE/workstreams/`... This directory is for git repos only — no strategy docs, no roadmaps, no tracking here" (Project Directory Convention, inverted statement of the same rule). A repo-tracked `workstreams/agent-council/canon/resistance-registers-lexicon.md` is a direct violation of an already-ratified convention, not a novel aesthetic preference invented for this PR. This is also a direct instance of the golden-pattern "canonical placement must be obvious from first encounter" (2026-04-25): "No split canonical homes: If something could plausibly live in two places, that ambiguity is the structural problem." Two directories with the same name and overlapping content (`~/lobster/workstreams/agent-council/` vs `~/lobster-workspace/workstreams/agent-council/`) is exactly the anti-pattern that entry names. This citation changed what I looked for: instead of asking "is 16 files of markdown worth a PR," I asked "does the migration actually collapse the split to one home, or does it just move the split" — which is why I went and diffed every migrated file rather than trusting the PR body's narrative.

Against (b) — the real risk: I did not treat "content preservation happened before this PR, verified by the author" as sufficient. The learnings.md pattern "full-repo grep as precondition for dead-code removal" (2026-04-25) was directly load-bearing here even though it's phrased for Python modules — the underlying claim ("nothing reads this, therefore it's safe to delete") is structurally identical, and that pattern's Rule 2 ("run the grep, don't extrapolate from a subdirectory") is exactly what stopped me from accepting the PR's blanket "no code references any of these files" claim at face value. I ran the grep myself, both on main and on the PR branch, across the full extension set (not just `src/`), and got zero hits against the repo path. Without that pattern in mind I might have accepted the PR's self-report and moved straight to checking the file list.

What this forecloses: nothing structurally. This is subtractive-only — no source code, no schema, no bootup file, no agent definition is touched. It does not touch the deferred `~/lobster/philosophy/` fork (88 files, same pattern, explicitly out of scope per the PR and per item 14 of the reorg list, which needs a separate intent call from Dan on whether that's an intentional git-backed archive). Correctly scoped — this PR does not opportunistically expand into that adjacent, harder decision.

One thing I want on record but do not treat as blocking: `git rm` removes the content from the working tree and future history, but the content remains fully recoverable from git history (`git show 329a5c95^:<path>` — which is exactly how I verified the diffs). If "no personal data in `~/lobster`" is meant literally and permanently, this PR does not achieve that in the git-history sense — only in the checked-out-tree sense. I don't think this is what CLAUDE.md's rule is asking for (rewriting a shared repo's history is a materially different, riskier operation that nobody asked for), but it's worth naming so a future reviewer doesn't assume "removed from repo" means "never existed in repo."
