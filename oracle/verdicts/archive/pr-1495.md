## Stage 1 — right problem?

**Prior entering this review:** that "consult the verdict file" is the kind of fix that sounds obviously right and could still be wrong in a way the PR author, having just built it, would not see — specifically around the exact question the dispatch prompt raised: does skipping re-dispatch for an APPROVED-but-still-open PR (PR #1489, which is oracle-approved but held for Dan's own merge decision) correctly distinguish "don't re-review" from "don't need Dan's attention"? **Golden-pattern citation and its effect on the review:** "no split canonical homes" / "canonical placement must be obvious from first encounter" (2026-04-25) and its generalization "full-repo grep as precondition for dead-code removal" (2026-04-25) together changed what I checked, not just what I labeled. Before accepting the PR's claim that `has_review_comment()`'s marker check is dead, I ran the full-repo grep myself rather than trusting the PR body's assertion (confirmed above — zero hits for `REVIEW_MARKER`/`<!-- lobster-review -->` outside the sweeper and its test). This mattered because the PR is deliberately choosing to leave a second, now-partially-redundant dedup mechanism (`has_review_comment`) in place rather than removing it — if that mechanism were still load-bearing anywhere, converging dedup onto the verdict file alone would have been the wrong call. It isn't load-bearing; the design doc at `docs/design/pr-review-layer.md` that describes a different, label-based dedup scheme (`lobster-reviewed` label) is explicitly `Status: DRAFT`, never implemented — so there is exactly one live source of truth for "has this PR been reviewed," and this PR correctly points the sweeper at it rather than inventing a third. This is the specific behavioral effect of the citation: it is why I verified dead-code-ness independently instead of accepting the PR's self-report, per the "full-repo grep" pattern's Rule 2 ("run the grep and verify zero matches before trusting the claim").

**Answering the dispatch prompt's core question directly:** yes, the verdict file is the correct dedup source of truth, and yes, fail-open on missing/unreadable/non-terminal is correct — with the reasoning made explicit rather than just accepted. I traced `scheduled-tasks/pr-review-sweeper.py` end to end: its only job is deciding whether to write a `pr_review_request` inbox message that causes the dispatcher to spawn an oracle review. It has no merge authority and never did — merging is a separate step in CLAUDE.md's PR Merge Gate flow, driven by the dispatcher reading the same verdict file and dispatching a *merge* agent, not by the sweeper. This means "PR #1489 is oracle-approved but still open, awaiting Dan's merge decision" and "the sweeper should stop re-dispatching oracle review for PR #1489" are not in tension at all — they are two independent consumers of the same file for two independent purposes. The sweeper's job (avoid redundant *review*) is fully discharged the moment a terminal verdict exists; whether Dan chooses to merge, hold, or reject that already-reviewed PR is a downstream decision this script has no role in and does not gate. Suppressing sweeper noise for an approved-but-held PR does not suppress any signal Dan needs, because the sweeper was never the channel through which "this needs your merge decision" was communicated — the presence of the committed `VERDICT: APPROVED` file itself (and whatever surfaces it, e.g. Option A's GitHub review post or the dispatcher's own gate check) is that channel, and this PR does not touch either.

On fail-open specifically: the three fail-open branches (missing, unreadable, `NEEDS_CHANGES`) all correctly preserve the sweeper's original behavior for cases where a review genuinely might still be needed — a PR that was never reviewed, a verdict file the sweeper can't parse (safer to over-review than silently stop reviewing), and a PR mid-fix-loop. I checked whether fail-open on `NEEDS_CHANGES` could create a *new* double-dispatch risk against the dispatcher's own internal oracle→fix→re-oracle loop (i.e., sweeper firing a competing review while the dispatcher is already mid-loop on the same PR) — this risk is real but pre-existing and untouched by this PR: before this change, the sweeper had zero awareness of verdict files at all and would dispatch on any open, comment-free PR regardless of `NEEDS_CHANGES` state, so this PR strictly narrows the sweeper's over-dispatch surface, it does not introduce a new one.

## Stage 2 — well made?

**Encoded Orientation check (constraint-3):** this PR does not modify agent definitions, bootup files, gate tables, vision.yaml, or CLAUDE.md, and does not introduce a new behavioral default or decision rule — it makes an existing Type B cron script consistent with a source-of-truth convention (the oracle verdict file) that CLAUDE.md's PR Merge Gate already establishes as authoritative. This does not meet the bar for an Encoded Orientation decision requiring a fresh logged decision + vision.yaml anchor; it is closer to a bug fix that removes a divergence from already-decided policy.

**Correctness, independently verified (see reproduction block above):** path resolution (`ORACLE_VERDICTS_DIR = _REPO_ROOT / "oracle" / "verdicts"`, matching the real `~/lobster/oracle/verdicts/` layout used by every other verdict file in this repo), first-line exact match (consistent with `lobster-oracle.md`'s own spec: "The first line MUST be exactly `VERDICT: APPROVED` or `VERDICT: NEEDS_CHANGES`"), and error handling (missing file, empty file, directory-instead-of-file, all fail open) are all correct and all exercised by tests except the empty-file `IndexError` case specifically, which is covered by the exception handler's structure but has no dedicated test — a minor gap, not a correctness defect, since the same `except Exception` branch that the "unreadable" test exercises also catches it.

**Test quality:** non-vacuous. The PR's own regression check (revert to `origin/main`, re-run the new test file, confirm collection failure on the now-missing `VERDICT_APPROVED_LINE` attribute) was independently reproducible in spirit — I did not re-run that exact revert, but I ran the equivalent check by loading the module from `origin/main` directly in the worktree tests and confirming `VERDICT_APPROVED_LINE`/`has_final_verdict` do not exist there, which is the same fact the PR's stated check establishes. Both `has_final_verdict()` unit tests and the `main()`-level end-to-end test are present — the latter (`test_dispatch_skipped_for_pr_with_stale_state_but_committed_approved_verdict`) is the one that actually reproduces issue #1491's exact scenario (stale/absent state entry + committed verdict → no dispatch), not just the unit-level function. The negative control (`test_dispatch_proceeds_for_pr_with_no_verdict_and_no_state_entry`) is the right sanity check — it confirms the fix does not make the sweeper inert, which is the failure mode a badly-scoped fail-closed version of this change could have introduced.

**No regressions:** confirmed independently — 132/132 non-pre-existing-failure tests pass across the whole `tests/unit/test_scheduled_tasks/` directory; the 10 failures are reproduced identically on `main` with zero PR changes present. `grep` across `src/`, `.claude/`, `scheduled-tasks/`, `scripts/`, `hooks/` for any other consumer of `pr_review_sweeper`/`has_review_comment`/`REVIEW_MARKER` returns nothing beyond `message_types.py`'s two type-string registrations (unaffected by this diff).

**Failure modes / what would break without the key decision:** without the exact-first-line-match (as opposed to, say, a substring search for "APPROVED"), a verdict file whose *rationale prose* happened to contain the word "APPROVED" out of context could false-positive — the exact-match design correctly avoids this. Without the fail-open default on `NEEDS_CHANGES`, a PR legitimately mid-fix-loop would stop receiving sweeper coverage as a safety net if the dispatcher's own loop stalled — the PR's choice to fail open here is the safer default and is stated as deliberate, not accidental.

**Named gap, not blocking:** the verdict file has no binding to the PR's current HEAD commit SHA — `has_final_verdict()` returns `True` for any committed `VERDICT: APPROVED` regardless of whether new commits have landed on the PR since that verdict was written. This is a real staleness gap, but it is not introduced by this PR — it is a property of the whole verdict-file-as-authority convention already used identically by the dispatcher's own PR Merge Gate (which also checks only the first line, with no SHA comparison, per `.claude/agents/lobster-oracle.md`). Fixing this here would widen the PR beyond issue #1491's scope into a pre-existing architectural gap that affects the merge gate equally; flagging it as a forward note for the whole verdict-file convention (not as a blocker for this PR) is the correct scope call, consistent with the reuse guidance in the "split a conflated directory-role parameter" golden pattern.

**Patterns this introduces:** the pattern of a Type B script reading `oracle/verdicts/pr-{n}.md` as a pure local-filesystem check (no `gh` API call, no git operation) to consult the same source of truth the dispatcher's PR Merge Gate already uses is reusable anywhere else a script needs to know "has this PR's review concluded" without re-deriving it — e.g., a future health-check or staleness sweep over open PRs.
