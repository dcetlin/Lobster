## Round 1 — 2026-05-23

### Stage 1: Vision Alignment (written before reading implementation)

**Prior entering this review:** This implementation is solving the wrong problem, or solving the right problem in a direction that forecloses better paths.

The PR description states the problem plainly: `_log_dispatch_boundary` documented `outcome` as one of `"success"`, `"retry"`, `"failure"` and `dispatch_attempt` as `"1 for first, 2+ for retries"` — but no code path ever produces `outcome="retry"` or `dispatch_attempt > 1`. The fix chosen (annotate as reserved, add tests) is compared against the alternative (implement retry loop).

What would have to be true for this work to be the right path?

The dispatch boundary already has a recovery mechanism — steward heartbeat stall detection fires within ~8 minutes. The question for Stage 1 is: is annotating dead enum values as reserved the right action here, or does the existence of these phantom contract claims signal that the retry loop *should* be implemented?

Three orientations are relevant from vision.yaml:

- `principle-1`: Proactive resilience over reactive recovery. The stall detection being the only recovery path is a reactive recovery at an 8-minute bound. If the undocumented "retry" semantics were there because they were meant to be implemented, annotating them as permanently reserved forecloses that direction.
- `principle-2`: Ergonomics over shortcuts. Adding dead enum documentation is not a shortcut — it is honest debt marking.
- `principle-3`: Determinism over judgment for conditionals. Docstring cleanup is deterministic maintenance.

The cheaper test of the underlying assumption: does anything in the codebase or issue history indicate the retry loop was intended as a near-term feature rather than perpetually deferred? The PR description and the UoW reference (`uow_20260430_8b206e`) don't indicate planned retry implementation. The PR explicitly reasons: stall detection covers the recovery case; a retry loop would add complexity without improving the recovery time bound meaningfully. This reasoning is sound — the retry logic would need to be aware of the steward cycle to avoid doubling up on a UoW that the steward is already recovering.

What does this work foreclose? It forecloses interpreting the phantom retry documentation as a planned feature. Future implementers who add retry semantics will need to consciously un-reserve the values. That is a feature, not a foreclosure problem — the reservation makes the intent legible.

**Alignment verdict: Confirmed.** The theory of change is: dead contract claims mislead consumers (human and agent); annotating them as reserved is cheaper, lower-risk, and structurally honest compared to implementing the retry loop at the dispatch-boundary level. This is consistent with the current phase intent (WOS substrate health, not feature expansion), `principle-1` (proactive contract honesty over reactive discovery of misleading docs), and `principle-3` (the retry question is a future Deliberative-register decision, not an Encoded Orientation change).

No premise-review item is warranted.

### Stage 2: Quality Review

**Encoded Orientation check (constraint-3):** This PR changes docstrings and documentation annotations. It does not change behavioral defaults, system constraints, agent identity, or decision-making rules in a durable way. The reserved annotations explicitly defer the retry decision to a future loop. **Residual inconsistency (minor, does not block APPROVED):**

The module-level `#:` comment immediately above `_DISPATCH_BOUNDARY_LOG_TEMPLATE` (line 1326 of executor.py) reads: `#: Records all dispatch attempts, retries, and failures at the executor→inbox boundary.` This comment uses "retries" and was not updated by the PR. It is a minor inconsistency — a new reader of the constant declaration would still see the phantom "retries" claim. The four function-level docstrings and two documentation files were all corrected; this single-line module comment is the only survivor. Given the PR correctly resolves the primary contract claim surfaces (the function that actually accepts `outcome` and `dispatch_attempt` parameters, plus both doc files), the residual comment is a cosmetic gap rather than a misleading contract claim. It does not affect any consumer's understanding of the callable API.

**What would break without the key decisions made here?**

The decision to mark as reserved (Path A) rather than implement (Path B) is the structurally load-bearing choice. If Path B had been chosen, the retry loop implementation would need to reason about the steward's TTL-based recovery — avoiding double-dispatch of a UoW the steward has already queued for recovery. Path A avoids this complexity entirely. The tests pin the contract at the observable boundary: `dispatch_attempt == 1` and `outcome in {"success", "failure"}` are now machine-checkable invariants, not just docstring claims.

**Test design:**

The four tests are well-structured:

- `test_success_record_contains_required_fields` — asserts the full required field set, including `"failure_reason" not in rec` for the success case. This is the correct positive assertion pattern.
- `test_failure_record_contains_failure_reason` — asserts `"msg_id" not in rec` for the failure case. Symmetric and correct.
- `test_dispatch_via_inbox_always_logs_attempt_1` — the key contract-pinning test. Patches `_DISPATCH_BOUNDARY_LOG_TEMPLATE` and `_INBOX_DIR_TEMPLATE` directly from the production module (not local mirrors). This is the correct pattern per learnings.md (PRs #696, #800, #967, #970, #973, #974).
- `test_log_write_failure_does_not_raise` — verifies the non-blocking best-effort semantics. Correct use of a `blocker` file to produce a `NotADirectoryError` on subdirectory creation.

All four tests use `orig = executor_mod._CONSTANT; try: ...; finally: executor_mod._CONSTANT = orig` for cleanup — correct teardown without fixtures.

**Patterns introduced:**

The PR introduces the "reserve-rather-than-remove dead enum values" pattern in documentation: instead of silently deleting dead contract claims, name them as reserved for a future use case. This is correct for cases where the values might plausibly be implemented — it preserves design intent without overpromising.

**What does this make easier/harder for future work?**

Easier: any future PR implementing a retry loop can cite the reserved values and un-reserve them. The contract history is legible. Harder: nothing — reserving values is reversible.
