## Stage 2: Quality Review

### Fix #1280: Dynamic timezone in sys.subagent.bootup.md

**What it does:** Replaces hardcoded "EDT (UTC-4) / EST (UTC-5)" rule with a dynamic lookup: check `LOBSTER_USER_TZ` env var first; if absent, read it from `~/lobster-user-config/agents/user.base.bootup.md`.

**Does it do what it claims?** Yes. The replacement text is accurate. The env var `LOBSTER_USER_TZ` is an established convention (PR #1169 confirmed it was applied to the dispatcher already). The fallback to the bootup file is an appropriate degradation path.

**Implementability concern (from learnings prior):** Subagents are given a runtime environment. The env var lookup is straightforward. The file-path fallback requires the subagent to be able to read `~/lobster-user-config/agents/user.base.bootup.md` — this path is accessible to subagents (it is in the standard lobster-user-config tree). The instruction "look for a `LOBSTER_USER_TZ=` line or the timezone preference" is slightly informal but sufficient — a subagent capable of following other bootup instructions is capable of reading this file.

**What failure mode exists?** If LOBSTER_USER_TZ is not set and the bootup file does not contain a clear timezone line, the subagent has no fallback. The instruction does not specify what to do in that case — previously it defaulted to ET. This is a minor gap: the degradation path is under-specified. However, given that Dan is moving from ET to PT (a known, logged transition), the env var will be set and this gap will not materialize in practice. Note for future: if the env var is not set and the file is ambiguous, there is a silent failure mode where the subagent uses an incorrect timezone with no error signal.

**Verdict on #1280:** Correct fix. The under-specified fallback-of-fallback is acceptable given the operational context.

### Fix #1281: Replace nonexistent `forward=` parameter in lobster-oracle.md

**What it does:** Removes `forward=true` / `forward=false` from the oracle's Completion section and replaces with `sent_reply_to_user=False` plus guidance to make verdict prominent in the `text` field for surfacing.

**Reviewer concern verification:** The concern was whether collapsing both forward=true and forward=false to `sent_reply_to_user=False` matches actual dispatcher routing behavior for oracle results.

**Actual dispatcher routing (verified from sys.dispatcher.bootup.md lines 415–651 and the subagent result handler):**
- `sent_reply_to_user=True` → dispatcher marks processed, does not relay (user already has it)
- `sent_reply_to_user=False` → dispatcher reads the text, runs the SEED/PEARL/relay classifier, and decides whether to surface it

The oracle NEVER calls `send_reply` directly (confirmed by the agent definition: it writes to verdict files). So `sent_reply_to_user=False` is structurally correct — the oracle always returns False.

**How does surfacing to Dan happen?** Under the old text, `forward=true` was described as causing the dispatcher to "surface it to the user." The new text says "make the verdict prominent in the `text` field so the dispatcher surfaces it to the user." This is behaviorally correct: when `sent_reply_to_user=False`, the dispatcher's relay classifier runs on the text. A prominent Questioned/Misaligned verdict in the text will route through the relay path.

**What was lost?** The old `forward=` parameter implied a binary gate: forward=true means definitely surface it. The new form relies on the dispatcher's text-content classifier, which is a content-based heuristic, not a deterministic gate. This is a small semantic change: oracle results flagged as Questioned/Misaligned now depend on the relay classifier making the right call, rather than an explicit `forward=true` flag.

**Is this acceptable?** Yes. The `forward=` parameter did not exist in `write_result` — it was a fiction. The real surfacing mechanism was always the dispatcher relay classifier. The new text is more honest about what actually happens. The instruction to "make the verdict prominent in the `text` field" is an appropriate compensating instruction.

**Verdict on #1281:** Correct fix. The collapse of both forward values to `sent_reply_to_user=False` matches actual dispatcher routing. The surfacing mechanism is now accurately described as text-content-based rather than a nonexistent flag.

### Fix #1282: Ack message selection rule in sys.dispatcher.bootup.md

**What it does:** Adds a new behavioral selection rule: personality-flavor ack messages (from `compact-ack-messages.json`) are used only during compaction/restart catchup; plain "On it — [what]" is used for all other acks.

**Encoded Orientation check:** This PR encodes a new behavioral default into a bootup doc — specifically a decision-making rule for ack message selection. This constitutes an Encoded Orientation change (constraint-3 applies).

Checking for prior logged decision and vision.yaml anchor:
- The rule addresses `compact-ack-messages.json`, which exists in the codebase. The file's existence implies prior intent to use it. Issue #1282 named the gap: the file existed but there was no documented rule for when to use it.
- The rule itself encodes a behavioral constraint: do NOT use personality ack for routine task acknowledgment. This is a new constraint, not a correction to an existing one.
- vision.yaml anchor: constraint-4 ("minimize metabolic cost of cybernetic engagement") — misusing personality ack for routine tasks would create misaligned tone, increasing friction. The rule is defensibly anchored here.
- Prior logged decision: there is no oracle/verdicts/ decision file for this specific behavior. However, the issue #1282 was generated by the Night 2 negentropic sweep, and the rule being added is corrective (closing a documentation gap for a feature that already exists). This is not introducing a new capability — it is documenting when an existing capability applies.

**Constraint-3 assessment:** The rule is advisory (it is prose in a bootup doc, not a hook). It changes a behavioral default but does not introduce new automated behavior — the ack messages already existed. The "is compaction/restart" trigger is human-interpretable context the dispatcher recognizes, not a new automated condition. This is below the threshold that would require a formal logged decision, especially given the vision.yaml anchor to constraint-4 is clear.

**Is the "compaction/restart only" constraint correctly stated?** Yes. The text specifies:
- Use personality-flavor: "only when acknowledging that you are recovering from a compaction or restart — i.e., when sending the 'catching up' signal during compact-catchup startup"
- Example trigger: "user asks a question right as a compaction-restart is completing"
- Use plain: "all direct user requests, normal task dispatches, and any non-restart ack"

The distinguishing principle ("what happened to you" vs. "what the user asked") is clear and operationally usable. The constraint is correctly stated.

**Pattern introduced:** The selection rule is advisory prose. Given the "advisory-to-hook promotion" golden pattern, the question arises: should this be a hook? The answer is no — the trigger condition ("is this a compaction-restart catchup?") requires semantic judgment about the dispatcher's context state, not a string pattern on tool input. It cannot be reliably expressed as a PreToolUse hook. Advisory is correct here.

**Verdict on #1282:** Correct fix. Constraint-3 does not block it. The compaction-only constraint is correctly stated.
