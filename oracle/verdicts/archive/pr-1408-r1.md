## NEEDS_CHANGES finding

**Mirror-constant in test file (mirror-constant pattern, learnings.md — 10+ recurrences)**

The test file declares two module-level constants:
```python
ISSUE_CLOSED_STATE = "CLOSED"
ISSUE_OPEN_STATE = "OPEN"
```
These mirror `_GITHUB_ISSUE_STATE_CLOSED = "CLOSED"` introduced in `steward.py` by this PR. The test assertions use the test-file-local constants rather than importing from the production module.

This is the exact failure class documented in learnings.md across PRs #696, #800, #967, #970, #973, #974, #980, and others. When the production constant changes, the test assertions silently validate against stale values.

**Fix required:** Remove `ISSUE_CLOSED_STATE` and `ISSUE_OPEN_STATE` from `test_steward.py`. Import `_GITHUB_ISSUE_STATE_CLOSED` from `src.orchestration.steward` at the top of `TestSourceIssueClosedCompletion` or at the test-file module scope. Construct `IssueInfo` instances using the imported constant, not a local string. The `ISSUE_OPEN_STATE = "OPEN"` constant has no production counterpart — use the string literal directly in helper `_make_open_issue_info`, or add `_GITHUB_ISSUE_STATE_OPEN = "OPEN"` to production and import it.

No other NEEDS_CHANGES findings.

This is correct alignment with `principle-1` (proactive resilience over reactive recovery) and `principle-3` (determinism over judgment for conditionals — a closed GitHub issue is a binary field check, not an LLM judgment).

The only thing this forecloses is a UoW whose GitHub issue is closed but whose owner wants it to run again anyway — but that scenario would require the owner to reopen the issue, which is the correct external signal to use.

**Opportunity cost:** Minimal. Two additions to `steward.py`, 274 lines of tests. Well-scoped.

## Stage 2: Quality review

### Author's three flagged concerns

**Concern 1 — Override ordering (closed-issue check fires AFTER hard_cap override):**
The ordering is correct. The sequence in `_diagnose_uow` is:
1. `_assess_completion` may produce `is_complete=True` for completed UoWs or `False` for first_execution
2. `stuck_condition = _detect_stuck_condition(...)` — may produce `hard_cap`
3. `if stuck_condition == "hard_cap": is_complete = False` — hard_cap sets False
4. [NEW] `if _source_issue_is_closed(issue_info): is_complete = True; stuck_condition = None` — closed-issue overrides True

This ordering is sound. The hard_cap step at (3) exists to prevent infinite LLM loops; a closed issue at (4) is definitive external evidence the loop has ended. The last writer wins, and the closed-issue check is correctly last.

**Concern 2 — stuck_condition cleared to None when is_complete=True for closed issue:**
The clearing is correct. In `_process_uow`, the routing sequence is:
1. `if stuck_condition == "owner_decision_required"` → fast-path return
2. `if stuck_condition:` → surface to Dan
3. `if is_complete:` → declare done
4. else → prescribe

When a closed-issue UoW has `is_complete=True, stuck_condition=None`, it correctly reaches branch 3 (declare done). If `stuck_condition` were not cleared, a hard_cap UoW with a closed issue would go to branch 2 (surface to Dan), which would be noise — the issue is resolved. The clearing is intentional and correct.

`executor_blocked` and `owner_decision_required` are conditions based on executor output from a previous run. For a UoW whose source issue is already closed, those prior conditions are superseded. The silencing is correct semantics, not a silent bypass of a live problem.

The PR description accurately names this: "A closed issue supersedes all stuck conditions including hard_cap." The comment in the diff states this reasoning explicitly, which is load-bearing documentation for future reviewers.

**Concern 3 — "CLOSED" constant (uppercase) matches gh CLI output:**
Confirmed correct. Verified against production:
```
gh issue view 843 --repo dcetlin/Lobster --json state → {"state":"CLOSED"}
gh issue list --repo dcetlin/Lobster --state open --limit 3 --json number,state → [{"state":"OPEN"}, ...]
```
`_fetch_github_issue` uses `data.get("state", "open")` (lowercase "open") as the default fallback for missing state. This fallback correctly fails the `== "CLOSED"` comparison, which is the safe behavior.

Note: the fallback default `"open"` is lowercase while gh CLI returns `"OPEN"` uppercase. This is not a bug — the fallback only fires when the JSON response is missing the `state` field (error case), and in that case a lowercase "open" simply means the check correctly returns False (not closed). However, if any downstream code were to compare `issue_info.state == "OPEN"` it would miss the fallback case. The PR does not introduce such a comparison, so this is a note rather than a finding.

The test file at module scope declares:

```python
ISSUE_OPEN_STATE = "OPEN"
```

Production introduces `_GITHUB_ISSUE_STATE_CLOSED = "CLOSED"` in `steward.py`.

The learnings.md mirror-constant pattern entry (cited 10+ times across PRs #696, #800, #967, #970, #973, #974, #980 and more) is the active prior here. The behavioral effect on this review: this finding was checked first, before reading test logic, because learnings.md establishes it as a "first-pass oracle check, not a per-PR discovery" (2026-04-26 Meta entry). The `ISSUE_OPEN_STATE = "OPEN"` constant has no production counterpart. The fix options are:
- Use `"OPEN"` as a literal in `_make_open_issue_info` (acceptable, since no production constant exists)
- Add `_GITHUB_ISSUE_STATE_OPEN = "OPEN"` to `steward.py` and import it (correct if the production code will eventually need it)

### Other observations (non-blocking)

**executor_outcome = None override:** The closed-issue block sets `executor_outcome = None` alongside `is_complete = True`. This is harmless — `executor_outcome` is only used in the prescription path (step 4c), which is not reached when `is_complete=True` sends the flow to step 4b. But setting it to None provides no benefit either; the original value would be irrelevant regardless. This is dead code in the override block. It's not worth a NEEDS_CHANGES but could be removed without effect.

**Feature bundling check:** PR modifies only `src/orchestration/steward.py` and `tests/unit/test_orchestration/test_steward.py`. Two files, one purpose, no bundling.

**Encoded Orientation check:** Not triggered. No behavioral defaults, agent identity, or system constraints are changed. The check fires and passes silently.

**Test coverage quality:** 7 tests are well-targeted:
- Unit test for the primary livelock scenario (first_execution + closed issue)
- Regression guard (open issue stays False)
- Regression guard (None issue_info stays False)
- Closed issue overrides hard_cap
- Integration: run_steward_cycle transitions to "done"
- Integration: open issue does not close in cycle

The integration test `test_closed_issue_marks_uow_done_in_steward_cycle` uses a real DB and registry, which is higher-confidence than pure unit tests for state transitions. Good coverage posture.

**Source issue number in completion_rationale:** `uow.source_issue_number` is interpolated into the rationale string. If `source_issue_number` is None (non-GitHub source UoW), `_source_issue_is_closed` would return False before this block is reached (because `issue_info` would be None for non-GitHub sources, causing the early return). So `source_issue_number` is effectively guaranteed to be non-None when the override fires. This is correct, but worth a note in the docstring. Not a NEEDS_CHANGES.
