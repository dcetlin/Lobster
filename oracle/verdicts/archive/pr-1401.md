# Oracle Review: PR #1401 — fix(wos): raise DEFAULT_MAX_PARALLEL from 2 to 5

## Summary

This PR raises `DEFAULT_MAX_PARALLEL` from 2 to 5 in `shard_dispatch.py` and updates `_DEFAULT_WOS_CONFIG["max_parallel"]` to 5 in `dispatcher_handlers.py`. Test assertions that hardcoded the old value of 2 are updated to use `DEFAULT_MAX_PARALLEL` dynamically. The change is narrowly scoped, well-reasoned, and backed by production evidence.

---

## Review Criteria

### 1. Correctness

**Pass.** The change is internally consistent:

- `DEFAULT_MAX_PARALLEL = 5` in `shard_dispatch.py` matches `"max_parallel": 5` in `_DEFAULT_WOS_CONFIG`.
- `read_max_parallel()` reads from `wos-config.json` at runtime, falling back to `_DEFAULT_WOS_CONFIG["max_parallel"]` — both are now 5.
- The `check_shard_dispatch_eligibility` function is unchanged; only the constant it gates on is updated.
- The ScalingGovernor (`N/5` cap on proposed eligible UoWs) is a separate layer that operates on *eligible UoWs per cycle*, not on the shard-stream parallel cap. No interaction risk.
- `MAX_CONCURRENT_PRESCRIPTIONS=5` (PR #1391) caps concurrent prescription subagents. That is a prescription-phase gate, not an execution-phase gate. Aligning both caps at 5 is logical and the PR correctly notes this alignment.

### 2. Test Coverage

**Pass.** 36 tests pass. Key tests updated correctly:

- `TestMaxParallelCap::test_at_max_parallel_blocks_dispatch` — refactored to use a list comprehension of `DEFAULT_MAX_PARALLEL` stubs instead of a hardcoded pair. This is strictly more correct: the test now documents the actual cap behavior rather than a specific count.
- `TestNullScopeIndependent::test_null_scope_still_blocked_by_max_parallel` — same improvement.
- `TestDefaultMaxParallel::test_default_is_five` — correctly documents the new invariant.
- `TestWithinCycleAccumulation::test_two_non_overlapping_dispatched_in_same_cycle` — retained with max_parallel=2 hardcoded (tests the function behavior at a specific value, not the default constant). This is correct: this test is not about the default.

No tests were deleted. No test coverage was weakened.

### 3. Rationale Quality

**Pass.** The rationale in `shard_dispatch.py` is unusually thorough:

- Cites the production incident (uow_20260522_fa2150, 34 blocked cycles).
- Identifies that the original constraint was file-scope conflict, not global serialization — the correct framing.
- Names all remaining throttles that prevent overload at the new cap.
- References the PR that established the consistent value (PR #1391).

### 4. Scope Discipline

**Pass.** Only three files changed:

- `src/orchestration/shard_dispatch.py` — constant and comment updated.
- `src/orchestration/dispatcher_handlers.py` — default config updated, comment updated.
- `tests/unit/test_orchestration/test_shard_dispatch.py` — test assertions updated to match.

No unrelated files touched.

### 5. Runtime Safety

**Pass.** The change is runtime-overridable via `wos-config.json "max_parallel"` key without restart. The existing `read_max_parallel()` mechanism already handles this. If the production instance already has `max_parallel: 5` in `wos-config.json` (as noted in the PR), the effective behavior is unchanged at deploy time.

### 6. No Regressions Introduced

**Pass.** The steward, executor, and shard dispatch logic are all unchanged. Only the constant and its documentation are updated.
