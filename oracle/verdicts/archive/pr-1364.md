## Scrutiny Results

### 1. touchstart delegate + e.preventDefault() — PASS with known tradeoff

Handler is registered `{ passive: false }`, which is required for `preventDefault()` to work in Chrome and modern browsers. Without this, `preventDefault()` on touchstart is silently ignored.

**Known tradeoff (not a bug):** `e.preventDefault()` on touchstart when the touch starts on a vocab term blocks scroll for that touch gesture. If a user places their finger on a term as the first contact point of a scroll gesture, the page will not scroll. This is a fundamental tradeoff with all `{ passive: false }` touchstart handlers. The behavior is acceptable for an inline vocab tooltip — terms are typically tapped, not used as scroll anchors — but worth documenting if UX complaints arise.

**Synthetic click suppression:** The 300ms synthetic click is correctly suppressed. The `{ passive: false }` + `e.preventDefault()` pattern is the right approach.

### 2. repositionTip() coordinate arithmetic — MINOR BUG (non-blocking)

**Normal-screen right/left edge correction:** Correct. `getBoundingClientRect()` gives viewport-relative coordinates. The adjustments are computed as deltas applied to `tip.style.left` (offset-parent-relative). Since the delta is viewport-relative and the offset parent is `.vocab-term` (position: relative), the delta is invariant to scroll. No `window.scrollX/Y` adjustment is needed for delta shifts. This is correct.

**Narrow-screen centering (vw < 400px):** Minor arithmetic error.

Code:
```js
var centreLeft = (vw / 2) - (tipRect.width / 2);
var offsetLeft = centreLeft - termRect.left + (termRect.width / 2);
tip.style.left = offsetLeft + 'px';
```

The correct formula (for CSS `left` in offset-parent coords, where offset parent is `.vocab-term`) is:
```
offsetLeft = centreLeft - termRect.left
```

The code adds `+ (termRect.width / 2)`, which shifts the tip right by half the term's width. For typical short terms (30–60px wide), this is a 15–30px rightward shift from center. On a 375px iPhone viewport the tooltip would appear ~15–30px right of true center. Visually this is a slight misalignment, not a functional failure. The tooltip still stays on screen and is readable.

**Severity:** Minor. Does not break functionality; causes slight right-shift on narrow screens proportional to term width. Can be fixed post-merge.

### 3. One-at-a-time invariant + race condition — PASS

No race condition exists. The document touchstart handler checks `e.target.closest('.vocab-term')` before any closeAll() call. If a term is tapped:
1. `termEl` is found → early-return path
2. `closeAll()` runs before the new tip opens (synchronous, no async gap)
3. The new tip is opened

The document-level close-on-outside-tap path (`if (!tipEl) { closeAll() }`) is unreachable when tapping a term. No second handler exists that could close the just-opened tip.

### 4. × close button + toggle logic — PASS

The `closeBtn` check runs before the `termEl` check and early-returns. When × is tapped:
- `closeBtn` is found → `parentTerm.classList.remove('vocab-tip-open')` → closes → returns
- The term tap toggle never fires

When the term text itself is tapped:
- `closeBtn` is null (× is a child of `.vocab-tip`, not a direct descendant of `.vocab-term` being closest-matched first in e.target)
- Actually: if the tap lands on the × button, `e.target.closest('.vocab-tip-close')` returns the button AND `e.target.closest('.vocab-term')` would also match. But closeBtn is checked first. Correct behavior.

If user taps the term text area (not the × button): `closeBtn` is null, `termEl` is found → toggle logic runs. Correct.

### 5. .vocab-tip-below CSS caret — PASS

Normal (above-term) caret: `border-top-color: var(--border2)` at `top: 100%` — downward-pointing caret at the bottom of the card, pointing toward the term below. Correct.

Below-term caret: `border-bottom-color: var(--border2)` at `bottom: 100%` — upward-pointing caret at the top of the card, pointing toward the term above. Correct. `border-top-color: transparent` is explicitly set in the below variant to clear the default.

### 6. Test shallowness — ACKNOWLEDGED, non-blocking

All 26 new tests verify rendered HTML/JS string content from Python — they cannot execute JavaScript in a browser. This is structurally limited but accurately documented in the test file header: "Tests verify that the rendered output contains the JS and CSS constructs needed for these behaviors."

The tests confirm: correct event types wired, correct CSS classes managed, correct threshold constants present, correct structural constructs (getBoundingClientRect, repositionTip called after open class added). This is the right level of testing for a Python-rendered JS component without a headless browser in the test suite.

### 7. Dead code nit — non-blocking

`isTouchDevice` (lines 395–399) is computed but never used. Touch events are unconditionally registered. The variable is dead code. Harmless but misleading.
