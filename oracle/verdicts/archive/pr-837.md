### Stage 1: Vision alignment (formed before reading implementation)

**Adversarial prior:** This implementation is solving the wrong problem, or solving the right problem in a direction that forecloses better paths.

The question this work is meant to serve: Build the StewardHeartbeat class with OODA vision context integration — the typed OO wrapper around the existing `run_steward_cycle()` engine, plus the `fast_thorough_selector.py` meta-selector for OODA loop routing.

What would have to be true for this to be the right path:

1. The existing `run_steward_cycle()` engine handles core UoW processing correctly and this wrapper adds behavioral structure (audit trail, vision context, typed outputs) without duplicating it.
2. The `fast_thorough_selector.py` reflects an actual gap in decision-making that the codebase currently lacks — not a theoretical formalization of what the dispatcher already does by other means.
3. The timing is right: the WOS executor is live (confirmed: `execution_enabled=True`, 2026-05-18), making the Steward's cycle critical path rather than aspirational.
4. The work does not foreclose the Executor implementation by prescribing a format it cannot consume.

**Encoded Orientation check (constraint-3):** This PR adds `StewardHeartbeat` with convergence/anti-convergence behavioral defaults (anti-convergence alert threshold at `steward_cycles >= 3`, close-on-completion logic) and the Fast/Thorough Path meta-selector (a decision-routing behavioral default). These are Encoded Orientation decisions: they change agent decision-making rules in a durable way.

Checking for prior logged decision and vision.yaml anchor:
- The UoW spec (issue #228, `uow_20260422_a2db63`) explicitly specifies the audit-before-transition invariant, the convergence conditions, the anti-convergence signals, and the vision context requirement. The issue is the logged prior.
- `vision.yaml constraint-3` is the explicit anchor. The issue spec was written against it — the `select_path()` function mirrors the constraint-3 Fast/Thorough Path language verbatim.
- The anti-convergence threshold (3 cycles) is specified in the issue: "Three or more cycles without a concrete artifact" is listed as an anti-convergence signal.

**Both conditions are met.** Constraint-3 is satisfied.

**Cheaper test I was looking for:** Could the vision context integration be achieved without a new class by adding `vision_fields_cited` to the existing `Diagnosis` dataclass and `CycleResult`? Possibly — but that would scatter the audit-trail write and convergence logic into the already-4340-line `steward.py` as procedure. The class boundary is a correct seam (golden pattern: seam-first abstraction). The separation is not decorative.

**What this forecloses:** The class-based heartbeat approach commits to an object lifetime per run (inject registry, call `run()`, read result). A future refactor to a coroutine or async model would require re-wrapping. This is a low-severity foreclosure — the OODA architecture does not imply async, and the cron heartbeat model explicitly calls for single-invocation runs.

**Opportunity cost:** The vision.yaml `current_constraint` names the WOS bidirectional interface (#1118) and completion notification layer as the active constraint. This PR is not that. However, it is the `uow_20260422_a2db63` implementing UoW — meaning it was already in the WOS queue. The PR description references the correct UoW ID and the work is within the active WOS Phase 1 envelope.

**Alignment verdict: Confirmed.** The work serves the Vision Object substrate goal (constraint-2: every UoW carries traceable vision fields in the audit record) and the Phase 1 completion criteria. The timing is correct given that the executor is live. The class boundary is the right structural seam.

#### Does it do what it claims?

**StewardHeartbeat:**
- `run()` correctly delegates to `run_steward_cycle()` — no logic duplication.
- `diagnose()` fetches vision context (file-backed fallback), delegates core diagnosis to `_diagnose_uow()`, and wraps the result in `DiagnosisRecord` with vision fields. Correct.
- `prescribe()` calls `select_workflow()`, formats workflow artifact content, writes via `_write_workflow_artifact()`. Dry-run skip is correctly gated. Correct.
- `write_audit_entry()` writes JSON before any state transition. The method raises on write failure (not catches and continues) — this enforces the audit-before-transition invariant. Correct.
- `close()` calls `write_audit_entry()` before `self._registry.transition()`. The ordering invariant is enforced in code, not just in comment. Correct.
- `check_convergence()` implements the spec's conditions and anti-convergence signals. Condition 4 ("Dan explicitly marked done") is implemented as `"done" in uow.close_reason.lower()` — a substring match that would also fire for a close_reason of "not done" or "marked done by mistake." This is a minor implementation smell.

**select_workflow():** The selection table matches the issue spec. First match wins. Defaults to `investigation` for unclear cases. Correct.

**fast_thorough_selector.py:** `select_path()` returns `"fast"` or `"thorough"` (naked strings). The golden pattern "StrEnum constants in all enum-backed routing logic" (learnings.md 2026-04-24) applies here: `select_path()` returns one of two fixed string choices — this is exactly the case the golden pattern names: "PathSelection/type discriminators get StrEnum." Rule 3 of that pattern states: "Any function that returns one of N fixed string choices (path selection, strategy names, mode strings) should define a StrEnum." This PR does not define a StrEnum for the return value.

Behavioral effect: the StrEnum pattern matters most for two reasons — (a) caller comparisons like `if path == 'fast'` versus `if path == 'thorough'` work against an unchecked string; (b) renaming the path values later requires a repo-wide grep rather than an enum rename. The PR itself is internally consistent (the tests assert against the string literals "fast" and "thorough"), so this does not break anything now. But it introduces exactly the pattern the golden rule exists to prevent. The instruction in golden-patterns.md is explicit: this is a blocking consideration when merging routing discriminators. However, the learnings.md entry categorizes this as a documented rule, not a fire-and-stop-everything blocker in isolation — the surrounding context matters. Given that `select_path()` is not yet wired to any production call site (it is a new module with no imports in production code), the severity is reduced: there are no callers to mismatch against. I note this as a gap with the recommendation to add a `PathSelection(StrEnum)` before any production caller is written.

**Wiring gap:** `StewardHeartbeat` and `fast_thorough_selector.select_path()` are not imported anywhere in production code outside `steward.py` itself. This is the same pattern named in learnings.md PR #714: "A new module with N additions and 0 deletions, with no import in any existing file, is a library with no wiring." `steward-heartbeat.py` still imports `run_steward_cycle` directly, not `StewardHeartbeat`. The PR does not wire the new class into the heartbeat scheduler. This is not a defect in the code itself — the PR description correctly scopes this as the class implementation; future PRs will wire it. But the production call site issue is worth naming explicitly so it is tracked.

**sweep-context.md Step 1d:** This is a distinct feature — a pipeline ripeness classifier added to the sweep instruction. It is a substantial addition (102 lines) and does not appear in the PR title or summary. The PR title is "Add StewardHeartbeat class with OODA vision context integration." Step 1d is not mentioned. This is the feature-bundling pattern (learnings.md 2026-05-14: "feature-bundling across unrelated workstreams in a single PR"). The sweep instruction is a different workstream from the StewardHeartbeat implementation. However, the Step 1d addition is: (a) purely instructional, (b) well-contained, (c) not behavioral code. It does not introduce a production import risk or a migration gap. The severity is lower than the #1148 example (which mixed code from multiple UoWs). I note it as a documentation gap in the PR description without blocking.

**Test quality:**

- `test_fast_thorough_selector.py`: 10 tests covering Fast Path, Thorough Path, empty/whitespace anchor, prior decision fallback, preference order. Assertions are against string literals "fast" and "thorough" — same StrEnum gap applies to tests, but since no production constant exists, there is no divergence risk yet.
- `test_steward.py`: 15+ tests. The fixtures are clean — `_make_uow()` and `_make_diagnosis()` helpers with sensible defaults. Tests patch `_get_vision_context_via_mcp`, `_diagnose_uow`, `_fetch_audit_entries` correctly at the module level (not at the import site). Audit-before-transition invariant is tested via `mock_transition.side_effect` that checks file existence — this is a correct structural test, not just an assertion about call order. The vision fields propagation test correctly asserts on `diagnosis.vision_fields_cited` rather than just on whether the function was called.

One test smell: `test_prescribe_writes_workflow_artifact` asserts `result.workflow_selected in (WORKFLOW_INVESTIGATION, WORKFLOW_EXECUTION_PASS, WORKFLOW_SYNTHESIS_PASS, "single_assessment", ...)` — this is an enumeration of all possible values, equivalent to asserting the result is non-null. It does not verify which workflow was selected for the given inputs. The diagnosis fixture uses defaults (`cycle=0, reentry_posture=FIRST_EXECUTION, output_valid=False`) which should deterministically produce `WORKFLOW_INVESTIGATION`. The test should assert that specific value. This is a minor test precision issue — the test proves the function runs without error but does not verify the selection logic for the fixture's inputs.

**Pass:** Audit-before-transition invariant correctly enforced in code. Vision context integration (fetch, log unavailability, write to audit record) correctly implemented. Delegation to `run_steward_cycle()` without logic duplication. Tests cover the five required behaviors named in the PR description. Encoded Orientation check passes on all new behavioral defaults.

5. `test_prescribe_writes_workflow_artifact` assertion is too permissive — enumerates all possible return values rather than asserting the specific expected selection for the test fixture's inputs.
