## PR #1303 — feat(germinator): co-occurrence scoring for ambiguous philosophical terms

### Stage 1: Vision alignment

**Prior used:** No relevant named failure patterns from learnings.md applied to this specific change. The PR #845 precedent (removing "clearing" due to false positives) is the structural predecessor — this PR generalizes that fix into a proper scoring architecture.

**The adversarial prior:** This implementation is solving the wrong problem, or solving the right problem in a direction that forecloses better paths.

**Checking the prior:**

- **Is this solving the right problem?** The UoW artifact (uow_20260525_37c1af.md) states: "the fix is co-occurrence scoring, not term removal." The problem class is real — boolean frozenset intersection gates are architecturally fragile when terms are semantically overloaded across registers (philosophical vs. technical). PR #845 already demonstrated this fragility by fixing "clearing." The co-occurrence approach generalizes the fix rather than patching case-by-case.

- **What would have to be true for this work to be wasted?** Either (a) the `register` false positive never actually manifests in production (because `register` was never in `_PHILOSOPHICAL_TERMS`), or (b) a better approach exists that this forecloses. On (a): `register` was NOT in `_PHILOSOPHICAL_TERMS` on main — this is a proactive fix, not a reactive one. The code was not currently broken for `register`, but the UoW explicitly prescribed this architecture anyway. On (b): no better path is foreclosed — the scoring function is composable, the threshold is a named constant, and the co-term sets are module-level frozensets that are trivially extensible.

- **Cheaper test not run?** The simpler intervention would be to just never add `register` to `_PHILOSOPHICAL_TERMS`. The PR goes further by implementing a proper architecture for the whole class of semantically overloaded terms. This is proportional — the WOS system processes many UoWs and a misrouted UoW has real metabolic cost (constraint-4). The architectural investment is appropriate.

- **What does this foreclose?** Nothing structurally significant. The scoring function is additive — new terms can always be classified as unambiguous (contribute 0.3) or ambiguous (contribute via co-occurrence). The `_PHILOSOPHICAL_TERM_WEIGHT = 0.3` constant is tunable if the threshold needs adjustment.

- **Opportunity cost:** Low. This is a focused, two-file change with no cross-cutting concerns.

**Alignment verdict: Confirmed.** This is a sound architectural improvement solving the right problem class.

### Stage 2: Quality review

**Mode: VERIFICATION** — external adjudicators: test suite (30/30 pass), manual score verification for stated test cases.

**What the PR does:**
- Replaces `_is_philosophical()` (boolean) with `_philosophical_score()` (float, [0.0, 1.0])
- Adds `_AMBIGUOUS_TERMS`, `_PHILOSOPHICAL_CO_TERMS`, `_TECHNICAL_CO_TERMS`, `GATE3_THRESHOLD`, `_PHILOSOPHICAL_TERM_WEIGHT`, `_AMBIGUOUS_TERM_WEIGHT`, `_CO_OCCURRENCE_WINDOW` as module-level named constants
- Gate 3 fires when `_philosophical_score(title, body) >= GATE3_THRESHOLD` (0.3)
- Unambiguous terms in `_PHILOSOPHICAL_TERMS` each contribute 0.3 → single term still fires (backwards-compatible)
- Ambiguous `register` contributes `0.15 * phil_hits` only when `phil_hits > tech_hits` in a 40-word context window

**Backward compatibility:** A single unambiguous term (e.g. `attunement`) still fires Gate 3 (contributes 0.3, threshold = 0.3). This is stated explicitly in the PR body and verified.

**Scoring calibration concern (minor, non-blocking):** The `_AMBIGUOUS_TERM_WEIGHT * phil_hits` formulation means a single `register` with 4 philosophical co-terms contributes 0.60 to the score. Combined with one unambiguous term (0.3), that's 0.90. The `min(score, 1.0)` cap prevents overflow. The calibration seems intentionally generous — the goal is to catch philosophical `register` usage reliably, not to calibrate a precise confidence interval. The PR body acknowledges this with its worked examples. No concern.

**Constants placement:** All scoring constants are at module scope with clear names and inline comments. No magic numbers. Importable by tests. Consistent with the named-display-cap golden pattern (learnings.md, PR #938).

**Test quality:** Three new tests in `TestGate3CoOccurrenceScoring` cover:
1. Technical context (false positive guard)
2. Philosophical context (true positive confirmation)
3. Neutral context (no co-terms, no fire)

Tests are behavioral (spec-derived from the PR description), not implementation-coupled. They import from the production module and exercise through the public `classify_register()` API. No test-local constant re-declarations.
