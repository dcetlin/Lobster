## Stage 1 — Vision Alignment

**Reviewed before seeing implementation.**

**Implicit theory of change in vision.yaml:** The system builds structural decision capture so routing decisions are traceable to logged decisions, not inferred from conversational texture (constraint-2). The `⚖️ decided` signal closes the loop on the existing `💬 decide` forward-looking signal — capturing that a decision was reached and persisting it structurally.

**What would have to be true for this work to be the right path:**
- Decisions made during agent conversations are currently lost in conversational texture.
- The hook layer is the right interception point (fire-and-forget, does not block send_reply).
- The decisions table and ledger become queryable inputs for routing decisions.

All three conditions hold. The issue (#463, authored by Dan) established the design intent explicitly: "no backward-looking signal currently exists to record that a decision was reached." This is the prior logged decision for constraint-3 purposes — the issue is the authorization record.

**Cheaper test of the assumption:** The `decision:` footer block already routes to the decisions table via `decision-router.py`. The question is whether `decided` in a `side-effects:` block is a genuinely distinct semantic case. It is: `decision:` blocks are explicit declarations surfaced to the user via the footer; `decided` in `side-effects:` is a signal that the system recognized a previously open question is now resolved, captured automatically. Different triggers, different use cases.

**What this forecloses:** Nothing material. Hook writes are fire-and-forget; failures are swallowed.

**Opportunity cost:** Minimal — the change is targeted (247 lines, 0 deletions, one new function + tests).

**Alignment verdict: Confirmed** — directly traceable to constraint-2 (decisions traceable to logged records), principle-3 (structural capture rather than LLM judgment), and issue #463 as the prior logged decision.

**Learnings.md citation check:** The schema duplication pattern (same `CREATE TABLE IF NOT EXISTS decisions` in both `decision-router.py` and `route_decided()`) is a mild instance of the PR #839 "locally-declared mirror of a production constant" learning — the schema is duplicated rather than shared. However, `IF NOT EXISTS` makes it safe, both hooks write to the same DB, and the schema is trivially inspectable. Not blocking.

## Stage 2 — Quality Review

### Does it do what it claims to do?

Yes. All 8 unit tests pass (`uv run python -m pytest tests/unit/test_hooks/test_signal_footer_decided.py -v`). Tests cover: no-footer passthrough, side-effects without decided passthrough, emoji routing to DB, no-emoji routing to DB, ledger append, bare-decided fallback description, DB failure resilience, non-send_reply tool passthrough.

### What would break without the key decisions made here?

- **try/except wrapping both DB write and file write:** Without this, any sqlite3 error or filesystem error would propagate and block the `send_reply`. The wrapping is the correct pattern given this is a hook.
- **SIDE_EFFECTS_CONTENT_RE with DOTALL:** Without DOTALL, multi-line side-effects blocks would not match. Correctly applied.
- **`CREATE UNIQUE INDEX IF NOT EXISTS idx_decisions_dedup ON decisions(date, summary)`:** The dedup index prevents duplicate entries if the same send_reply fires twice (e.g., retry). Correctly placed.

### Failure modes

1. **`decided-upon` false positive:** The regex `^(?:⚖️\s*)?decided\b` fires on `decided-upon: ...` because `-` is a non-word character, triggering a word boundary after `d`. This would produce `-upon: something` as the description. Extremely unlikely in practice (no signal uses `decided-upon`), not blocking.

2. **Schema duplication between `decision-router.py` and `route_decided()`:** Both define the same `decisions` table DDL. Safe due to `IF NOT EXISTS`, but creates a synchronization risk if the schema evolves — a future column addition must update both files. Minor tech debt; not blocking given the golden pattern (StrEnum ×2) is not violated here in any material way.

3. **Raw string literals `"decision"` and `"decided-signal"` for source/category columns:** Per the golden-patterns StrEnum rule, these should use StrEnum constants. However, `decision-router.py` already uses `"hook"` as a raw string for source, so this is consistent with existing practice. Not blocking.

### Patterns introduced

- **Hook-layer signal routing as fire-and-forget:** The `route_decided()` pattern (read signal from body, write to DB, swallow failures) is structurally identical to how `decision-router.py` handles `decision:` blocks. This is good — it reinforces the existing pattern rather than introducing a new one.
- **Env-var override for DB/file paths:** `DECIDED_DB_PATH` / `DECIDED_LEDGER_PATH` env vars enable test isolation cleanly. This is the correct pattern for hook testability.

### What this makes easier / harder

- **Easier:** Decision capture now happens automatically when Lobster emits `⚖️ decided` in a `side-effects:` block. No manual ledger entry required.
- **Harder:** Nothing. The hook is additive and isolated.

### OODA constraint-3 check

This PR changes a behavioral default (hook now silently writes decisions to DB when `decided` signal appears). This is an Encoded Orientation decision. Check: (a) prior logged decision exists — **yes**, issue #463 authored by Dan establishing the design and implementation order; (b) vision.yaml anchor — **yes**, constraint-2 ("traceable to a logged open decision"). Both conditions met. Not a gate violation.

- Tests use env var overrides for path isolation (correct pattern per the PR #839 learning).
- 8 tests cover the expected failure modes including DB failure resilience (exit 0).
- No stale assertions; no behavior-prohibiting tests.
