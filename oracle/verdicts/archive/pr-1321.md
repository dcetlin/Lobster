A Registry that raises ValueError on valid DB rows containing legacy `completed` values directly contradicts this substrate goal.

**Theory of change:** `completed` is a documented legacy status value present in production DB rows. The fix makes the enum match the actual DB state, restoring correct deserialization. This is not a speculative fix — the crash reproduces on any DB with `completed` rows.

**What would have to be true for this to be the right path:** The `completed` status actually exists in live DB rows. It does — PR body documents this as a known legacy value predating enum enforcement, matching the pattern for `cancelled` (#903) and `closed` (#1279).

**Cheaper test:** A try/except workaround in `_row_to_uow()` would suppress the ValueError but would mask future enum-DB divergence. The enum fix is structurally correct — it closes the gap rather than papering over it.

**What this forecloses:** Nothing. Pure StrEnum extension is backward-compatible by definition. No existing enum member is modified or removed.

**Opportunity cost:** Near-zero. Correctness fix for a crashing code path in the Registry substrate. Not addressing it leaves the Registry broken for any UoW with `completed` status.

**Alignment verdict: Confirmed.** This is a narrowly-scoped correctness fix directly serving the active project's phase intent. Vision reference: `active_project.phase_intent` (Registry substrate must be operationally correct for intent-anchored routing to function).
