## Stage 1 — Vision alignment (written before seeing implementation)

**Theory of change:** vision.yaml active_project phase_intent is "build the substrate that lets every agent make intent-anchored decisions." The htmlgen editor (introduced in PR #1349) is a parallel capability track that addresses a concrete operational bottleneck: LLM agents must know section IDs in advance to target edits, which requires an additional round-trip or produces hallucinated IDs. This PR adds read-only content-based discovery so agents can locate sections by what they contain rather than by IDs they must already know. The EditTrace layer adds observability over the edit pipeline.

**What would have to be true for this work to be the right path:** Agents using the htmlgen editor must be blocked or degraded by not knowing section IDs ahead of time. The PR description motivates this concretely: the alternative is either (a) always call `list_section_ids` first and correlate by title, or (b) receive the full HTML and reason about structure. `find_sections_by_content` removes this friction by making section discovery a first-class operation rather than a workaround.

**Foreclosures:** None. The function is read-only and additive. The EditTrace adds observability without changing edit semantics. The return type change is additive (tuple rather than string), and the only existing callers discard the return value.

**Encoded Orientation check:** No new behavioral defaults, no agent decision rules, no OODA routing changes. This is a library capability extension with no dispatcher or bootup file changes. constraint-3 does not fire.

**Alignment verdict: Confirmed.** The problem is real, the solution is bounded, and the design follows the seam-first golden pattern (golden-patterns.md 2026-03-30): edit discovery and edit execution remain cleanly separated.

**Adversarial prior check (was this solving the wrong problem?):** The adversarial reading would be: "LLM agents should use structured document metadata rather than content search to find sections." This is a reasonable alternative design. However, the existing `list_section_ids` already serves that need; `find_sections_by_content` serves the case where the agent has content but not IDs. The two functions are complementary, not redundant. The adversarial reading does not hold.

### Advisory finding 1: TRACE_LOG_PATH is a dead mirror-constant in the test file

The test file adds a module-level constant:
```python
# Spec-mandated constant: the path where edit traces are appended
TRACE_LOG_PATH = Path.home() / "lobster-workspace" / "data" / "html-edit-traces.jsonl"
```

This duplicates the production `TRACE_LOG_PATH` from `src/htmlgen/editor.py`. The production module exports this constant and it is the correct import target. However, the test file does NOT import it — it re-declares it locally with the same value.

More critically: the test-file `TRACE_LOG_PATH` is never used in any test assertion. All `TestJsonlTraceLog` tests use `log_path = tmp_path / "traces.jsonl"` (a monkeypatched tmp path) in their assertions. The constant is dead code.

This matches two learnings.md patterns simultaneously:
- PR #848: "Dead code immediately before an unconditional override" — the constant exists but all consumers immediately override it via monkeypatch
- PR #970: "Dead test constant with semantic mismatch" — a dead constant whose presence implies future test authors can assert against `TRACE_LOG_PATH` in tests, when doing so would assert against the production path (not the monkeypatched tmp path), silently breaking the test intent

**Advisory — not a blocker.** The existing tests are correct and complete. The constant is dead and poses only a future-author confusion risk. Recommended follow-on: either import `TRACE_LOG_PATH` from the production module (replacing the local declaration) or remove the local declaration entirely. The monkeypatch pattern used in `TestJsonlTraceLog` is correct and does not reference the local constant.

### Advisory finding 2: sections_accessed deduplication is inconsistent across op types

In `_apply_instruction`, the three op handlers treat `sections_accessed` differently:
- `replace_section_content`: appends `sid` unconditionally (no dedup)
- `remove_section`: appends `sid` unconditionally (no dedup)
- `add_section`: checks `if sid not in sections_accessed` before appending (dedup)

A batch of two `replace_section_content` ops on the same section produces `sections_accessed = ["s1", "s1"]`. The `sections_accessed` field's semantic intent is "which sections were accessed" — a set, not a multiset. Duplicate IDs in the trace misrepresent the number of distinct sections touched and could mislead any consumer that computes `len(trace.sections_accessed)` as a distinct-section count.

The test `test_batch_trace_sections_accessed_contains_all_targeted_sections` uses two different sections (s1, s2) and only asserts membership — it does not catch the duplicate case.

**Advisory — not a blocker.** The core observability purpose (which sections were involved) is served correctly for normal usage where sections are targeted once. The inconsistency only surfaces with repeated ops on the same section. Recommended follow-on: apply the same dedup logic to `replace_section_content` and `remove_section`, or document the semantic as "IDs may repeat for repeated ops."

### Swallow-append-errors policy

`_append_trace` uses a bare `except Exception: pass` with a `# noqa: BLE001` suppression. The intent is correct: trace logging must never mask edit results. The docstring explicitly states this. The `# noqa: BLE001` is the correct form for ruff. No issue.

### _apply_instruction as mutable accumulator

The engineer flagged: `_apply_instruction` now takes `sections_accessed` as a mutable accumulator parameter — only stateful element in an otherwise pure function. This is a noted design tradeoff. The function is internal, the parameter is not exposed publicly, and the accumulator pattern is idiomatic Python for this kind of in-loop collection. The alternative (returning a list of accessed IDs from each call and accumulating externally) would require a return type change and more complex caller logic. The current design is acceptable. No issue.
