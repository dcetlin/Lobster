## Stage 1: Vision Alignment

**Prior entering review:** This implementation is solving the wrong problem, or solving the right problem in a direction that forecloses better paths.

**What would have to be true for this work to be the right path:**

1. The blocking `subprocess.run(claude -p, timeout=600)` call inside the steward heartbeat is a real operational bottleneck — not just a latency concern but a structural one that prevents WOS execution from resuming while the executor pause is active.
2. The async inbox message pattern (write message → return immediately → dispatcher routes to subagent) is the appropriate architectural vehicle for this specific indirection, and it doesn't create a worse problem (e.g., message queue floods, orphan accumulation).
3. Path 1 (async prescription) is structurally independent enough from Path 2 (executor routing) and Path 3 (verdict normalization) that shipping it first doesn't foreclose the later paths.

**Is there a cheaper test of the underlying assumption?** The migration plan document (HTML) confirms the 600-second blocking call was already architecturally diagnosed. The assumption is well-founded: `_llm_prescribe` is a `subprocess.run` with `timeout=600s` that blocks the 3-minute cron heartbeat. The async path is the correct structural fix.

**What does this work foreclose?** The `if llm_prescriber is _llm_prescribe` identity check as the async gate is a specific design choice. It means: any callable that is the production `_llm_prescribe` function (identity, not just signature match) triggers the async path; any other callable (including the exact same function imported again via a different path) would fall through to the sync path. This is an intentional, clean discriminator — it doesn't foreclose future changes to use a different gate.

**Opportunity cost vs. vision priorities:** `vision.yaml current_focus.current_constraint` explicitly states "WOS execution remains paused while Stage 1/2 substrate work stabilizes." This PR is Stage 1/2 substrate work. `principle-1` ("structural prevention over reactive correction") is directly served — the 600s block is a structural gap in the heartbeat that this PR addresses at the correct layer. `principle-4` ("wire what exists before building more") is also served — this wires the existing inbox/dispatcher pattern to a new use rather than introducing a new coordination mechanism.

**Vision anchor check (constraint-3 — Encoded Orientation):** The async prescription path is a durable behavioral default change — after this PR, every production steward heartbeat uses the async path by default. This is an Encoded Orientation decision.

## Stage 2: Quality Review

### What the PR does

1. Adds `UoWStatus.PRESCRIBING = "prescribing"` to the registry enum with `is_in_flight()` coverage.
2. Adds `record_startup_sweep_prescribing()` to the registry — an atomic UPDATE+audit_log write for TTL recovery.
3. Adds `_write_prescription_request()` to steward.py — writes a `wos_prescribe` JSON file to `_INBOX_DIR_PATH`.
4. Adds an async gate in `_process_uow`: `if llm_prescriber is _llm_prescribe and not dry_run` — triggers the async path, writes the inbox message, transitions to `prescribing`, returns `PrescribingQueued`.
5. Adds `handle_wos_prescribe()` to dispatcher_handlers.py — pure routing function that returns `action="spawn_subagent"` with a subagent prompt.
6. Adds `wos-prescription-agent.py` — standalone script that reads the payload, runs `_llm_prescribe`, writes the WorkflowArtifact, transitions to `ready-for-executor`.
7. Adds Population 5 to `startup_sweep.py` — orphan recovery for `prescribing` UoWs stuck beyond TTL.
8. 29 new tests in `test_wos_prescribe.py` + 3 modified tests in `test_steward.py`.

### What would break without the key decisions

- The identity check `llm_prescriber is _llm_prescribe` (not `llm_prescriber is not None`) is the correct discriminator: it preserves the existing `llm_prescriber=None` sync path AND the `llm_prescriber=<stub>` custom-function path without requiring callers to change. The sync path tests pass `llm_prescriber=None` or a stub; the async path uses the production default. This is clean.
- The TTL = `LOBSTER_LLM_PRESCRIPTION_TIMEOUT_SECS` default (600) + 60s grace = 660s is well-reasoned. The comment names the intent. Correctly implemented as a named constant `_PRESCRIBING_ORPHAN_THRESHOLD_SECONDS` at module scope.
- The `_STATUS_PRESCRIBING = UoWStatus.PRESCRIBING` module-scope alias in steward.py follows the existing pattern for other status constants in the same file (not raw strings).

### Structural correctness checks

**Registry.record_startup_sweep_prescribing:** Uses `BEGIN IMMEDIATE`, conditional audit_log insert (only if rows_affected == 1), commit/rollback. This matches the optimistic-lock + audit pattern used by the sibling methods. Correct.

**_write_prescription_request:** Uses `_INBOX_DIR_PATH` (module-scope constant, same used by existing inbox write paths in steward.py). Not using `LOBSTER_MESSAGES` env var — but this is consistent with the existing `_INBOX_DIR_PATH` definition at line 4360 of steward.py which also hardcodes `expanduser("~/messages/inbox")`. Not a regression; consistent with the established pattern in this module.

**handle_wos_prescribe:** Returns `action="spawn_subagent"` with properly formed YAML frontmatter (`task_id`, `chat_id: 0`, `source: system`), `Minimum viable output`, and `Boundary` constraints. Satisfies dispatch template gate. Confirmed: the subagent prompt uses `chat_id: 0` (silent-drop sentinel pattern — internal result, not user-facing). Correct.

**startup_sweep Population 5:** Uses the same `_is_bootup_candidate_gated` check as the other four populations. Handles missing `updated_at` and unparseable timestamps with explicit skips (not silent failures). Correctly aggregates `prescribing_swept` into the total for the summary log. The `StartupSweepResult` dataclass field `prescribing_swept: int = 0` has a default — backward compatible.

**CycleResult extension:** `prescribing_queued: int = 0` added with default. `as_dict()` updated. The `match` statement in `run_steward_cycle` adds a `PrescribingQueued()` case before `case _:`. Correct — the catch-all doesn't count prescription as skipped.

**Diagnosing → prescribing transition race:** `rows = registry.transition(uow_id, _STATUS_PRESCRIBING, _STATUS_DIAGNOSING)` — if `rows == 0`, returns `RaceSkipped`. Correct.

### Finding 1 (advisory): Dead code block in wos-prescription-agent.py Step 4

In `wos-prescription-agent.py`, the Step 4 block:

```python
try:
    from orchestration.steward import _diagnose_uow, _fetch_audit_entries
    from orchestration.steward import generate_v2_prescription, IssueInfo
    audit_entries = _fetch_audit_entries(registry, uow_id)
    # Note: generate_v2_prescription requires a Diagnosis object; ...
    # Full v2 is a best-effort bonus — not required for ready-for-executor.
except Exception as v2_exc:
    log.debug(...)
```

The `try` block imports four symbols, calls `_fetch_audit_entries` (a real DB read with side effects), assigns the result to `audit_entries`, and then does nothing with any of it. The except block silently absorbs any exception. The code after the block never uses any of these bindings.

This is the dead-code-immediately-before-override pattern (learnings.md PR #848): `audit_entries` is computed but never read; `generate_v2_prescription` and `IssueInfo` are imported but never called. The comment explains the intent ("best-effort bonus — not required for ready-for-executor"), but the implementation does not generate the v2 prescription — it only fetches data that would be needed and then discards it.

**Impact:** Low. The DB read is harmless. The v2 prescription is explicitly marked optional. No wrong behavior results.

**Resolution:** Remove the imports and `_fetch_audit_entries` call, or add a comment to the try block that reads: `# TODO: v2 prescription generation placeholder — not yet implemented`. The current form misleads future readers into thinking v2 prescription is being generated when it is not.

This is advisory. It does not block APPROVED.

### Note: Assertion softening in test_steward.py

Three tests were updated from `assert uow["status"] == "ready-for-executor"` to `assert uow["status"] in ("ready-for-executor", "prescribing")`. These tests do not pass `llm_prescriber=None`, so after this PR, the async path fires, and the UoW lands in `prescribing` rather than `ready-for-executor`.

The learnings.md PR #839 pattern (assertion softening to "not-legacy-value") caused elevated scrutiny here. The assessment: this is NOT the PR #839 anti-pattern. Both `"ready-for-executor"` (sync path) and `"prescribing"` (async path) are correct and intended outcomes. Neither is a fallback or error value. The OR is structurally unavoidable because the test can't control which path fires without `llm_prescriber=None`.

The four tests that DO need to assert specific end states (`test_sync_path_preserved_when_injecting_none`, `test_sync_path_preserved_when_injecting_stub`, `test_normal_uow_still_prescribed_alongside_orphan`, etc.) correctly pass `llm_prescriber=None` and assert `"ready-for-executor"` exactly. This demonstrates the right technique is known and applied where applicable.

Advisory: the three tests with OR assertions could add a comment explaining why OR is required ("async path fires with default prescriber → prescribing; only ready-for-executor with explicit stub").
