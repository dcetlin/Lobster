## Stage 1: Vision Alignment (written before reading implementation)

### Prior: this implementation is solving the wrong problem, or solving the right problem in a direction that forecloses better paths.

**What would have to be true for this work to be the right path?**

The change addresses a specific named bug (#1253): the heartbeat sidecar was masking dead agents by refreshing `heartbeat_at` unconditionally for all active/executing UoWs, preventing orphan detection from firing. This is squarely an executor stability concern — and `vision.yaml current_focus.current_constraint` explicitly names "Executor stability must be confirmed before re-enabling" as the blocking operational constraint. The work is not speculative infra-building; it is fixing an identified defect that is gating a stated current_focus goal.

**What would have to be false for this to be wasted effort?**

The approach could be wrong if: (a) the sidecar masking is not actually the dominant cause of the 22+ hour cycling, (b) the output file mtime is an unreliable liveness signal (e.g., Claude Code writes to stdout/output file continuously even when actually hung at a tool call), or (c) there is a simpler structural fix at a different layer (e.g., fix `claimed_until` TTL logic directly). These are legitimate risks but they are addressed by the fail-open design choice — the worst case is false negatives (agents not detected as dead when they are), not false positives (live agents killed). The fail-open posture preserves the current behavior for ambiguous cases and only changes behavior when the file is definitively stale.

**What does this foreclose?**

The mtime-based liveness check introduces a coupling between the sidecar and the sessions DB / filesystem. If the output file convention changes (e.g., agents no longer write to a single output file, or output_file column goes away), the liveness gate silently reverts to fail-open. This is the correct fallback behavior but it creates a silent capability loss with no alerting. The module docstring documents the fail-open contract clearly, which partially mitigates this.

**Opportunity cost:** The WOS executor is stopped (`execution_enabled=false`). Fixing the sidecar masking bug is directly on the path to safely re-enabling it. This is the right thing to be working on per `current_focus.current_constraint`.

**Alignment verdict: Confirmed.** The work directly serves `vision.yaml current_focus.current_constraint` ("Executor stability must be confirmed before re-enabling"). The fix is a correctness improvement to a known P1 bug in the executor stability path, using a conservative fail-open design that doesn't introduce new risk classes.

## Stage 2: Quality Review

### Does it do what it claims to do?

Yes. The core mechanic is:
1. For each candidate UoW, call `_is_agent_output_stale(uow_id, now, stale_seconds, sessions_db_path)`.
2. If stale, increment `dead_agent_skipped` and `continue` — no heartbeat write.
3. If not stale (or unknown), proceed to `registry.write_heartbeat()` as before.

This correctly stops the sidecar from masking dead agents: once the agent output file stops being written (because the agent is dead), the mtime grows stale and the sidecar stops refreshing `heartbeat_at`, allowing the startup sweep's staleness check to fire normally.

### Fail-open paths — are they correct?

The fail-open contract: `_is_agent_output_stale` returns `False` (do not skip) when:
- No session row found → correct. Agent may not have registered yet, or schema predates output_file column.
- `output_file` column is NULL → correct. Pre-migration agents.
- Sessions DB is unreadable → correct. Avoids blocking during DB maintenance.
- File doesn't exist on disk → correct. Agent may be starting up and hasn't written output yet.
- OSError on stat → correct. Avoids blocking on filesystem issues.

Returns `True` (skip heartbeat) only when: session found, output_file populated, file exists on disk, AND mtime > threshold. This is a conservative gate. All tests validate these paths.

### What failure modes exist?

**1. Test uses the default stale threshold (600s) for the "stale" test case.** In `test_skips_heartbeat_when_output_file_is_stale`, the output file is set to 1800s old and the sidecar is called with `sessions_db_path=sessions_db` — using the default `_agent_output_stale_seconds()` which returns 600 (from env var or default). Since 1800 > 600, the test passes. However, the test does not explicitly set or assert the threshold value — it relies on the module's default. If `LOBSTER_SIDECAR_STALE_SECONDS` were set to 3600 in the test environment, the test would fail (file would appear fresh). This is a minor test-environment sensitivity: tests rely on the module's default but don't pin it. Not a blocker — the pattern of passing `sessions_db_path` explicitly is consistent with the intent; the threshold was not made injectable because the env-var override is readable at call time.

**2. The comment says `# Mirrors session_store._DEFAULT_DB_PATH`.**  The docstring on `_default_sessions_db_path()` contains: "# Default path for agent_sessions.db — mirrors session_store._DEFAULT_DB_PATH." This is the mirror-constant comment pattern flagged in learnings.md #976. The comment names `session_store._DEFAULT_DB_PATH` as the canonical source. Whether that symbol actually exists in `session_store.py` cannot be verified from the diff alone. If it doesn't exist, this is a learnings.md #976 instance (comment pointing at a non-existent symbol). However: (a) the function reads from `os.environ.get("LOBSTER_MESSAGES")` which is the correct env-var, not a hardcoded path; (b) the comment is documentation of intent, not a structural dependency; (c) if the session_store path changes, the env-var convention would still be correct. This is a low-severity documentation risk, not a structural one.

**3. New per-UoW DB connection on each heartbeat cycle.** `_get_session_output_file` opens a new `sqlite3.connect()` for each UoW on each cron tick. With many active UoWs, this is N SQLite connections per 3-minute cron cycle. The timeout is 2 seconds. The behavior is correct but slightly inefficient — a connection-per-cycle design would be cleaner. This is a performance note, not a correctness issue, and the codebase generally uses this per-call connection pattern elsewhere.

**4. Path resolution via `Path(output_file).resolve()`.** The `resolve()` call follows symlinks. If the output file path is a symlink to a deleted file, `resolve()` will return a path that doesn't exist and `real_path.exists()` returns `False`, triggering fail-open. This is the correct behavior — if the underlying file is gone, treat as not-stale (fail-open). No issue.
