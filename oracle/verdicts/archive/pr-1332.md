## Stage 1 — Vision Alignment

**Reviewed:** 2026-05-26

**Prior from learnings.md applied:** No named failure pattern directly matches this PR. Golden pattern "epoch-scale normalisation as an isolated seam function" was considered — the DB-path derivation follows a similar seam-first approach (isolates the path derivation into `_db()`).

**Vision alignment:** This work directly serves `active_project.phase_intent` — building the substrate that lets agents make intent-anchored decisions requires knowing whether the prescription system is working. Without structured metrics, the only signal is operational success/failure counts; there is no way to distinguish "prescriptions worked because UoWs were easy" from "prescriptions worked because they were well-formed." The `prescription_events` and `closure_events` tables create the observational substrate for that distinction. The work is justified by `vision.yaml sc-5` (routing decisions traceable to vision.yaml content, verifiable by comparing routing outcomes).

**Theory of change check:** The implicit theory is that structured prescription metrics → better understanding of which prescription elements correlate with UoW success → better prescription templates → higher single-cycle success rate. This theory is sound but has a gap: the reporting path (`wos_metrics_report.py`) currently reads from `registry.db` analytics functions, not from the new `wos-metrics.db` tables. The tables will accumulate data without the report surfacing it. This is not a blocking issue — it is a known phase boundary (the PR explicitly says "baseline captured").

**Cheaper test not run:** Could use logging counters before committing to a new DB. However, the method signatures were already stable and the stub had been in production since PR #1305. A new DB is the correct form for queryable, durable metrics.

**Forecloses:** Nothing significant. The separate-DB choice (WAL, no write contention with registry.db) keeps the option open to move metrics to a different store later. The lazy-init pattern means the DB is never created unless prescription events actually fire.

**Alignment verdict:** Confirmed

**Mode:** VERIFICATION — all three subsystems (PrescriptionMetricsLogger, maybe_fail_wos_uow, Phase 3 health monitors) have test coverage. The external standard is the test suite.

### PrescriptionMetricsLogger (prescription_metrics.py)

- Schema creates `prescription_events` and `closure_events` with `CREATE TABLE IF NOT EXISTS` — safe for repeated lazy init.
- WAL mode set via `PRAGMA journal_mode=WAL` in `_SCHEMA_SQL` — correct; executed before any INSERT.
- `_lock = threading.Lock()` protects `_connect()` and the write path — race-safe.
- `_initialized` flag is checked inside `_connect()`, which is always called under `self._lock`. The flag is not protected by its own lock, but since `_connect` is only ever called within the lock, this is effectively safe. If `_connect` is ever called outside the lock in future, the flag check becomes a TOCTOU. This is a fragile structure worth noting but not blocking.
- Non-fatal: both log methods catch all exceptions and warn — correct.
- `**kwargs: Any` reserved fields accepted and ignored — stable signature contract honored.
- 4 tests pass: happy path prescription, happy path closure, non-fatal on bad path, multi-row accumulation.

### maybe_fail_wos_uow (wos_completion.py)

**Prefix mismatch (code quality, not functional):** Line 1009 guards with `_WOS_UOW_EXECUTOR_PREFIX = "wos-uow_"` but line 1012 strips using `WOS_TASK_ID_PREFIX = "wos-"`. The comment reads "strips 'wos-', leaving 'uow_<id>'" — this is accurate: `"wos-uow_20260526_abc"[4:] = "uow_20260526_abc"`, which is the correct registry ID format. But the code uses two different constants for guard vs strip, creating a latent divergence risk: if `WOS_TASK_ID_PREFIX` is ever updated to include more of the prefix, the strip would become wrong while the guard remains correct. This is a real code quality finding from the learnings.md "mirror-constant" pattern category, but since behavior is coincidentally correct and all 4 tests pass, it does not warrant NEEDS_CHANGES at this stage.

- Guard condition `task_id.startswith("wos-uow_")` correctly excludes `wos-diagnose-*`, `wos-surface-*` — verified by `test_maybe_fail_wos_uow_skips_non_executor_prefix`.
- Status check `uow.status != UoWStatus.EXECUTING` prevents re-transition of already-failed UoWs — verified by `test_maybe_fail_wos_uow_skips_non_executing_status`.
- Missing DB handled silently — verified by `test_maybe_fail_wos_uow_skips_missing_db`.
- Core transition test passes: executing → failed.

### Phase 3 health monitors (wos-health-check.py)

- `check_dark_pipeline`: queries `MAX(ts)` from `audit_log`, compares against threshold. Returns None if DB absent (correct for optional monitoring). Handles unparseable timestamps gracefully.
- `check_ready_queue_drain`: three SQL queries — current queue depth, drain events, new-ready events. Returns alert only when growth AND no drain. Edge case: if `audit_log` does not have a `from_status` column on older DBs, this would raise. However, `audit_log` schema in registry.py includes `from_status` (confirmed by existing usage in the codebase).
- `check_issue_rate_trend`: uses `gh issue list` with `--limit 500`. This is a pagination boundary — if a repo has >500 issues opened or closed in 7 days, the count will be capped at 500. This is a reasonable practical limit given the repo's actual velocity (typically <50/week), but the limit is not documented. Not blocking.
- Bundled with PrescriptionMetricsLogger changes: the PR title names only the metrics logger, but the diff includes Phase 3 monitors and maybe_fail_wos_uow. These are correctly implemented and separately tested. The bundling is a scope management concern, not a quality defect.
