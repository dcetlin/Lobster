## Stage 1 — Vision Alignment

Prior entering review: this implementation is solving the wrong problem, or solving the right problem in a direction that forecloses better paths.

The PR's implicit theory of change: adding a documentation requirement in the output template will enforce ping protocol compliance. What would have to be true for this to be the right path? The assumption is that pings are being omitted (or at least going unrecorded) because there is no required audit field in the output format — and that adding a required field will cause future sweep agents to comply.

Issue #1335 establishes the problem: recent sweep files (Nights 2–7) show no evidence of either ping being documented. This is consistent with two scenarios: (a) pings were sent but not documented, or (b) pings were not sent. The PR does not distinguish between these. If the root cause is (a), the fix is correct and sufficient. If the root cause is (b), the fix adds a compliance record field but does not address why the pings were not sent — however, the required field will at least surface non-compliance by requiring explicit `ping_1_sent: false` with a reason.

Cheaper test of the assumption: check whether actual Telegram messages were sent by the sweep agent in the relevant time windows. This wasn't done, but the PR is a reasonable additive step regardless of which scenario applies — it adds observability without foreclosing anything. The issue description notes Ping 2 specifically (process-improvement feedback loop) could be silently omitted across multiple sweeps without detection; the audit trail addresses this directly.

**Vision alignment verdict: Confirmed.** The change is aligned with vision.yaml principle-1 (structural prevention over reactive recovery — making a behavioral gap structurally visible). It is additive, reversible, and does not increase screen dependency. The PR is pure documentation and does not require Dan's attention for any architectural decision.

One observation on the weaker side of principle-3 (determinism over judgment for conditionals): a required template field is an advisory enforcement, not a structural one. A hook or automated check would be stronger. However, sweep template fields are not mechanically checked at present, and adding this as an advisory first step is consistent with vision.yaml principle-4 (integration rate before new feature rate).

## Stage 2 — Quality Review

**Engineer flag resolved:** The field names `ping_1_sent` / `ping_2_sent` in the PR diff match the "Ping 1" / "Ping 2" protocol vocabulary in sweep-context.md's Two-Ping Protocol section. sweep-context.md does not define named fields — it defines the protocol by prose — so the snake_case `_sent` suffix is a new naming choice by this PR. The choice is appropriate: it reads as a boolean audit field, mirrors the protocol names directly, and follows the lowercase-underscore convention used elsewhere in the sweep output format (`execution_enabled`, `posture_summary`).

**Cross-file consistency gap (noted, not blocking):** The PR adds the Pings section to `sweep-instruction.template.md` (the generic template). sweep-context.md's Output Format section (lines 444–493) still ends at `Open Questions` — the Pings section does not appear in the negentropic sweep's own authoritative output format. The PR description states this is intentional: "sweep-context.md — the two-ping protocol definition is already correct and complete there." This is defensible: the template governs the canonical output format, and sweep-context.md's output format section should be understood as derived from the template. However, any sweep author using sweep-context.md's output format section as their working reference will not see the Pings requirement. This gap is a candidate for a follow-on PR to add the Pings section to sweep-context.md's Output Format section — or to add a pointer from that section to the template's Pings requirement.

**Precondition-as-harness golden pattern (2026-05-18):** The PR applies this pattern correctly. Both fields are required, explicitly stated, and the failure case (ping not sent) requires a documented reason — not a blank field. This converts the ping compliance check from a tacit obligation to a named, auditable output field.
