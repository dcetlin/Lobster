## Stage 2 — Quality review

**Mode:** VERIFICATION — this PR has an external adjudicator (test suite, migration SQL schema).

### Confirmed: fast-path ordering is correct

The three Stage 2 event fast-paths (`wos_issue_created`, `wos_uow_completed`, `wos_capacity_available`) are inserted at lines 766–806 of the `route_wos_message` diff, immediately before the spawn-gate block. The spawn-gate comment begins at line 808: "Spawn-gate (issue #920): all WOS message types MUST produce action=spawn_subagent." All three fast-paths return before reaching that block. The existing `agent_failed` fast-path (another `mark_processed` handler) is the structural precedent, and the Stage 2 fast-paths follow the same pattern exactly. No spawn-gate bypass occurs.

### Confirmed: dedup_key semantics for capacity events

`freed_uow_id` as the dedup_key for `wos_capacity_available` is correct. One UoW completion frees at most one slot. The concern would be if multiple poll cycles fired before the dispatcher consumed the event — the dedup_key on `freed_uow_id` ensures exactly one capacity signal per completed UoW regardless of how many poll cycles run. This is the semantically correct boundary: "did this specific UoW completion signal capacity availability?" not "is capacity available right now?" (which changes). The design is sound.

### Confirmed: Migration 130 installs poller as disabled

The jobs.json entry has `"enabled": False` and `"wos_core": True`. The `wos_core` flag means `wos start` will toggle it alongside other core WOS jobs. The poller starts inert until explicitly enabled — correct given the current `execution_enabled: false` constraint.

### Finding: GH_TOKEN env override pattern

`_fetch_new_wos_issues` passes `env={**os.environ, "GH_TOKEN": "", "GITHUB_TOKEN": ""}` to `subprocess.run`. This intentionally clears both token env vars so the `gh` CLI falls back to its hosts.yml token. The live system shows `GH_TOKEN` is set but invalid (`Failed to log in using token (GH_TOKEN)`) while the hosts.yml token is the working auth. This override is correct for the live deployment — it prevents the invalid env-var token from being used. However, it is the only scheduled task in the codebase that does this override; all sibling scripts (`file-size-monitor.py`, `wos-health-check.py`, `daily-metrics.py`) call `gh` without the env override and rely on gh's own auth resolution. The pattern introduces an inconsistency. It is not a NEEDS_CHANGES blocker — it is functionally correct for the live deployment — but it creates a divergent pattern that future tasks will encounter without explanation. A comment noting why the override exists is warranted. Not blocking.

### Finding: `_registry_db_path()` in wos_events.py duplicates paths.py logic

`wos_events.py` defines a local `_registry_db_path()` that recomputes `workspace / "orchestration" / "registry.db"` and reads `REGISTRY_DB_PATH` from env. The canonical implementation is in `src/orchestration/paths.py` which the `wos-event-poller.py` imports directly. The local duplication exists to keep `wos_events.py` testable via `patch.dict(os.environ, ...)` without reimporting the module. The canonical placement principle from golden-patterns.md (2026-04-25) flags this — but the pattern is used elsewhere in the codebase for the same testability reason, and the values are consistent. Not a blocker. Worth noting as a mild instance of the mirror-constant pattern at the function level.

### Finding: test file hardcodes migration filename path

`_make_event_log_schema()` in the test reads the migration by hardcoded filename. When the migration is renumbered to `0030`, this reference breaks. This is not a separate gap — it is part of the same fix required by the collision blocker.

### No false-checkbox finding

The test file is present in the diff and covers: schema creation, dedup index, emit functions (all three), mark_event_consumed, handler functions (return values and consumed calls), route_wos_message routing, and poller behavior (disabled gate, emit logic, cursor advancement). Test coverage is real and specific. No false-checkbox issue.

### What would break without key decisions here

- Without `INSERT OR IGNORE` on the dedup constraint, the poller's 30s cadence would flood the inbox with duplicate events every cycle for any issue or UoW that persists across poll windows.
- Without the fast-path placement before the spawn-gate, the three event types would be routed to the spawn-gate which enforces `action="spawn_subagent"` — a guaranteed gate violation alert on every event, producing `send_reply` noise to Dan at 30s intervals.
- Without `wos_core: true` in jobs.json, `wos start` would not toggle the poller, requiring manual intervention each time WOS execution is resumed.
