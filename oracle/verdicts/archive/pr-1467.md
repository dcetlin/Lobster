## Stage 2 — implementation review

**(a) Correct completion path / no regression to existing gating.** Verified directly in the diff and by rerunning the suite: `_maybe_auto_archive_workstreams(valid_calls)` is one more statement inside the existing `if valid_calls:` success branch, placed after `_cleanup_fire_state` and before `_exit_ok()`. It does not touch `is_dispatcher()` exemption, the `chat_id is None` rejection branch (exit 2, unchanged), or the no-write_result retry/give-up branches (`fire_count`, `MAX_HOOK_FIRES`, synthetic recovery message). No new exit codes. This is additive in the strict sense the PR claims.

**(b) Path-traversal soundness — probed beyond the shipped test suite.** I ran the following against `_archive_workstream_dir` directly (not through `main()`), using a temp `workspace_root`:
- Classic traversal (`../../etc/passwd`, `foo/bar`, empty string, `..`, `.`) — all correctly rejected by `_SAFE_SLUG_RE.fullmatch` before any path is built. Matches the shipped tests plus a few the shipped tests don't cover (bare `.`, bare `..`).
- Symlink escape: created `workstreams/evil-task` as a symlink to a directory outside `workstreams/` entirely. The slug passes the regex (it's a valid-looking name), but the "defense in depth" check (`src.resolve().parent != workstreams_root`) correctly catches it after symlink resolution and returns `False` — the outside directory was untouched. This scenario is **not** in the shipped test file; it is exactly the kind of case the code comments claim to defend against ("defense in depth in case the slug check is ever weakened") but the claim was previously untested. I recommend adding this as a test case in a fast-follow, not blocking this PR.
- **Named finding — reserved-name collision, untested:** `task_id == "archive"` passes the slug regex (alnum/dash/underscore only — "archive" qualifies) with no denylist check. I constructed the case where a real subagent's workstream dir is itself named `archive` (i.e., created before any archive/ subdirectory exists) and called `_archive_workstream_dir("archive", ...)`. `src` and `dst_root` resolve to the *same path* (`workstreams/archive`), and `shutil.move(src, dst)` — where `dst` is `src/archive`, i.e. moving a directory into its own subtree — raises internally; the function's blanket `except Exception: return False` swallows it, so the outcome is a silent, permanent no-op (this one workstream never archives) rather than corruption. I also verified the more concerning direction — a pre-existing `workstreams/archive/` containing other agents' already-archived work, hit with `task_id="archive"` — and got the same safe `False`/no-op result, not the feared "nest the entire archive tree inside itself" outcome. So: **no data-loss or corruption risk**, but the safety is incidental (an emergent property of `shutil`'s own "cannot move directory into itself" guard), not a deliberate design decision, and it is completely uncovered by the shipped test suite. A future refactor that swaps `shutil.move` for a manual copy+`rmtree` (a very plausible refactor motivation — e.g. to support cross-filesystem archives) would silently lose this protection with no test to catch the regression. **Recommend, as a fast-follow (not a merge blocker given the current behavior is safe):** add `"archive"` (and ideally the other reserved sibling name, though none currently exist) to an explicit denylist checked alongside the regex, plus a test asserting `_archive_workstream_dir("archive", ...)` is a no-op via explicit denylist rather than incidental exception-swallowing.

**(c) Could it archive a still-active workstream dir, or race with a dir mid-write?** For the ordinary single-shot Agent dispatch, no: `SubagentStop` fires only once the subagent's own generation has actually terminated, so by construction no further writes to that workstream dir can occur from that same agent afterward. The harder case is the documented `SendMessage`-to-resume pattern (continuing a previously-spawned background agent with full context) — if an agent calls `write_result(status="success")` prematurely (self-reports done while more work is actually expected) and is later resumed via `SendMessage`, any subsequent `mkdir -p`/write to the now-archived path would silently recreate a *fresh, empty* directory at the original active-namespace path rather than erroring — producing two directories for one task_id (one correctly archived-and-stale, one newly created and orphaned from the archive). This is a real, non-hypothetical scenario given `SendMessage` is a documented, currently-available tool for resuming agents, but it is a protocol-discipline problem (an agent shouldn't call `write_result(status="success")` before it is actually done) rather than a defect in this hook's logic — the hook is doing exactly what it should given a (possibly premature) success signal. Not a blocker; worth a one-line note in the `write_result` tool description or subagent bootup docs that a premature success call has this side effect now, where previously it had none.

**(d) Failure modes for missing/absent directories.** `workstreams/` absent → `src.exists()` is `False` → clean no-op. `archive/` absent → `dst_root.mkdir(parents=True, exist_ok=True)` creates it. Both traced directly in the source and match the shipped tests (`test_noop_when_workstream_dir_absent`). Cross-filesystem partial-move risk is negligible here since `archive/` is nested inside `workstreams_root` itself — same mount in every realistic deployment, so `shutil.move` resolves to an atomic `os.rename`, not a copy+delete.

**Live-firing gap.** The PR is honest that the hook was not observed firing on a real `SubagentStop` event, only via unit tests and a `main()`-via-stdin simulation. I judge this acceptable for merge, not a pre-merge blocking gate, because: (1) the `SubagentStop`/`Stop` hook registration itself is pre-existing, already-proven infrastructure — this PR adds behavior inside an already-firing path, it does not add a new trigger; (2) the failure mode of a latent bug in the new code is "a workstream dir fails to archive" (a missed cleanup), not data loss, corruption, or a blocked session — `_archive_workstream_dir` never raises out of the hook; (3) the very next real subagent completion with a workstream dir present will exercise this path within the normal operating cadence of this system. Recommend (not require) that whoever merges this explicitly watch the first organic firing rather than assuming success silently — that is a one-time observation, not a smoke-test gate.

**`workstream-canonicity-check.py` — INDEX.md parsing.** Checked the parser (`parse_index_names`) against the real `~/lobster-workspace/workstreams/INDEX.md` (38 active + 6 archived rows, standard `| name | ... |` markdown table). The parser's correctness does not depend on the README/log Y/N columns in INDEX.md (which can go stale) — `missing_readme`/`missing_log` are computed from the live filesystem, only `not_in_index` depends on table-row name matching. This is the right split: it doesn't trust INDEX.md for the two checks INDEX.md could easily be stale on. The remaining brittleness (exact first-cell string match, no bold/link-wrapped name handling) is real but matches the actual file's current format; if a future INDEX.md rewrite introduces `**name**` or `[name](...)` cells, `not_in_index` would false-positive across the board. Not blocking — the script is explicitly flag-only, not yet cron-wired, and a false-positive here produces a wrong report line, not a wrong filesystem action.
