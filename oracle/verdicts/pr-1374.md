## Stage 1 — Vision Alignment

**Adversarial prior:** this implementation is solving the wrong problem, or solving the
right problem in a direction that forecloses better paths.

**Reviewed before reading implementation.**

This PR implements Issue C of the compaction-resilience workstream: checkpoint-aware orphan
classification. The theory of change: when a WOS executor is killed mid-execution and has
written checkpoint progress, the startup sweep should surface that context in the audit
log so the Steward (Issue D) can make a better re-entry decision.

**Disconfirmation check:**

- Is there a cheaper test of the assumption? The PR is deliberately inert — `checkpoint_ref`
  doesn't exist on UoW objects until #1322 merges. This is the cheapest possible integration:
  read defensively via `getattr(uow, 'checkpoint_ref', None)`, produce zero behavior change
  until the substrate is ready.
- Does this foreclose better paths? No. The audit enrichment is additive. The classification
  string is new, the note fields are new, nothing is removed or changed for the existing paths.
- Is the opportunity cost justified? The current_focus in vision.yaml shows executor paused,
  Stage 1/2 substrate work ongoing. This PR is part of that substrate. The inertness means
  it does not disrupt live execution.

**Alignment verdict: Confirmed.** Serves `active_project.phase_intent` ("build the substrate
that lets every agent make intent-anchored decisions") and vision.yaml `principle-1`
("proactive resilience over reactive recovery"). The inertness-by-design is correct
per `principle-2` (ergonomics over shortcuts — prefer forms that keep the correction
path open over forms that produce faster output).

**Golden pattern match:** "seam-first abstraction" (2026-03-30 entry) — the PR places the
abstraction precisely at the seam where checkpoint context enters the classification
function, with a `checkpoint_ref=None` default that makes the entire new path inert
until the upstream producers exist. Effect on my analysis: I did not flag the
`_determine_reentry_posture()` gap (not handling the new classification) as a blocker,
because the PR is explicitly scoped as Issue C and the Steward wiring is Issue D.
That gap is by design.
