Signature: `transition(self, uow_id: str, to_status: str, where_status: str) -> int`

The PR's undo call (from diff):

```python
registry.transition(uow_id, _STATUS_READY_FOR_STEWARD, _STATUS_DIAGNOSING)
```

This maps to `to_status=READY_FOR_STEWARD, where_status=DIAGNOSING` — semantically: "set to ready-for-steward, only if currently diagnosing." That is the correct undo of the claim transition (which set it to diagnosing). Argument order is correct.

### Area 2: prescription_slots_available default of MAX_CONCURRENT_PRESCRIPTIONS

The parameter is:
```python
prescription_slots_available: int = MAX_CONCURRENT_PRESCRIPTIONS,
```

Intent: backward compat for tests that don't pass this argument. The default is `MAX_CONCURRENT_PRESCRIPTIONS` (5), meaning tests that don't inject this value will see a slots-available value of 5 — they can proceed to prescription without being capped. This is correct: existing tests use `llm_prescriber=None` (not `_llm_prescribe`) so they bypass the cap gate entirely anyway, or they set `prescription_slots_available` explicitly. The default does not affect existing tests.

The more subtle question: does the default create any behavior where production callers of `_process_uow` that don't pass `prescription_slots_available` would erroneously bypass the cap? No — `_process_uow` is called exclusively from `run_steward_cycle`, which always passes `prescription_slots_available=_prescription_slots`. There are no other production call sites that would miss the cap.

**PASSES.**

### Area 3: _count_prescribing_in_flight catches all exceptions and returns 0

```python
try:
    in_flight = registry.list(status=str(_STATUS_PRESCRIBING))
    return len(in_flight)
except Exception:
    return 0
```

The stated failure mode: "If the query fails, return 0 — better to allow dispatch than deadlock."

This is the correct choice for this specific context. The cap is a rate-limiting optimization, not a correctness invariant. If the registry query fails, the cap simply doesn't fire for this cycle — the prescriptions may proceed — which is the lesser harm compared to a heartbeat deadlock or exception propagation that blocks all processing. The flood will not recur from a single failed query because `startup_sweep` will reset timed-out prescriptions and the next cycle's query will succeed.

The broad `except Exception` is appropriate here because the function is a pure read-only heuristic. The caller (`run_steward_cycle`) has no recovery action it can take on query failure, so propagating the exception would just crash the cycle.

**PASSES.**

### Additional findings

**Finding A: PrescriptionDeferred is not observable as a distinct counter in StewardCycleResult**

`PrescriptionDeferred` is handled in the match statement as `case PrescriptionDeferred(): skipped += 1`. The `StewardCycleResult` dataclass has dedicated fields for `shard_blocked` (0-default field) and `prescribing_queued` (0-default field), following the pattern that operationally significant routing outcomes get their own counters. A `prescription_deferred` counter would let operators distinguish "cap hit, retry next cycle" from other skip reasons — particularly useful during the transition from paused to resumed execution.

This is an observability gap, not a correctness defect. The cap functions correctly. The `skipped` counter rising is a visible signal. A production operator watching `registry.db` can count `status='prescribing'` rows directly. Severity: minor note. Does not block approval.

**Finding B: Redundant inner dry_run guard in the cap gate**

```python
if llm_prescriber is _llm_prescribe and not dry_run:  # outer guard
    if prescription_slots_available <= 0:
        ...
        if not dry_run:  # inner guard — unreachable-as-false
            registry.transition(...)
        return PrescriptionDeferred(uow_id=uow_id)
```

The inner `if not dry_run:` is unreachable as `False` because the outer `if` requires `not dry_run`. The PR comment acknowledges this is intentional. It's dead conditional code but produces no incorrect behavior. Severity: cosmetic note. Does not block approval.

**Finding C: Test comment misnames transition parameter**

In `test_undo_diagnosing_transition_on_deferred`, the comment reads `# registry.transition(uow_id, to_status, from_status)` but the registry's parameter is named `where_status`. The assertion itself (`args[1]`, `args[2]`) is correct. Severity: cosmetic note. Does not block approval.
