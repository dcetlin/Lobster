## Stage 1 — Vision Alignment (formed before reading implementation)

**Adversarial prior:** The implementation is solving the wrong problem, or solving the right problem in a direction that forecloses better paths.

The issue is #1437: a systemd unit, `lobster-mcp.service`, has been restart-looping ~43,894 times because `MCP_HTTP_TOKEN` is missing from its environment. The engineer's proposed fix is to stop + disable the unit rather than supply the missing token.

**What would have to be true for disabling to be wrong?**

The disabling approach is the wrong fix if either of these holds:
1. Some code path lazily depends on lobster-mcp.service being in active/running state — either by polling its status, or by requiring the HTTP bridge it provides
2. The unit is actually needed and the token gap is the correct thing to fix

The adversarial prior demands I probe these before seeing the implementation.

**What theory of change does vision.yaml support?**

Vision `principle-1` ("Proactive resilience over reactive recovery") and `constraint-4` ("Minimize metabolic cost of cybernetic engagement") both cut against leaving a silent restart storm in place. A unit looping 43,894 times masks real restart signals from `lobster-claude.service` — this is an active orientation impairment. Stopping the noise is vision-aligned.

**Does the task foreclose better paths?**

The only foreclosed path is: "activate lobster-mcp.service by supplying MCP_HTTP_TOKEN and wiring it up properly." This path would require the HTTP bridge to actually serve a purpose. The PR's claim — that the live MCP server is inbox_server.py in lobster-claude.service's cgroup, not this unit — determines whether that path is foreclosed or merely dormant. This is the claim to probe in Stage 2.

**Stage 1 finding:** The disabling approach is correct if (and only if) the live MCP server is confirmed to be lobster-mcp-local, not lobster-mcp. If any code path uses lobster-mcp as its transport, disabling the unit causes a real outage. Stage 2 must independently verify the transport path before the Stage 1 question can be answered.

**Alignment verdict: Confirmed** — subject to Stage 2 verification of the transport claim.

### Migration 134 — Detailed Analysis

**Outer guard correctness:** `systemctl list-unit-files lobster-mcp.service --no-pager 2>/dev/null | grep -q "lobster-mcp.service"` — tested live, returns true on this system. For systems without the unit installed, the guard correctly skips all three steps.

**Stop guard:** `[ "$_mcp_active" != "inactive" ] && [ "$_mcp_active" != "unknown" ]` — captures state before acting. Tested: active loop is stopped only if not already inactive. The `_mcp_active` variable retains the pre-stop value, so the final "already stopped and disabled" message only fires when both conditions were already in the correct state at entry — not after the migration itself achieves them. This is correct and intentional.

**Disable guard:** `[ "$_mcp_enabled" != "disabled" ] && [ "$_mcp_enabled" != "unknown" ]` — same pattern, independently gated from stop. Each step increments `migrated` separately, so partial completion (e.g., stop succeeds, disable fails via `|| true`) still logs the work done.

**Sed pattern correctness:** 
Pattern: `s/After=network\.target lobster-mcp\.service/After=network.target/`

Tested against the exact installed file content (`/etc/systemd/system/lobster-wos-router.service`):
- Exact match: `After=network.target lobster-mcp.service` → `After=network.target` ✓
- Idempotent on already-edited file: `After=network.target` → `After=network.target` ✓ (grep guard prevents sed from running if pattern already absent)
- Does not match if ordering is reversed: `After=lobster-mcp.service network.target` → no match (not a real risk — the file has always had `network.target` first)
- Does not match with extra whitespace: `After=network.target  lobster-mcp.service` → no match (not a real-world risk — systemd unit files rarely have double spaces; the installed file confirms single space)
- Works if a future service is added after the reference: `After=network.target lobster-mcp.service lobster-foo.service` → `After=network.target lobster-foo.service` ✓

**Grep guard for sed:** `grep -q "lobster-mcp.service" "$_wos_router_unit"` — confirmed this fires on the actual installed file. The sed is not unconditional.

**Daemon-reload placement:** Correctly placed inside the sed's if block, immediately after the sed runs. Not placed before (which would be a no-op) or outside (which would reload unnecessarily on systems where the sed didn't run).

**`|| true` risk assessment:** Both `sudo systemctl stop` and `sudo systemctl daemon-reload` are guarded with `|| true`. The stop failing silently is acceptable — if stop fails (e.g., unit not currently running despite `is-active` returning a non-inactive state), the disable still runs. The daemon-reload failing silently is acceptable — the wos-router unit continues running with its in-memory configuration and will pick up the file change on next daemon-reload or boot.

**Fresh install path:** On a fresh install, `services/lobster-wos-router.service` in the repo already has `After=network.target` (no lobster-mcp.service reference, per the PR diff). `install.sh` copies this file to `/etc/systemd/system/`, so fresh installs never get the stale reference. The migration correctly skips entirely if lobster-mcp.service is not installed.

**Install.sh consistency:** `install.sh` copies `lobster-mcp.service` to `/etc/systemd/system/` but does NOT enable it (`sudo systemctl enable lobster-mcp` is listed only as a manual step in the info message). `lobster-mcp-local` is enabled; `lobster-mcp` is not. The PR does not change install.sh, which is correct — install.sh already treats lobster-mcp as a manually-enabled optional unit. The migration 134 only operates on the existing unit state.

**Migration counter semantics:** The three steps can produce migrated increments of 0, 1, 2, or 3. If all three are no-ops (already stopped, already disabled, no stale After= in wos-router), migrated stays at its pre-134 value, and "No migrations needed" fires if no other migrations ran. This is correct — if the unit is already stopped + disabled AND the wos-router file is already clean, there is nothing to do.

**The migration was NOT run end-to-end (flagged by engineer):** This is a real gap in confidence. However, the risk is bounded by `|| true` on every destructive systemctl command and the independently-gated structure. The failure modes are:
- `stop` fails: loop continues until next system action; disable still runs; NOT catastrophic
- `disable` fails: unit might restart on next boot; stop still ran; gracefully degraded
- `sed` fails: wos-router unit file unchanged; `daemon-reload` still runs with original file; NOT catastrophic

None of these failure modes break the live system. The oracle accepts the untested migration because the `|| true` guards make partial failure safe and the fix is not the kind of unrecoverable action (data deletion, schema change) where untested execution is a blocker.
