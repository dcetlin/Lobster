## Stage 2: Quality review

### Crash-loop blind spot (primary Stage 1 finding — assessed)

The concern is: in a perpetual crash-loop, `InactiveExitTimestampMonotonic` resets on each restart attempt, keeping the computed age small. The health check returns YELLOW indefinitely.

**Mitigating factors identified in the diff:**

1. **SYSTEMD_ACTIVATING_GRACE_SECONDS=120s is bounded.** The concern requires that `InactiveExitTimestampMonotonic` is reset every time systemd attempts a restart. This is correct for SubState=`auto-restart` (waiting through RestartSec), but the timestamp *is not reset* during the RestartSec countdown itself. After each failed activation attempt, systemd enters `auto-restart`, waits 30s, then tries again. The `InactiveExitTimestampMonotonic` timestamp is only updated when the unit *exits the inactive state* (i.e., when a new start attempt begins). The elapsed age is measured from the last inactive-exit, not from the first one. So during the 30s RestartSec countdown, the age can accumulate correctly if the unit transitions through activating → failed within that window.

2. **StartLimitBurst provides the structural backstop.** The PR description notes that `lobster-mcp` shows `NRestarts=25994`, confirming the hardware is healthy and the concern is real. However, systemd's default `StartLimitBurst=5` within `StartLimitIntervalSec=10s` means that after 5 rapid failures, systemd self-limits: the unit enters `failed` state with SubState=`start-limit-hit`. At that point `is_systemd_activating()` returns 1 (false) and `check_services()` returns 2 (RED). The crash-loop blind spot window is therefore bounded by systemd's own StartLimitBurst exhaustion — typically within 10 seconds of a real crash-loop. After StartLimitBurst fires, the unit is genuinely failed and the grace window cannot suppress it.

3. **The 4-minute health check interval further bounds the risk.** Even if one health check is suppressed during a YELLOW window, the next 4-minute cycle will either see a recovered service (correct YELLOW behavior) or see a failed state (if StartLimitBurst fired in the interim).

**Assessment:** The crash-loop blind spot is real but bounded. The combination of StartLimitBurst exhaustion producing a hard-failed state + the 4-minute check interval means the maximum suppression window for a genuine crash-loop is StartLimitBurst cycles (seconds) before the unit enters `failed` state. The grace window (120s) is long enough that a genuinely stuck activation loop without StartLimitBurst firing would be misclassified — but the comment in the diff correctly addresses this: "SYSTEMD_ACTIVATING_GRACE_SECONDS" is explicitly scoped to cover restarts completing in well under 60s, and the 120s grace specifically targets the StartLimitHit scenario. The advisory note in the test suite description about this scenario is absent (see Test Coverage section), but this is not a blocking correctness defect.

### Monotonic timestamp math

The elapsed-time computation:
```bash
uptime_us=$(( uptime_s * 1000000 ))
local age_us=$(( uptime_us - inactive_exit_ts ))
local age_s=$(( age_us / 1000000 ))
[[ $age_s -lt 0 ]] && age_s=0
```

`/proc/uptime` field 1 is seconds (float truncated to int via `awk '{print int($1)}'`). `InactiveExitTimestampMonotonic` is microseconds since boot. The arithmetic is correct. The truncation via `int()` introduces up to 1 second of error, which is acceptable given the 120s grace window. The negative-age guard is correct for the edge case where the monotonic clock source has minor skew.

One potential issue: `uptime_s=$(awk '{print int($1)}' /proc/uptime 2>/dev/null || echo 0)` — if `/proc/uptime` is unavailable (container environments without procfs), `uptime_s` becomes 0, making `uptime_us` = 0, and `age_us` becomes negative, which is clamped to 0. With `SYSTEMD_ACTIVATING_AGE_SECONDS=0` and the condition `$activating_age -le $SYSTEMD_ACTIVATING_GRACE_SECONDS`, the result is always YELLOW (0 <= 120). This is the safer failure mode: fail-safe to YELLOW rather than fail-safe to RED.

### Three-way return-code contract

- `check_services()` returns 0 (GREEN), 1 (YELLOW), 2 (RED)
- `main()` reads `svc_rc=$?` and branches correctly on each value
- The router/bot service handling preserves the existing contract: router `failed` sets `[[ $rc -lt 2 ]] && rc=2` (correct — avoids downgrading a 2 to 2, no-op; upgrades a 1 to 2 correctly if router fails while claude is healing)

One structural note: the case statement uses `activating|*)` as the second branch, meaning `active` is the only explicit positive case and everything else — including the normal `activating` string that `systemctl is-active` returns — falls into the same wildcard branch as `failed`, `inactive`, `unknown`, etc. This is intentional: the function does not trust the `is-active` output for the non-active case; it re-queries via `get_systemd_state()`. This is correct defensive design.

### State parsing correctness

`get_systemd_state()` uses `systemctl show -p ActiveState,SubState`, which is the reliable API (not `is-active`) for detailed state. The output parsing via `grep '^ActiveState=' | cut -d= -f2` is correct and handles the standard systemd output format. No field value contains `=` in practice for these fields.

The `is_systemd_activating()` function correctly classifies:
- `ActiveState=activating` (any substate) → healing
- `SubState=auto-restart` (regardless of ActiveState) → healing
- Everything else → not activating

The second condition (`SubState=auto-restart` regardless of ActiveState) is the important one: during the RestartSec countdown, systemd may report `ActiveState=failed` with `SubState=auto-restart`. This correctly catches the case.
