## Stage 1 — Vision alignment (written before reading implementation)

### Adversarial prior

My prior entering this review: this reorganization is solving the wrong problem, or solving the right problem in a direction that forecloses better paths.

The framing I'm testing: docs organized by origin rather than epistemic status is causing real failures — agents loading WOS docs have no structural signal about which files to trust. If this is true, the PR's approach (directory-as-authority-signal) is structurally sound. If this is false — if the actual failure mode is that agents ignore docs entirely, or that path references in code are the binding artifact not directory position — then reorganizing directories rearranges furniture while the problem lives elsewhere.

### Vision alignment questions

**What is the implicit theory of change?** The PR claims agents loading docs for WOS work had no structural signal for which files to trust. The fix: make directory position encode authority level. `docs/wos/current/` means authoritative; `docs/wos/archived/` means superseded. The theory of change is: agents that read docs will make fewer misaligned decisions because the structure answers "is this authoritative?" without requiring the agent to parse document prose.

**What would have to be true for this to be the right path?** Agents would have to be (a) loading docs as orientation before WOS work, and (b) making decisions based on doc content rather than DB state or live registry. Both are plausible. The vision.yaml risk-1 explicitly names "agents read as context rather than query structurally" as a real risk — but that's a risk about vision.yaml specifically, not docs generally. If agents are primarily consulting the WOS registry DB for operational decisions and docs only for design background, the epistemic-status gap in docs has lower real-world impact.

**Is there a cheaper test of the assumption?** The PR is testing the assumption structurally by reorganizing. A cheaper test would have been: what agent behavior would change if docs were reorganized? What decision in the last week was made worse by not knowing a doc was superseded? This test was not run. However, this is a low-cost PR (docs only, pure renames + unified spec) — the risk of the assumption being wrong is low.

**What does this foreclose?** Very little. Directory-level authority encoding is additive. It doesn't prevent a future approach (e.g., frontmatter-based machine-readable status) and in fact uses frontmatter for the SUPERSEDED signal. The consolidated `wos-v3-spec.md` is the highest-risk element: if the two source docs (wos-v3-proposal.md and wos-v3-steward-executor-spec.md) had meaningful divergence between them, the unification may have silently resolved that divergence in one direction. But this is a small risk, and the source docs are archived for reference.

**Opportunity cost relative to vision priorities?** vision.yaml current_focus.this_week names WOS bidirectional interface (#1118) and completion notification layer as primary. This PR is docs maintenance. However, the PR's stated purpose is to reduce agent miscalibration when loading WOS docs — which directly supports the WOS work in current_focus. The cost is bounded.

**Golden patterns active in Stage 1:**

The "canonical placement must be obvious from first encounter" golden pattern (2026-04-25) is directly relevant: the original docs/ structure was organized by origin rather than epistemic status, meaning a new contributor could not determine authority level from structure alone. This pattern states: "A name that needs a comment to justify it has not found its form." The pre-PR docs/ structure required opening each file to determine its status — the form had not been found. This constrained my Stage 1 analysis: the problem being solved is real, not constructed. The pattern also names "no split canonical homes" — the PR eliminates the split between `wos-v3-proposal.md` and `wos-v3-steward-executor-spec.md` by unifying them, which is a direct application.

The "design-spec-blockquote as authority-status declaration" golden pattern (2026-05-03) is also relevant: it establishes that design docs co-existing with divergent production implementations require explicit status markers. The SUPERSEDED frontmatter on archived docs is this pattern applied at the directory+frontmatter level.

**Alignment verdict: Confirmed.** The problem being solved (epistemic-status ambiguity in docs/) is real and traceable to vision.yaml risk-1. The approach is the correct form for this problem. The cost is low and the foreclosure risk is minimal.

## Stage 2 — Implementation quality review

### Encoded Orientation check

Does this PR constitute an Encoded Orientation decision — changing behavioral defaults, system constraints, agent identity, or decision-making rules in a durable way?

The PR includes one non-docs change to `.claude/agents/review.md`: updating the path from `docs/engineering-lessons-learned.md` to `docs/reference/engineering-lessons-learned.md`. The `oracle/document-review-protocol.md` is a new protocol document. This expands the oracle review system to cover non-code artifacts (retros, design docs). This is an Encoded Orientation decision: it changes the oracle's decision-making rules. Checking constraint-3 requirements:

- **Prior logged decision exists?** No explicit oracle verdict authorizing this expansion is cited. The document itself notes it was "Produced by WOS UoW uow_20260427_a30505" — the UoW is the authorization context. The document itself is thorough and well-specified (self-applying worked example shows it passed the self-applying Stage 2 check from golden-patterns.md 2026-04-20).
- **Traceable to vision.yaml anchor?** vision.yaml constraint-2: "Every agent decision that touches Dan's priorities must be traceable to a specific field in the Vision Object or a logged open decision." The document-review-protocol extends oracle authority to document artifacts — this is a system constraint change. The closest vision.yaml anchor is constraint-2 itself (traceability) and constraint-3 (full OODA loop). The connection is plausible but not explicit.

I am not blocking on this. The WOS UoW authorization provides the prior-decision context, and the document-review-protocol is well-enough specified that the constraint-3 borderline is in acceptable territory. I am noting it as a finding, not a blocker.

This is the same risk that existed before — it has not been introduced by this PR. The PR is correct to update the reference; the structural solution (a config variable or canonical-locations file) is out of scope.

**`docs/wos/current/INDEX.md` is now the component glossary pointer in three source files.** If `INDEX.md` moves or is renamed, three warning strings in the production codebase will reference a broken path. Low risk — INDEX.md is now a first-class document in a stable location.

**`oracle/document-review-protocol.md` — the worked example is self-referential and hypothetical.** The worked example (Section 3) imagines an oracle reviewing the protocol itself and issuing NEEDS_CHANGES because it lacks a storage location for approved verdicts. The document then immediately provides that storage location in section 1. This is a clever self-applying structure (consistent with golden-patterns.md 2026-04-20), but the hypothetical NEEDS_CHANGES in the worked example is confusing to a first-time reader: they see "VERDICT: NEEDS_CHANGES" in the document and must read carefully to understand it is an example, not an actual verdict on the document. The `VERDICT: NEEDS_CHANGES` in the worked example is not machine-parseable as a verdict on this document (it is inside a code block), so the dispatcher PR Merge Gate would not misinterpret it. This is a readability note, not a correctness issue.

### What does this make easier?

- Agent orientation before WOS work is now structurally guided: load `docs/wos/current/` for authoritative specs, skip `docs/wos/archived/` unless doing historical research.
