## Stage 1 — Vision Alignment (written before seeing the diff)

**Adversarial prior:** This implementation is solving the wrong problem, or solving the right problem in a direction that forecloses better paths.

**What would have to be true for this work to be the right path?**

The vision's `current_focus.current_constraint` explicitly names the WOS bidirectional interface (#1118) as the active blocker: "the HTML dashboard needs to support user-initiated actions (approve, cancel, reprioritize) not just read-only status." For this PR to be right, the Telegram deep-link UX must be the least-friction path for Dan to execute WOS actions — not a screen-switching detour.

**Stress test:** Telegram deep-links route browser → Telegram app → `/start` handler → reply. That is three context-switches for each action. The alternative (native HTML form POST to a local or hosted API) would eliminate the Telegram hop. Does this violate constraint-4 (minimize metabolic cost of cybernetic engagement)?

**Resolution:** The deep-link pattern keeps Telegram as the authoritative action surface, which is correct for this system. Dan receives all WOS notifications and results via Telegram already. The HTML dashboard is a secondary visibility surface, not an interaction-primary surface. The action handler runs inline in the dispatcher (no subagent), meaning the round-trip is: tap → Telegram sends `/start` → dispatcher handles → reply in Telegram. The net result is: Dan is in Telegram before and after the action. The browser is a read surface; Telegram is the action surface. This is architecturally consistent with constraint-4.

**What does this foreclose?** The base64url payload encoding and the specific `{"a": ..., "u": ...}` format become a contract between the dashboard generator and the dispatcher handler. Any future action type must fit this envelope. This is a low-severity foreclosure — the envelope is extensible by adding action names.

**Opportunity cost check:** vision.yaml `horizon.next` = "Complete WOS bidirectional interface (#1118). Verify completion notification delivery end-to-end." This PR directly closes the first item. The investment is justified by the vision anchor.

**Alignment verdict: Confirmed.** The PR serves the active constraint and the stated horizon. The deep-link approach is consistent with the system's interaction model. The Stage 1 question is answered: this is solving the right problem.

- **Prior logged decision:** No `oracle/verdicts/` entry or `meta/premise-review.md` item records a prior decision to add `/start` deep-link routing to the dispatcher. The bootup doc change was introduced without a prior logged decision of the same class.
- **Vision anchor:** `current_focus.current_constraint` names the bidirectional interface need, which is sufficient as a vision anchor.
- **Assessment:** One of the two constraint-3 requirements (prior logged decision) is missing. However, the vision anchor is present and the change is traceable. The constraint-3 gate requires BOTH. This is a soft miss — the decision is clearly justified by the active constraint, but the logged-prior requirement exists precisely to ensure the dispatcher's orientation encoding is traceable after compaction. The bootup doc addition should carry a decision reference (an issue number, an oracle round, or a WOS UoW ID) so future reviewers can trace it.

This is flagged as a **NEEDS_CHANGES** item: the `/start` routing block in `sys.dispatcher.bootup.md` should include a `decision:` reference or a comment tracing it to a logged decision.

### Gap 1: Duplicate deep-link encoding logic (code duplication pattern)

`_action_footer_html` in `wos_uow_detail_gen.py` and `_tg_deep_link()` in `wos_dashboard.py` implement identical base64url encoding logic:

- `wos_dashboard.py._tg_deep_link`: `base64.urlsafe_b64encode(json.dumps({"a": action, "u": uow_id}, separators=(",", ":")).encode()).rstrip(b"=").decode()`
- `wos_uow_detail_gen.py._action_footer_html` (inner `_link()`): same pattern, re-implemented inline.

`wos_uow_detail_gen.py` does not import `_tg_deep_link` from `wos_dashboard.py`. This is a private duplication — both encode identically today, but are independent going forward. If the payload format changes (e.g., adding a `"c"` chat_id field for multi-tenant routing), both sites must be updated in lockstep with no tooling enforcement. The `TELEGRAM_BOT_USERNAME` env var default (`"LobsterBot"`) is also duplicated.

The golden-patterns.md "canonical placement must be obvious from first encounter" principle applies: there is no obvious answer to "where does the deep-link encoding live?" — it lives in two places.

**Fix required:** Extract `_tg_deep_link(action, uow_id)` to a shared location (e.g., a new `src/orchestration/wos_action_link.py` or moved to a module both files import). Both `wos_dashboard.py` and `wos_uow_detail_gen.py` should import from the canonical site.

### Gap 2: Bare `except Exception` silently swallows registry errors in `_active_uows` / `_stalled_uows`

The refactored `_active_uows()` and `_stalled_uows()` wrap each `registry.list(status=status_str)` call in `try/except Exception: continue`. This means if the registry raises for a status that is not a legacy issue (e.g., a DB connection error, a schema change, a null registry), the dashboard renders an empty active-UoW table with no error signal. The prior code's failure mode (crashing on a legacy `closed` row) was loud; the new code's failure mode (silently empty dashboard) is silent.

The bare `except Exception: continue` is broader than needed. The actual failure being guarded against is an enum parsing error from `UoWStatus` when the DB contains legacy string values. The correct guard is either:
- a narrower exception type (the specific exception `UoWStatus(...)` raises on an invalid value), or
- a pre-filter at the registry level so the query itself does not return rows with legacy status values.

The current approach converts a loud failure into a silent one across all exception classes.

**Fix required:** Narrow the except clause to the specific exception type raised by enum parsing failure, or add logging before the `continue` so an empty dashboard is distinguishable from "no active UoWs."

### Gap 3: String-replace injection in `generate_html()` is fragile

```python
return html.replace("</div>\n</body>\n</html>", f"{action_footer}\n</div>\n</body>\n</html>")
```

This is a string-replace injection into the output of `_HTML_TEMPLATE.format(...)`. It works as long as:
1. The template ends with exactly `</div>\n</body>\n</html>` (no trailing whitespace, no CRLF, exact match).
2. This string does not appear elsewhere in the template.

If the template is reformatted (e.g., `</div>\r\n</body>\r\n</html>` on Windows), or if a future template update changes the closing structure, the replace silently fails and the action footer disappears from the output with no error. The test plan only checks that `_action_footer_html('uow_test_abc123')` returns valid HTML — it does not verify the footer appears in `generate_html()` output.

The golden-patterns.md "proactive resilience over reactive recovery" (principle-1) applies: this is a reactive injection pattern rather than a designed injection point.

**Fix required:** Either (a) add a named placeholder (e.g., `{action_footer}`) to `_HTML_TEMPLATE` and pass `action_footer_html=_action_footer_html(uow_id)` to `.format()`, or (b) assert the replace succeeded by checking `html != result` after the replace, raising a descriptive error if not.

The test plan checks:

None of these verify that the dispatcher correctly routes a `/start <payload>` message to `handle_wos_action`. The bootup doc addition is prose — it describes what the dispatcher should do, but there is no hook, no test, and no structural enforcement (contrast with the PR Merge Gate hook pattern in golden-patterns.md "advisory-to-hook promotion"). The `/start` routing is entirely advisory.

This is noted as a gap but not a hard blocker if the test plan is updated to call `handle_wos_action` with a valid encoded payload and assert the registry transition. The existing 52 tests presumably cover the handler's internals.

**Fix required (lower severity):** Add one test that encodes a valid payload, calls `handle_wos_action`, and asserts both the return string and the registry state transition. The PR description's test plan checks import success but not invocation correctness.

### Gap 5: Auth guard is permissive by default with no documented operational risk

```python
admin_chat_id_str = os.environ.get("TELEGRAM_ADMIN_CHAT_ID", "")
if admin_chat_id_str and str(chat_id) != admin_chat_id_str:
    return "Unauthorized: WOS actions are restricted to the admin user."
```

If `TELEGRAM_ADMIN_CHAT_ID` is unset, any Telegram user who can craft a valid deep-link can execute WOS registry writes (status changes, audit log appends). The comment says "permissive default for single-user installs" — which is accurate but understates the operational risk: a public Telegram bot with an unset `TELEGRAM_ADMIN_CHAT_ID` would accept WOS actions from any user.

The `TELEGRAM_ADMIN_CHAT_ID` env var is not documented in the PR description, not added to any config template, and not checked in `upgrade.sh`. If Dan's instance does not have this set (or if the var was never defined), the guard is a no-op.

**Fix required:** Either (a) add `TELEGRAM_ADMIN_CHAT_ID` to the config template / upgrade.sh verification step so its absence is surfaced on deploy, or (b) reverse the default to deny-all when the var is unset (requiring an explicit opt-in to the permissive mode). As-is, the auth guard is security theater if the env var is not set.
