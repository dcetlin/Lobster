## Stage 1: Vision alignment

**Prior entering this review:** This PR is solving the wrong problem, or solving the right problem in a direction that forecloses better paths.

**What would have to be true for this work to be the right path:**
The two identified leak structures — `_error_timestamps` and the `message_claims` table — must account for a meaningful portion of the 7–10 GB RSS growth observed over 2–4 hours. The PR explicitly acknowledges that PRs #1432 (infinite dispatch loop) and #1433 (large inline wos_execute blobs) are already merged, so this is addressing what remains.

**The Stage 1 question:** Are these two leaks sufficient to stop the OOMs, or is the real driver elsewhere?

**Honest assessment:**

The PR cannot prove sufficiency — and it does not claim to. The system-audit context confirms 8 OOM kills in ~2 months with accelerating frequency (5 kills in the last 2 days). The issue description correctly identifies that the root cause was hypothesized (needs a heap profile) rather than confirmed by measurement. The PR body similarly states: "The OOM-level growth (7–10 GB) requires hours to manifest, so direct RSS verification requires waiting."

This is the crux of Stage 1. The fix is structurally correct — both structures now have bounded lifetimes where previously they had none. But the key question is: **are these two structures large enough to drive 7–10 GB RSS?** The `_error_timestamps` list stores Python datetime objects (~72 bytes each). Even at 10,000 errors/hour over 4 hours without pruning, that is roughly 2.9 MB — not 7 GB. The `message_claims` table is SQLite (on disk + WAL + page cache), not Python heap. 5,376 rows is unlikely to drive GB-scale RSS growth in Python.

This suggests the two fixed leaks may not be the dominant contributors to the OOM. The PR description itself acknowledges this obliquely: "The acceleration pattern (28 min in the most recent kill on Jun 6) points to two in-memory structures that accumulate without bound." But a 28-minute kill window with two structures of modest per-element size does not cleanly fit.

**What this PR forecloses:** Nothing — these are correct fixes regardless of whether they are the primary driver. Pruning two unbounded structures is correct engineering independent of their relative contribution to the OOM. The concern is that if a larger driver exists (MCP JSON response accumulation, session_store SQLite WAL growth, tool list generation creating large in-memory objects per-call, observation queue overflow accumulation, or something else in the 11,500-line inbox_server.py), the OOM kills will continue after this PR and the time spent on this PR will be categorized as "necessary but insufficient." That is not a reason to reject the PR — it is a reason to confirm the PR and simultaneously note that the OOM investigation is not closed.

**Vision alignment:** Confirmed. The vision's "proactive resilience over reactive recovery" (principle-1) and "structural prevention is preferred over better correction mechanisms" both apply here. Fixing two confirmed unbounded accumulation patterns before they compound further is structurally correct. The work does not foreclose anything — if a larger driver is found, this PR is still a net improvement.

**Adversarial prior outcome:** Disconfirmed — this is the right work — but with the honest observation that it is likely necessary and not yet proven sufficient. The investigation into root cause should continue in parallel.

### Leak 1: MetricsListener._error_timestamps (event_bus.py)

**Correctness of the fix:**

The `_prune_error_timestamps()` method is introduced as a private helper that computes a new cutoff of `datetime.now(timezone.utc) - timedelta(hours=1)` and list-comprehends out entries older than 1 hour. This is called from two sites:

1. `deliver()` — every `_PRUNE_INTERVAL` (100) deliveries, inside the `self._lock` hold
2. `get_snapshot()` — on every snapshot, also inside the `self._lock` hold (now delegating to the helper rather than inlining the same list comprehension)

**Thread-safety:** The prune is called under `self._lock` in both paths. The `_deliver_count` increment happens inside the lock as well. No race condition is introduced. Correct.

**Sliding-window math:** The cutoff is `now - timedelta(hours=1)` and the filter is `ts >= cutoff` (inclusive). This is consistent with the existing `get_snapshot()` semantics. No regression.

**Amortization reasoning:** At 100 deliveries per prune interval, the list can accumulate at most 100 extra entries beyond the 1-hour window before eviction. The maximum extra accumulation is bounded at `_PRUNE_INTERVAL` events, not unlimited. The PR's comment correctly characterizes this: "at most 100 extra entries can accumulate before the next prune fires."

**One structural note (non-blocking):** `_prune_error_timestamps()` is documented as "Must be called under self._lock" in its docstring. Both call sites honor this. However, the method is not structurally enforced — it is documented as an invariant but not checked. This is consistent with the existing codebase convention (the surrounding class has similar undocumented lock requirements). Not a defect; noting for pattern consistency.

**The `deliver()` prune fires inside the outer `try: ... except Exception: pass` block.** The `_prune_error_timestamps()` call is inside the `with self._lock:` block, which is inside the `try`. If `_prune_error_timestamps()` raises (it cannot under normal operation, but could if `datetime.now()` raised or the list was replaced mid-comprehension by another thread — the lock prevents the latter), the `except Exception: pass` swallows it. This is the correct behavior for a metrics listener that must never propagate. Correct.

**Test coverage adequacy:**
- `test_error_timestamps_bounded_without_get_snapshot`: drives `PRUNE_INTERVAL + 10` old-timestamped events through `deliver()` without calling `get_snapshot()`, then asserts the list has fewer entries than events delivered. This directly tests the regression scenario.
- `test_recent_error_timestamps_preserved_after_prune`: mixes old and recent events across the prune interval, verifies recent events survive. Tests the preservation side.
- `test_get_snapshot_errors_last_1h_accurate`: verifies the snapshot count after delivering old and recent events. Tests end-to-end correctness of the sliding window.
- `test_prune_interval_constant_is_importable`: verifies `_PRUNE_INTERVAL` is an importable positive int (golden-patterns: named display cap / importable constant).

**Mirror-constant check:** The test uses `PRUNE_INTERVAL = MetricsListener._PRUNE_INTERVAL` (imports from production, does not redeclare). Correct — this is the right pattern per learnings.md (PRs #696, #800, #967, #970, etc.). No mirror-constant finding here.

Coverage is adequate. The primary regression scenario (bounded without get_snapshot) is directly tested.

### Leak 2: message_claims SQLite table (claims.py)

**Correctness of the pruning logic:**

`_prune_old_claims()` deletes rows where `claimed_at < cutoff_iso`, where `cutoff_iso` is `datetime.now(timezone.utc) - timedelta(days=7)`. The cutoff is computed fresh on each call. The `DELETE` uses the same connection as all other operations. The method is wrapped in a `try/except Exception` that logs at DEBUG level and swallows the exception — consistent with the "non-fatal" contract described in the docstring.

`cleanup_old_claims()` (the public startup-cleanup method) uses identical logic but logs at INFO level (startup) rather than DEBUG (periodic), and returns the deleted count. The inbox_server.py startup code calls it and logs the result.

**The `_claim_count` increment placement:**

From the diff, after the `with conn:` block succeeds (INSERT succeeded), the code does:
```python
self._claim_count += 1
if self._claim_count % self._CLAIM_PRUNE_INTERVAL == 0:
    self._prune_old_claims()
return True
```

This is **inside the `try:` block**, after the `with conn:` succeeds. The `return True` comes after the increment and optional prune. This means:
- The counter only increments on successful claims (INSERT succeeded)
- Failed claims (`IntegrityError` → `return False`) do not increment the counter
- The `fail-open` path (generic exception → `return True`) bypasses the increment because the prune check is inside the `try` but the exception handler goes directly to `return True`

Wait — re-reading the diff carefully: the increment is placed **before** `return True` inside the `try` block, after the `with conn:` block. The `except sqlite3.IntegrityError: return False` catch comes after. The `except Exception as exc: ... return True` fail-open also comes after. So the increment only fires on successful INSERT. That is correct. The prune does not fire on duplicate-claim attempts (IntegrityError) or DB failures (fail-open). This is the right design — the counter tracks successful claims, which is the only path that adds rows.

**Thread-safety of `_claim_count`:** `_claim_count` is an instance variable incremented in `claim()`. The existing docstring says "Thread-safe: SQLite serializes concurrent INSERTs under WAL mode." However, `_claim_count` is a Python int incremented outside any lock. Two concurrent threads could read the same value, both increment, and both potentially trigger `_prune_old_claims()` at the same time.

This is a real but low-severity issue:
- Python's GIL means the `+=` is effectively atomic for CPython on a GIL-protected int
- Even if two concurrent calls both trigger the prune at the same count, the prune is idempotent (two concurrent DELETEs on the same rows — the second DELETE finds 0 rows and returns 0) — SQLite WAL serializes the writes
- The `except Exception` in `_prune_old_claims()` catches any resulting error

Under CPython with GIL, this is safe. Under a hypothetical no-GIL Python, this would be a race. For the current deployment context (CPython 3.11+), this is acceptable.

**Startup wiring:**

`inbox_server.py` calls `_claims_db.cleanup_old_claims()` immediately after `_claims_db = _AtomicClaimDB()` succeeds. The `_NoOpClaimsDB` stub now includes a `cleanup_old_claims` method that returns 0 — this is the correct defensive addition. Without this stub method, the startup code's `_claims_db.cleanup_old_claims()` call on a no-op stub would raise `AttributeError`. The PR correctly adds it.

The startup cleanup is inside a nested try/except that is itself inside the outer try/except that degrades to `_NoOpClaimsDB`. The log message in the startup cleanup uses an f-string (`log.warning(f"..."`) while the rest of claims.py uses `%`-style formatting. This is a minor inconsistency — not a correctness defect.

**Test coverage adequacy:**

The `test_claims_pruning.py` tests use direct SQLite insertion (`_insert_claim` helper) to plant rows at controlled timestamps, bypassing `claim()` to isolate age from counter behavior. This is the correct approach for testing time-based deletion.

- `test_old_rows_removed_and_count_returned`: plants 5 old rows, verifies `cleanup_old_claims()` returns 5 and leaves 0 rows
- `test_recent_rows_preserved`: plants 3 old + 4 recent, verifies 3 deleted, 4 preserved
- `test_returns_zero_when_table_is_empty`: edge case, correct
- `test_rows_exactly_at_boundary_not_deleted`: the boundary test plants a row `PRUNE_AGE_DAYS - 0.05` days old (i.e., just inside the window, 1.2 hours before the cutoff) and verifies it is NOT deleted. The name says "exactly at boundary" but the test uses `days=PRUNE_AGE_DAYS - 0.05` which is actually 1.2 hours inside the window, not at the exact boundary. The intent is clear (test the preservation side) but the name is slightly misleading. Non-blocking.
- `test_prune_fires_after_prune_interval_claims` and `test_prune_does_not_fire_before_interval`: directly test the `_CLAIM_PRUNE_INTERVAL` mechanism. The "fires after" test drives exactly `PRUNE_INTERVAL` claim() calls and verifies old rows are gone. The "does not fire before" test drives `PRUNE_INTERVAL - 1` calls and verifies old rows survive.

**Mirror-constant check:** The test file uses `PRUNE_AGE_DAYS = AtomicClaimDB._CLAIM_PRUNE_AGE_DAYS` and `PRUNE_INTERVAL = AtomicClaimDB._CLAIM_PRUNE_INTERVAL` — imported from production, not redeclared. Correct per the named-constant golden pattern.

**Feature-bundling check:** PR modifies 2 source files (event_bus.py, claims.py), 1 test file (test_event_bus.py additions), 1 new test file (test_claims_pruning.py), and 1 wiring file (inbox_server.py). All 5 files are described in the PR body. No undescribed changes. Clean.

**Encoded Orientation check (OODA constraint-3):** This PR changes internal server behavior (pruning schedules, startup cleanup), not agent decision-making rules, behavioral defaults, or system constraints in the OODA sense. The fix is a correctness/stability fix. No Encoded Orientation decision.

**Migration check:** No new DB migrations. The `message_claims` table already exists from prior PRs. The startup cleanup and periodic pruning require no schema changes. Correct.

**Ruff check:** PR description states 7 pre-existing E402/E741 errors in event_bus.py, 0 new errors introduced by this PR. The claims.py changes are ruff-clean.

**Missing coverage note (non-blocking):**
