### Stage 2: Quality review

**Engineer concern 1: _upsert_verdict INSERT OR IGNORE + UPDATE pattern**

Pattern verified correct for accumulator semantics. The INSERT OR IGNORE ensures
the row exists; the conditional UPDATE increments exactly one counter and sets
last_updated. Non-matched counters (e.g., n_failures and n_partial when outcome
is "pass") are untouched by the UPDATE because they are not named in the SET
clause. This is precisely the stated anti-pattern avoidance — INSERT OR REPLACE
would reset all counters by inserting a new row with DEFAULT 0 values.

The idempotency concern: if `score_and_normalize_verdict` is called twice for the
same UoW (e.g., due to retry), it will double-count. The `_mark_hypothesis_scored`
function uses `WHERE scored_at IS NULL` to prevent re-marking, but
`_upsert_verdict` has no such guard — it will increment on every call regardless.
This is a known structural limitation. The PR's `_ensure_schema` + non-fatal
design means re-calls are unlikely in normal operation (UoW closure fires once),
and the engineer's description does not promise strict per-UoW idempotency at the
accumulator level. Advisory note: if future work exposes the scoring hook to
retry paths, a `scored_at` guard in `_upsert_verdict` would prevent double-count.
Not a blocker for this PR.

**Engineer concern 2: Hypothesis source priority in _score_verdict_for_uow**

Reviewed. The function looks up `prescription_hypothesis_log` via
`get_hypothesis_for_uow(uow_id)` (returns the most recent unscored row) and falls
back to `uow.summary` via `hypothesis_from_uow_summary()`. The fallback is
correctly documented in the PR description as the bootstrap behavior for UoWs
created before this deploy. The `getattr(uow, "register", "operational")` fallback
for register is also correct — the schema has no null constraint on register in
verdict_accumulator, and "operational" is a valid default.

**Engineer concern 3: get_normalization_cluster_health join semantics**

The join `normalization_log n JOIN prescription_hypothesis_log p ON n.uow_id = p.uow_id`
by uow_id is semantically correct for the stated purpose: getting the register for
each normalization_log row. The data dependency is: normalization_log records raw
hypotheses (by uow_id, no register column); prescription_hypothesis_log has the
register for each uow_id. The join correctly derives `distinct_raw` per register.

One structural note: the outer query (accumulator_rows) and the inner query
(raw_counts via JOIN) use different source tables. If a normalization_log row
exists for a uow_id with no corresponding prescription_hypothesis_log row (e.g.,
UoWs that used the uow.summary fallback path, which doesn't write to
prescription_hypothesis_log), that UoW's raw hypothesis will be excluded from
raw_counts. The `raw_counts.get(register, distinct_normalized)` fallback handles
the missing-register case by defaulting to distinct_normalized, which means the
distinct_raw column shows the normalized count (a conservative underestimate of
raw fragmentation). This is a known limitation of the summary-fallback path and
is explicitly documented as the bootstrap tradeoff. Not a blocker.

**Engineer concern 4: DUAL-DB PATTERN consistency**

Migration 0029 targets the registry DB via migrate.py — this is consistent with
how all prior migrations work. The migration SQL creates the three new tables.

`verdict_normalization.py` and `verdict_stats.py` read/write wos-metrics.db via
their own `_metrics_db_path()` function (resolves to
`$LOBSTER_WORKSPACE/orchestration/wos-metrics.db`). The `_ensure_schema` call in
`score_and_normalize_verdict` creates the tables lazily on wos-metrics.db.

This matches the prescription_metrics.py pattern exactly:
- `PrescriptionMetricsLogger._ensure_schema()` creates tables lazily on
  wos-metrics.db
- migrate.py runs on registry DB; migration 0028 is explicitly a documentation
  file, not an executable migration

However: migration 0029 is an executable migration (contains CREATE TABLE
statements) targeting registry DB, but the tables it creates (verdict_accumulator,
prescription_hypothesis_log, normalization_log) are also created lazily by
`_ensure_schema` on wos-metrics.db. These are the SAME table names in TWO
different databases.

This diverges from migration 0028's explicit documentation: "This file documents
the intended schema for reference; it is not applied by the migrate.py runner."

The verdict: migration 0029 creates these tables in registry DB
($REGISTRY_DB_PATH = registry.db), while `_ensure_schema` creates the same tables
in wos-metrics.db. The production flow writes to wos-metrics.db (the verdict_stats
and verdict_normalization functions use _metrics_db_path, not REGISTRY_DB).
The tables in registry.db are created but never written to by this code.

This is not a correctness defect — the tables exist in both DBs but only
wos-metrics.db is actually used by the new code. However, it is a structural
divergence from the prescription_metrics pattern, which has NO executable
migration for wos-metrics.db tables. The migration 0028 explicitly states that
wos-metrics.db tables should be documented but NOT migrated via migrate.py.

Migration 0029 ships an executable migration that creates tables in registry.db
that are never used by the production code. The live tables are in wos-metrics.db,
lazily created by _ensure_schema. This is a documentation inconsistency rather
than a runtime defect — the code works correctly, but the migration creates
orphaned tables in the wrong DB.

Verdict: the runtime behavior is correct. The migration 0029 tables in registry.db
are dead schema — harmless but inconsistent with the established pattern. The
test suite (TestMigration0029) verifies the migration is idempotent and the tables
exist, but tests use a tmp wos.db path that exercises the migration runner, not
the actual production wos-metrics.db path. This means the test is validating the
migration runner, not the runtime code path.

This is an advisory finding — the code is functionally correct and the runtime
DB (wos-metrics.db) is handled correctly via _ensure_schema. The orphaned migration
tables do not affect correctness. Not a blocker.
