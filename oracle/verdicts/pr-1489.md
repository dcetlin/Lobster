## Stage 1 — right problem?

**Prior:** entering this review, the working assumption was that the "masked failure" framing was likely a narrative dressing — that a 4-night streak of "succeeded" reports with `synced:0` was either overstated by tonight's agent (pattern-matching two loosely-related issues into a tidy story) or that #1480 was not actually the operative cause. This is exactly the shape of claim this review posture exists to distrust: an autonomous overnight job asserting a clean two-bug causal chain about its own domain, with no human in the loop before the PR was opened.

**Golden-pattern citation and its effect on the review:** `oracle/learnings.md` (2026-04-21, PR #804 re-oracle) names exactly this failure class — "Migration path mismatch produces silent no-op... For state files, the canonical location is determined by the runtime code that reads them — trace the reader, not the writer's assumption about where the file should be." This PR is structurally the same bug (default source path resolves to a directory that doesn't exist → guarded no-op → apparent success with zero effect) applied to a bridge-sync function instead of a migration script. Because this pattern was active going in, I did not accept the PR's own claim that `~/lobster-user-config` is the correct canonical path — I independently traced the reader (CLAUDE.md's "Key Directories" section, and confirmed the files actually exist on disk at that path) rather than trusting the PR body's assertion, and I ran the fix against the real files rather than only the test harness's synthetic fixtures. This is also why I did not stop at "tests pass" for Stage 2 — the PR #804 precedent is specifically about tests/guards passing while the underlying path is silently wrong, so a passing test suite was treated as necessary but not sufficient, and I re-derived the sync counts from a scratch DB pointed at the real production directory as a check independent of both the PR's test suite and its prose claims.

**Verification of the causal claim:** confirmed, not overstated. The `~/lobster-user-config/memory/archive/digests/` archive is written each night by an independent nightly-consolidation job run, contemporaneously, before tonight's PR existed — it is not something tonight's agent could have retroactively fabricated evidence for. It shows, in its own words, four consecutive nights (Jul 27, 28, 29, 30) of "Step 10 (bridge sync) SUCCEEDED again this cycle... result: `{'projects': {'synced': 0, ...}, 'priorities': {'injected': 0}, ...}`" — immediately preceded by a run (Jul 25–26) that failed outright with the `ModuleNotFoundError` from #1482. That transition (crash → "succeeds" but zero-effect) lines up exactly with when the in-session manual import-path workaround started being applied, without the #1480 path/row_factory fixes. #1480's own issue body independently root-causes the zero-count behavior to the wrong default directory, filed and diagnosed by a separate report two days before #1482, before this PR's author ever touched the code. Both bugs are real, distinct, and compounding as claimed — this is not a narrative embellishment.

I read this restriction as scoped to the *inference/prediction* subsystem (drift detection, emotional/preference modeling — the genuinely new-capability parts of user-model-v2) rather than to `bridges.py`'s ETL-style sync of already-shipped, already-invoked, already-documented markdown→DB plumbing that predates this PR and is called every night regardless of whether this fix lands. **Patterns this introduces:** the `canonical_path` vs `workspace_path` split (source-of-truth directory vs. output directory as two independently-overridable, separately-defaulted parameters) is a reusable pattern anywhere a function currently conflates "where I read canonical input from" with "where I write output" under one `workspace_path` parameter — worth citing forward if a similar conflation surfaces elsewhere in `user_model/`.
