- `scripts/health-check-v3.sh` line ~161: `WFM_SUPPRESSION_MARGIN_SECONDS="${LOBSTER_WFM_SUPPRESSION_MARGIN_SECONDS:-300}"` — the 300s default margin is NOT reliably larger than the health-check cron cadence (`*/4 * * * *` = 240s, per `install.sh` and live crontab) by any real safety factor (300/240 = 1.25x). Because `main()` calls `check_session_age()` (fires graceful SIGTERM at `session_age >= SESSION_AGE_LIMIT_SECONDS = 7200s`) strictly before `check_dispatcher_heartbeat()` (fires RED at `heartbeat_stale_age >= WFM_SUPPRESSION_MAX_SECONDS = 6900s`) in the same script run, and a session that goes idle at/near its own start has `heartbeat_stale_age ≈ session_age`, the 300-second window `[6900s, 7200s)` during which RED-but-not-yet-graceful-restart is possible is *larger* than one 240s cron tick. By pigeonhole, that window is guaranteed to contain at least one cron check for any phase alignment — meaning the "idle since near session start" case (a real, not rare, pattern — e.g. dispatcher restarts into an empty inbox overnight) will still trip the forced-restart/alert path (`do_restart` + Telegram alert, confirmed at health-check-v3.sh lines ~2537-2567) *before* the graceful SIGTERM path ever gets a chance to run. This directly falsifies the code comment's claim ("a legitimately idle session... is now always reaped by the graceful SESSION_AGE_LIMIT restart before this cap can fire") and the regression test's docstring claim ("proving the false-positive path is actually closed, not just relabeled") — it is not closed, it is delayed from firing every ~45min to firing once per idle-from-near-start session at ~115min. That is a large, genuine improvement in frequency, but it is not the invariant the PR asserts, and the PR's own "Root-cause answer" section already concedes a residual risk exists — the code comment and test docstring should not claim more certainty than that section does.
- Fix: either increase `WFM_SUPPRESSION_MARGIN_SECONDS` to a value with a real safety factor over the cron cadence (e.g. 900-1200s, several cron ticks of buffer, chosen and documented explicitly against the 240s cadence — not just "less than SESSION_AGE_LIMIT_SECONDS"), or add an explicit ordering/suppression rule (e.g. skip the WFM-cap RED check entirely when `session_age` is already within N seconds of `SESSION_AGE_LIMIT_SECONDS`, since the graceful restart will fire imminently regardless), and add a unit test that asserts the margin-vs-cadence relationship as an enforced invariant rather than a prose assumption.
- `tests/test-health-check-dispatcher-heartbeat.sh` lines ~86-91: two NEW hardcoded mirror constants (`SESSION_AGE_LIMIT_SECONDS=7200`, `WFM_SUPPRESSION_MARGIN_SECONDS=300`) are declared independently of the production script's env-overridable computation in `scripts/health-check-v3.sh`, rather than sourced/derived from it. This is the "locally-declared mirror of a production constant" antipattern named in `oracle/learnings.md` (2026-04-20, PR #800): if the production defaults ever change, these test mirrors silently go stale and the test keeps passing against the wrong relationship.
