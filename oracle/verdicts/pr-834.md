## Round 1 — 2026-05-23

### Stage 1: Vision Alignment

**Prior entering this review:** This implementation is solving the wrong problem, or solving the right problem in a direction that forecloses better paths.

**Theory of change in vision.yaml this PR serves:**

The vision's fundamental intent is a system with "structural access to my intent, not just a prose reconstruction of it." Phase 1 success criterion sc-1 is: "removing vision.yaml would cause structurally different routing outcomes." The vision's active constraint is closing the observation-loop: the Vision Object solves routing but not the developmental ceiling — the inlet pathway (observation → field-change proposal → Dan confirm) was identified as the missing piece in a reflective-surface-queue observation dated 2026-03-27.

PR #834 builds exactly that missing piece. This is confirmed by: (1) the reflective-surface-queue.json entry naming "frictionless inlet pathway" as the structural gap; (2) vision.yaml active_project.phase_intent naming "build the substrate that lets every agent make intent-anchored decisions"; (3) od-1 (resolved 2026-03-28) establishing that agents may propose changes to current_focus.* with Dan confirmation.

**Is this solving the right problem?** Yes — confirmed. The vision inlet closes the loop from observation to field-change with Dan gating every write. The prior is disconfirmed for the core problem statement.

**What would have to be true for this to be the right path?** The binary confirm mechanism must actually be wired to the dispatcher callback routing path. If it is not, no proposal can ever be accepted or declined — the UI sends the button, Dan taps it, and nothing happens. This is the operative question for Stage 2.

**What does this foreclose?** The eligible field list encodes a permanent authority boundary via code rather than via the vision.yaml authority model header. Any change to which fields agents may propose now requires a code change to `_ELIGIBLE_EXACT` and `_CURRENT_FOCUS_PREFIX`, not a vision.yaml edit. This is a mild foreclosure but not a blocker — the field list is a reasonable seam for Phase 1.

**Encoded Orientation check (constraint-3):** This PR creates a mechanism by which agents can propose writes to `core.inviolable_constraints` and `active_project.phase_intent` via binary Telegram confirm. These are Dan-only fields per the vision.yaml authority model header. The mechanism is gated by Dan's explicit Accept tap — so it is not automated write. However, it establishes encoded orientation (a code path that can alter Dan-only structural fields) with a behavioral precedent. The od-1 decision (2026-03-28) authorized agent updates to `current_focus.*` and `life_domains.*` only. It did not authorize agent-originated proposals for `core.*` or `active_project.phase_intent`. This is a partially-unanchored Encoded Orientation decision: the `current_focus.*` eligibility is anchored by od-1; the `core.inviolable_constraints` and `active_project.phase_intent` eligibility is not anchored by a logged decision. A vision.yaml header note is not a logged decision — it states current authority assignment, not an authorization for proposal mechanisms.

**Alignment verdict: Confirmed (with constraint-3 flag on eligible field boundary).**

### Stage 2: Quality Review

**Does it do what it claims to do?**

Partially. The module correctly validates proposals, dispatches binary Telegram confirms with inline buttons, stores pending proposals atomically, and handles accept/decline via write to vision.yaml. The validation logic (eligible field check, field existence check, no-op check) is sound. The tests cover the five named scenarios.

However, there is a structural gap that renders the end-to-end path non-functional: **the callback handler is not wired into `route_callback_message`**. When Dan taps Accept or Decline, the dispatcher calls `route_callback_message(msg)` from `dispatcher_handlers.py`. That function currently handles only `decide_retry:` and `decide_close:` prefixes, then returns `handled=False` for everything else. The vision callbacks (`vision_accept:`, `vision_decline:`) fall through to the dispatcher's prose-based job-confirm/delete-confirm handling, which does not recognize them. No write to vision.yaml occurs.

The PR adds a `handle_vision_callback` shim to `dispatcher_handlers.py` with a usage comment showing correct integration, but the shim is never called from `route_callback_message`. This is a wiring gap, not a design gap.

**Gap 1: Callback routing not wired into route_callback_message**

The `handle_vision_callback` function in `dispatcher_handlers.py` is defined but not called by `route_callback_message`. The fix: add a branch in `route_callback_message` before the fall-through return that checks for `vision_accept:` and `vision_decline:` prefixes and routes to `handle_vision_callback`. Without this, every Accept/Decline tap by Dan silently produces "Unknown callback: vision_accept:..." as the reply, and vision.yaml is never written.

**Gap 2: yaml.dump silently destroys vision.yaml's authority model header**

In `handle_vision_accept`, the accepted field value is written back using `yaml.dump(vision_data, default_flow_style=False, allow_unicode=True)`. PyYAML's `yaml.dump` strips all YAML comments. The vision.yaml file begins with a 14-line comment block that constitutes the authority model for the entire system:

```
# Vision Object — Dan's intent at three temporal scales.
# Private: not committed to the Lobster repo.
# Authority model:
#   core.*                          — Dan only
#   active_project.phase_intent     — Dan only
...
```

On the first accepted proposal, this entire authority model is silently destroyed. The file still loads correctly as YAML, but the human-readable governance record is gone. A downstream agent or engineer reading vision.yaml for context would encounter a file with no authority model header, treating the loss as a pre-existing condition.

The fix: use a read-then-targeted-write approach (e.g., ruamel.yaml which preserves comments, or a regex-based field replacement that preserves the comment block). For Phase 1, the simplest acceptable fix is to use ruamel.yaml's round-trip loader, which is the idiomatic approach in Python for comment-preserving YAML writes.

**Gap 3: Hardcoded chat_id=6036 contradicts the established LOBSTER_ADMIN_CHAT_ID pattern**

`dispatch_vision_proposals`, `handle_vision_accept`, `handle_vision_decline`, and `handle_vision_callback` all default to `chat_id=6036`. The codebase's established pattern is `os.environ.get("LOBSTER_ADMIN_CHAT_ID", "8075091586")` — visible in `inbox_write.py`, `wos_throttle.py`, and `dispatcher_handlers.py`. The chat_id 6036 does not appear as an authoritative chat_id anywhere else in the codebase; the admin chat is 8075091586.

This means vision proposals on a canonical deploy would be dispatched to the wrong chat (6036), where they would be invisible to Dan. The default would need to be the env var pattern to be correct and portable across instances.

**Gap 4: active_project.phase_intent and core.inviolable_constraints eligibility lacks a logged prior decision**

vision.yaml's authority model header states: `active_project.phase_intent — Dan only` and `core.* — Dan only`. od-1 authorized agent updates to `current_focus.*` and `life_domains.*` with notification. It did not authorize agent-originated proposals for structural fields, even with a human confirm gate.

The PR extends proposal eligibility to these Dan-only fields without a logged decision. While the confirm gate provides a safeguard, establishing a code path that can alter Dan-only structural fields is an Encoded Orientation decision (constraint-3) that requires a logged prior. The fix: either (a) remove `core.inviolable_constraints` and `active_project.phase_intent` from the eligible set and restrict to `current_focus.*` only (anchored by od-1), or (b) log a decision in `oracle/verdicts/` explicitly authorizing proposal-plus-confirm as the mechanism for structural fields, with a vision.yaml anchor.

**Test observation (non-blocking):**

Test 4 (`test_accept_handler_writes_vision_yaml`) has a resource-management issue: it saves pending to the un-monkeypatched `vi.PENDING_JSON` (the live production path, not `tmp_data_dir`) due to the `try/finally` saving `original_pending` but calling `_save_pending({phash: proposal})` *before* the path is redirected in the `try` block. The `tmp_data_dir` fixture redirects `vi.PENDING_JSON` via monkeypatch, but the test directly calls `_save_pending` from the module (not through the monkeypatched attribute) and then reads `vi.PENDING_JSON` in the assertion. This has a subtle ordering issue: if `_save_pending` is called before `vi.PENDING_JSON` is set to `tmp_path / ...`, the file writes to production. Reading the test more carefully: `monkeypatch.setattr(vi, "PENDING_JSON", ...)` runs in the `tmp_data_dir` fixture before the test body, so the path IS redirected before `_save_pending` is called in the test. The test also stores `original_pending = vi.PENDING_JSON` and restores it in `finally` — but `monkeypatch` already handles restoration. The double-restore with `vi.PENDING_JSON = original_pending` in the `finally` block bypasses monkeypatch's cleanup order, potentially leaving production path exposed between the `finally` and monkeypatch teardown. This is a minor test hygiene issue, not a functional defect. Flag as note, not a revision-contract gap.

**What failure modes exist?**

1. Dan taps Accept → "Unknown callback: vision_accept:..." reply. No write occurs. (Gap 1 — functionally broken)
2. Dan accepts any valid proposal → vision.yaml comment block destroyed. (Gap 2 — data loss)
3. On a canonical deploy, proposals dispatched to wrong chat. (Gap 3 — wrong recipient)
4. Agent proposes change to core.inviolable_constraints → writes a new constraint with auto-generated id, rationale from the proposal's `basis` field — no review of constraint wording quality, no canonical id format check.

**What patterns does this introduce that will propagate?**

The binary confirm pattern (inline keyboard Accept/Decline with pending JSON storage) is a clean, reusable pattern for agent-originated structural changes. If the three blocking gaps are resolved, this pattern should be cited as a golden pattern candidate for other "agent proposes, Dan confirms" flows.

The inline import pattern in `_process_vision_proposals` (try `from src.harvest.vision_inlet` → fallback to `importlib.import_module("vision_inlet")`) is consistent with existing patterns in the codebase for cross-module imports in scheduled-task contexts.

### Revision contract

Each named gap must be resolved in one of three ways: (a) addressed — the revision shows the thing the gap named, (b) disputed — the author states why the gap does not apply, with specific reason, (c) deferred — the author acknowledges the gap and states why it is not addressed now.

**Gap 1 (Callback not wired):** Address. Add the vision callback branch to `route_callback_message`.

**Gap 2 (yaml.dump destroys comments):** Address. Use ruamel.yaml round-trip loader for comment-preserving writes, or use a targeted string-replacement approach that does not touch comment lines.

**Gap 3 (Hardcoded chat_id=6036):** Address. Replace default `chat_id=6036` with `int(os.environ.get("LOBSTER_ADMIN_CHAT_ID", "8075091586"))` in `dispatch_vision_proposals` and `handle_vision_callback`. The function signatures can keep `chat_id` as a parameter, but the default must use the env var.

**Gap 4 (Eligibility scope lacks logged prior for Dan-only fields):** Address or dispute. Either restrict eligible fields to `current_focus.*` (anchored by od-1), or log a decision in `oracle/verdicts/decision-vision-inlet-authority.md` citing a specific vision.yaml anchor and authorizing proposal-plus-confirm for structural fields.
