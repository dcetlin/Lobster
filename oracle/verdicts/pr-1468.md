## Stage 1 — Vision alignment

**Entering prior:** this implementation is solving the wrong problem, or solving the right problem in a way that forecloses better paths.

`vision.yaml current_focus` (updated_at 2026-05-31, ~34 days past its own 7-day staleness threshold) still lists in `what_not_to_touch`: *"New detection or classification rules — improve Orient routing before adding more detection."* Taken at face value, both #1463 and this PR add exactly that (a four-state classification taxonomy, staleness heuristics, auto-transition rules). I inherit the same judgment the prior oracle review of #1463 already reached on this point: the task context supplies a real (if informally logged) Dan directive to build the ratified global-canon proposal to a working state, and this PR is explicitly framed as *reconciliation* of already-authorized work, not new scope. I do not treat the stale `what_not_to_touch` entry as a fresh objection to this specific PR — but I note it is now stale across *two* PRs in the same area without correction, which is itself worth a premise-review entry (below), since a `current_focus` field that has been silently wrong through two full review cycles is drifting from "field-anchored" (success_criteria in vision.yaml) toward "decorative."

**Is this the right direction, given two competing implementations existed?** Yes, and the reasoning is sound on its own terms, not just because Dan's assessment doc said so. The assessment doc (`assessments/canon-reconciliation-20260704.md`) is a genuinely careful side-by-side: it verifies A's schema superiority (machine-readable `staleness_thresholds` vs. B's hardcoded, conflicting `30`-day literal), verifies B's meta/hygiene wiring is the *only* implementation anywhere of the proposal's "converge into a seed" valence-promotion mechanism, and verifies the dual-reconciler collision was real (not hypothetical — both processes already existed, live, with incompatible schemas). Collapsing two schema-incompatible live governance systems into one is a direct instance of `operating_principles.principle-4` ("Integration rate before new feature rate... wire what exists before building more") and of the golden pattern "No split canonical homes." This is the right problem and, structurally, the right direction.

**What this PR's core promise actually is, and whether Stage 2 confirms it:** the PR's stated goal is "exactly one writer cadence per artifact class instead of two." That promise is only as good as the correctness of the single writer it leaves in place. This is exactly why Stage 2's registry-id-shape check matters here more than it would in an ordinary PR: if the surviving single writer (`lobster-meta` Step 2.75) is itself broken in a way that corrupts the registry, the PR has not delivered on its central claim — it has just moved the collision from "two racing processes" to "one process duplicating its own data on every run," which is arguably a worse failure mode because it will look like organic registry growth (89 → 123 artifacts after one run) rather than an obvious dual-write collision, and will not be caught by the existing unit tests (which test `canon-digest.py` and `normalize-artifact-registry.py`, not `lobster-meta.md`'s prose — prose isn't unit-testable, which is itself the argument for finding #2 above). This is the concrete link between Stage 1 and Stage 2: the right architectural call, undermined by an implementation detail that defeats the architecture's own purpose.

**Opportunity cost / what shipping this as-is would foreclose:** if merged and run nightly before the id-matching bug is caught some other way, the registry gets 34 duplicate entries within 24 hours, at which point untangling "which of these two `lobster-meta` entries is real" becomes exactly the kind of manual forensic cleanup the whole canon-reconciliation effort exists to prevent needing. Catching it now, before merge, is categorically cheaper than catching it after the first corrupted nightly write.

## Stage 2 — Quality review

**Golden pattern citation and its effect on this review:** `golden-patterns.md`'s "Rule 3 — PathSelection/type discriminators get StrEnum" and "No split canonical homes" principle directly shaped what I checked. The PR's own `src/utils/artifact_registry.py` cites both patterns correctly for the *schema* constants (four-state enum, threshold defaults) — that part is genuinely well done. But the patterns' underlying concern — a value with a finite domain, or a piece of matching logic, must not have two independently-driftable homes — also applies to the *id-matching logic itself*, which the PR did not apply the same discipline to: `compute_job_diff` (Python, tested, fixed) and `lobster-meta.md` Step 2.75 (prose, untested, still broken) are two homes for the same operation, and they have already diverged. Without this pattern actively in mind, I would likely have stopped after confirming the Python-side fix and its regression test looked good, and would not have gone back to check whether the *same* fix needed to be mirrored into the prose file that performs the identical match. Checking that is precisely what surfaced the blocking finding.

**What I verified directly (not just from the PR's self-report), matching the specific scrutiny points in the task:**
- **(a) Migration 136 mechanics:** traced the heredoc/`mktemp`+`mv` pattern by hand. `uv run python3 - <<'PY136A' "$arg1" "$arg2"` is valid bash (heredoc redirection and trailing positional args can coexist in a simple command) and correctly produces `sys.argv[1]`, `sys.argv[2]` inside the quoted (non-interpolated) heredoc. The enable/absent-guard logic (`d.get('jobs',{}).get('canon-reconciler',{}).get('enabled')` truthy-gates the disable branch; membership check gates the canon-digest-add branch) correctly handles "already disabled," "never existed," and "already added" as no-ops — confirmed against the live `jobs.json`, which currently has `canon-reconciler: enabled=true` and no `canon-digest` key, i.e., exactly the state Migration 136 is designed to transform. `bash -n scripts/upgrade.sh` passes (confirmed independently, not just taking the PR's word). The agent's own disclosure that it did not run `upgrade.sh` end-to-end is accurate and appropriately flagged in the PR body — I could not run it end-to-end either without mutating this machine's real cron/jobs.json, so this remains a residual, disclosed, low-but-nonzero risk rather than a fully closed one.
- **(b) Is the retired reconciler fully de-fanged?** Yes, via the correct mechanism: `scheduled-tasks/dispatch-job.sh` (confirmed by reading it directly) checks `jobs.json`'s `enabled` flag and exits silently before any subagent is spawned when `enabled: false` — this matches CLAUDE.md's documented Type A architecture ("cron + jobs.json enabled field is the correct dispatch gate... runtime enable/disable lives in jobs.json without touching cron"). Migration 136 only needs to flip that flag, which it does; it does not need to touch any crontab line for `canon-reconciler` itself, and correctly does not attempt to. One residual point worth flagging as an operational note, not a code defect: the live `jobs.json` on this machine still has `canon-reconciler: enabled=true` right now (Migration 136 hasn't run yet), so the dual-write risk this PR exists to close is **not yet closed** until `scripts/upgrade.sh` is actually run post-merge — and separately, unlike the migration, the `lobster-meta.md`/`lobster-hygiene.md` prompt changes take effect immediately on merge (no migration needed, per CLAUDE.md's "editing files here is immediately live" note), so the blocking Step 2.75 bug above would fire on the very next nightly run regardless of whether `upgrade.sh` has been run yet.
- **(c) Migration 135 / normalizer idempotency:** ran the actual test suite from a fresh clone of the PR branch (`git fetch origin pull/1468/head`), not just trusting the PR's self-reported numbers: `uv run pytest tests/unit/test_scheduled_tasks/test_canon_digest.py tests/unit/test_scripts/test_normalize_artifact_registry.py -v` → 18 passed, matching the PR's claim exactly (12 in `test_canon_digest.py`, 6 in `test_normalize_artifact_registry.py`, hand-counted and confirmed). `uv run ruff check` on all five touched Python files → clean, confirmed independently. The normalize function's own logic is sound: pure function, never mutates `data` in place, backfills only, preserves existing `artifacts` field values untouched (explicitly tested), correctly folds B's flat schema into `_meta`. One untested edge case (a file with `_meta` present *and* leftover B-schema keys simultaneously) would silently leave the B keys in place forever, since the fold condition requires `_meta not in result` — low likelihood given how the two schemas actually diverged in practice, not blocking.
- **(d) Step 2.75 prose unambiguity:** this is where the blocking finding was found — see above. Everything else in Step 2.75/2.76/Step 2c reads clearly: threshold-from-registry (not hardcoded) is correctly instructed and matches CANON.md's 60/60/2 values; the human-gate language in both Step 2.75 (auto-transition only for the one explicitly-specified expiry case) and Step 2c (explicit "CRITICAL: Do NOT execute" quarantine gate, "Dan decides; you surface candidates only" for graduation) is unambiguous and consistent with the codebase's existing HYPOTHESIS-graduation posture. `max-turns` increases (15→18, 8→10) are reasoned in the PR body and include explicit "yield remaining budget" language for both new steps, addressing the turn-budget gap the prior `pr-1463` review flagged.
- **(e) Other registry-id-shape assumptions:** the one found (above) is the only one of consequence I could locate; `normalize-artifact-registry.py` and `canon-digest.py` do not make any further id-shape assumptions beyond the one already fixed in `compute_job_diff`.

**Direct live edits to `CANON.md`/`artifact-registry.json` (out-of-band, not repo-tracked) — sound or risky?** Sound, on balance, and better-reasoned than a default "just don't do out-of-band edits" rule would produce. These files are explicitly workspace runtime data per CLAUDE.md's Key Directories section (not trackable in this diff at all), and the edits made — correcting two known-bad cluster entries into 18 real per-job entries, marking `canon-reconciler`'s own registry entry `orphan`, updating `CANON.md`'s prose sections — are exactly the kind of one-off data corrections that `Migration 135`/`136` are not designed to make (they normalize *shape*, not *content accuracy*). The PR explicitly and correctly draws the line at the higher-risk operation: it did **not** hand-edit the live `jobs.json` `enabled` flag or crontab directly, deferring that specifically to the reviewable, idempotent Migration 136 path rather than an unreviewable subagent-session edit. That is the right split. I independently confirmed the live registry now has 89 artifacts / 34 correctly-shaped `scheduled_job` entries (matching the PR's 34/65 coverage claim) and that `jobs.json` still shows `canon-reconciler: enabled=true` / no `canon-digest` entry, consistent with "migration not yet run."

**Encoded Orientation check (constraint-3):** this PR changes durable, no-Dan-in-the-loop agent behavior (new classification/detection logic in two agents' processing sequences), so it is an Encoded Orientation decision. A prior logged decision exists in substance — `oracle/verdicts/pr-1463.md` plus this PR's own `assessments/canon-reconciliation-20260704.md` — but as with #1463, no `vision.yaml` field was updated to anchor the override of `what_not_to_touch`'s "no new detection/classification rules" line. I'm treating this the same way the prior review did: a real, secondary gap, recorded to premise-review, not the primary block (the primary block is the id-matching defect above).

**What would break without the key decisions made here:** nothing — the two live implementations keep colliding as already documented. **What would break by merging as-is:** the registry gets 34 duplicate entries on the next nightly `lobster-meta` run, which is a *new* corruption mode this PR did not have before it existed, worse in one respect than the pre-PR state because it is silent (looks like organic growth, not an obvious two-process race) rather than loud.
