## Stage 1 — Vision alignment

**Entering prior:** this implementation is solving the wrong problem, or solving the right problem in a way that forecloses better paths. I read vision.yaml and the ratified proposal before touching the diff.

`vision.yaml current_focus` (updated_at 2026-05-31 — already 34 days stale against the file's own declared 7-day staleness threshold for `current_focus`) lists in `what_not_to_touch`: *"New detection or classification rules — improve Orient routing before adding more detection."* This PR adds exactly that: a four-state classification taxonomy (seed/cadence/active_wip/orphan), staleness-detection heuristics (2x schedule period for cadences, 30-day threshold for active_wip), expiry-driven auto-transition rules, and unregistered-artifact detection scanning — bolted onto two existing agents. Taken at face value, this PR is doing the thing current_focus says not to do.

I do not treat this as dispositive on its own, for two reasons the task context and workstream logs supply: (1) the task prompt states this is recovery of a proposal Dan explicitly ratified, and (2) `workstreams/canon-build/log.md` records Dan's verbatim directive — "build the global canon to a working state, not a proposal doc... just do it and get it good enough" — which is a real, if informally logged, override. Per constraint-3's Encoded Orientation check, I looked for a prior logged decision and a vision.yaml anchor: the workstream logs supply the former (informally — no entry in `meta/premise-review.md` or `oracle/verdicts/` predates this PR for this specific proposal), but there is no vision.yaml anchor update reflecting the override of the `what_not_to_touch` item, and `current_focus` was never refreshed to reflect that this work is now in-scope. This is a real but survivable gap — I am not blocking on it alone — but it means the system currently holds a stale, contradicted `what_not_to_touch` entry that should be corrected regardless of this PR's disposition (flagged separately below as a premise-review item).

**What would have to be true for this to be the right path:** that the "global canon" gap the proposal diagnoses is real (it is — the proposal's own inventory work is careful and the gaps it names, e.g. 27/38 workstreams with no README+log, are independently verifiable) AND that this specific implementation is the only one being built. The second condition is false: a parallel session built and shipped a working alternative (CANON.md + canon-reconciler + a differently-shaped registry) in the same window, and this PR's own workstream README flags the overlap as an open question rather than a resolved one. That means the actual decision this PR represents — "extend lobster-meta/hygiene in place" vs. "stand up a dedicated canon-reconciler job" — was never actually decided; two different agents made two different architectural choices for the same directive and neither was reconciled before this PR requested review. This is the central Stage 1 finding: not that the problem is wrong, but that this PR does not know it is one of two competing answers to the same problem, and shipping it without resolving that foreclosis the ability to reason cleanly about which design is canonical — the exact class of problem the proposal itself was written to fix.

**Opportunity cost / what this forecloses:** if merged as-is, the system carries two artifact registries with different schemas and two reconciliation cadences, which is strictly worse than the pre-PR state (one ungoverned system) for exactly the failure mode the proposal names: "the same concept could silently live in two places." Fixing that after merge (once nightly/weekly runs have both mutated the shared file on different cadences) is materially harder than fixing it now, before either process has touched the file.

## Stage 2 — Quality review

**Golden pattern citation and its effect on this review:** `golden-patterns.md` — "Principle: canonical placement must be obvious from first encounter" (2026-04-25) — states "No split canonical homes: If something could plausibly live in two places, that ambiguity is the structural problem... Documentation is not a fix." This pattern directly named the failure I was looking for and changed what I checked: instead of stopping at "is the JSON schema-valid and is the migration idempotent" (both true), I went and checked whether `data/artifact-registry.json` already existed on disk with different content, and whether any other job already wrote to that path. Without this pattern actively in mind I would have treated the migration's `if [ ! -f ]` guard as sufficient evidence of safety and not gone looking for a live competing file — which is exactly where the blocking finding was. The pattern's own text ("No split canonical homes... the ambiguity is the structural problem") is what this PR violates: the registry itself now has two live homes, which is a first-order instance of the class of problem the pattern (and the proposal it feeds) names.
