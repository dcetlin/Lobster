### Phase 3 Monitors — Implementation Quality

**`check_dark_pipeline`:** Correct implementation. Opens raw sqlite3 connection (not via Registry abstraction), but this is acceptable for a read-only health-check script — minimal coupling to the domain layer. Proper error handling, ISO timestamp parsing with Z→+00:00 fix, clean return semantics (None = healthy).

**`check_ready_queue_drain`:** Correct logic. Counts new entries into ready-for-executor queue and drain events (from_status = 'ready-for-executor') in the observation window. Alert fires on `new_ready_count > 0 and drain_count == 0`. Clean implementation.

**`check_issue_rate_trend`:** Uses `gh issue list` with `--state open --search "created:>={cutoff}"` for opened count and `--state closed --search "closed:>={cutoff}"` for closed count. The "opened" metric captures issues created in the window that are still open (net new open issues), not total issues opened — this is a reasonable proxy for issue accumulation. The `--limit 500` cap could undercount for very active repos, but is appropriate for dcetlin/Lobster's scale. Graceful fallback when gh CLI is unavailable.

**Wiring into `run_health_check()`:** All three monitors follow the same pattern as Phase 1 alerts: check → log → `_write_inbox_alert()`. Phase 3 alerts pass `[]` for `uow_ids` (the first parameter), which creates inbox messages with `"stale_uow_ids": []` — functionally correct but semantically misleading field name. Minor.

**Constants:** All threshold values are module-scope named constants (`DARK_PIPELINE_THRESHOLD_DAYS`, `READY_QUEUE_DRAIN_WINDOW_MINUTES`, `ISSUE_RATE_WINDOW_DAYS`, `ISSUE_RATE_ALERT_RATIO`, `ISSUE_RATE_REPO`). This follows the learnings.md pattern requiring named constants for time-window comparisons (PR #968).

### Orphan-Exit Fix — Implementation Quality

**`maybe_fail_wos_uow`:** The function defines `_WOS_UOW_EXECUTOR_PREFIX = "wos-uow_"` inside the function body for the guard check, then uses module-scope `WOS_TASK_ID_PREFIX = "wos-"` for the slice operation. The guard narrows to executor task_ids only (excluding wos-diagnose-*, wos-surface-*); the slice strips the common "wos-" prefix to recover the raw uow_id. This is correct logic but the local constant definition inside the function body follows the pattern flagged in learnings.md PR #967 ("gate frozenset defined inside a function body is re-allocated on every call"). Promote `_WOS_UOW_EXECUTOR_PREFIX` to module scope.

**Path resolution fragility:** The function imports `REGISTRY_DB` from `orchestration.paths` (module-level constant, frozen at first import) for the DB existence check, then creates `Registry()` with no args (which re-reads `REGISTRY_DB_PATH` env var at call time). If `orchestration.paths` was imported before the env var was patched in tests, the existence check uses the frozen value while `Registry()` uses the patched value — a potential path mismatch. This is the learnings.md PR #839 pattern. In the test, the `patch.dict(os.environ, {"REGISTRY_DB_PATH": ...})` may or may not be effective for `REGISTRY_DB` depending on import ordering. The function should use `Registry()` path resolution consistently rather than mixing two different resolution mechanisms.

**Hook integration:** The bare `except Exception: pass` in `require-write-result.py` is acceptable — the hook must never block the agent exit path, and `maybe_fail_wos_uow` already handles exceptions internally with logging.
