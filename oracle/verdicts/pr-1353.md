### Guard condition analysis (engineer's explicit flag)

**Guard 1: 0-UoW check for wos-registry.db**

The inline Python uses `sqlite3.connect` + `SELECT COUNT(*) FROM uow_registry` with `except Exception: print(-1)`. This is the exact pattern from Migration 86 (lines 2974-2991 in upgrade.sh) which addresses the same file for the same reason. The `-1` sentinel routes to "could not read — skip" which is the conservative path. If the table does not exist, SQLite raises `OperationalError` (a subclass of `Exception`), caught correctly, returning -1. If the DB file is locked or unreadable, `sqlite3.connect` or `execute` raises, also caught. The only removal trigger is the string `"0"` in the count output — all other outcomes are explicit skips. `2>/dev/null` suppresses stderr from the invocation, preventing noise in migration output. This is correct.

**Guard 2: 0-byte check for wos.db and registry.db**

`[ ! -s "$file" ]` returns true when the file is empty (zero-size). This pattern is used 9+ times in upgrade.sh for similar guards. It is correct bash POSIX semantics: `-s` is true when file exists and size > 0; `! -s` is true when file is zero-size. The guard only fires after the `[ -f "$file" ]` check confirms file existence. This is correct.

**Idempotency:** Each of the three sub-steps checks `[ -f "$file" ]` first. If the file is already absent, the step logs "not present — skipping" and continues. Re-running the migration after files are removed produces only skip messages. Correct.

**Non-destructive skipping:** Non-empty files produce a substep warning and skip without removal. Data loss is structurally prevented for all three files. Correct.
