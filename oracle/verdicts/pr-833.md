### Stage 1: Vision Alignment (formed before reading implementation)

**Adversarial prior:** This implementation is solving the wrong problem, or solving the right problem in a direction that forecloses better paths.

**Theory of change under test:** PR #833 implements "WOS Phase 3" — a routing classifier, conditional hook system, and intake wiring. The claim is that this infrastructure is the right next step for the WOS substrate.

**What vision.yaml says:**

- `current_focus.current_constraint.statement`: "Active constraint is the WOS bidirectional interface (#1118)"
- `current_focus.horizon.next`: "Complete WOS bidirectional interface (#1118). Verify completion notification delivery end-to-end."
- `current_focus.horizon.after_that`: "Orient implementation (#733) — next structural investment once WOS execution loop is fully closed."
- `principle-4`: "Integration rate before new feature rate — Wire what exists before building more."

The PR does not address the stated current constraint (#1118) or the stated next horizon item (#733). It introduces new routing infrastructure for "WOS Phase 3" which is not named in any current_focus field. This is the potential misalignment: the system already has WOS execution running; the priority is closing the bidirectional interface loop, not adding new classifier infrastructure.

**What would have to be true for this to be the right path:** The existing WOS execution loop would need to be lacking a routing classifier that is causing real operational problems — UoWs being routed incorrectly in a way that impedes the active executor. If the classifier is a prerequisite for the bidirectional interface or completion layer, this is warranted. But the PR description does not claim this.

**What this forecloses:** The adversarial scenario is that this PR adds infrastructure parallel to existing infrastructure (routing classifier already exists in production as `routing_classifier.py`, already wired into `registry.py`), creating two classifier codepaths. This forecloses clean future routing by adding a second, unwired implementation alongside a working one.

### Stage 2: Quality Review

After reading the implementation, the Stage 1 concern is confirmed and becomes a blocker. Three gaps identified:

---

**Gap 1: Duplicate routing classifier — NEEDS_CHANGES (blocker)**

`src/orchestration/routing_classifier.py` already exists in production (198 lines) and is already wired into `registry.py` via a `from .routing_classifier import classify_posture` call inside `Registry.upsert()`. PR #833 introduces `src/orchestration/classifier.py` (194 lines) that does essentially the same thing: loads `~/lobster-user-config/orchestration/classifier.yaml`, applies first-match-wins rules, returns a typed result.

The two modules have the same external interface (same config file path, same rule evaluation semantics, same posture/route_reason output), but they are not the same module. This is the PR #714 learnings.md failure pattern: "A new module with 733 additions and 0 deletions, with no import of the new module in any existing file, is a library with no wiring." Applied here: `classifier.py` and `classify_intake.py` have zero production callers in the current codebase. The PR description says "wires classifier into UoW intake path without modifying registry.py" — but not modifying registry.py means the new classifier is not called at all from the production path. The production path calls `routing_classifier.classify_posture()` via `registry.py`. The new `classify_and_register()` in `classify_intake.py` requires the caller to invoke it manually after `Registry.upsert()` returns `UpsertInserted` — there is no such caller.

The PR introduces a parallel implementation of something that already exists and is already wired, without replacing or integrating with the existing implementation. This is not the seam-first pattern from golden-patterns.md — that pattern adds a named abstraction at a seam where future change will be needed, but places the implementation behind the existing caller. This PR adds a parallel implementation behind no caller.

Resolution: Either (a) merge classifier.py into routing_classifier.py (or replace routing_classifier.py with classifier.py) and wire it at the existing call site in registry.py, or (b) document the explicit architectural decision to have two classifier modules and explain what each is for. Currently there is no such documentation.

**Gap 2: Migration number collision — NEEDS_CHANGES (blocker)**

The PR adds `src/orchestration/migrations/0009_wos_phase3_classifier_hooks.sql`. Migration `0009_heartbeat_locking.sql` already exists in production at `~/lobster/src/orchestration/migrations/0009_heartbeat_locking.sql`. This is the exact failure pattern named in learnings.md (2026-04-27, #1000): "Migration number collision between simultaneous PRs produces silent feature deletion. The migration runner skips versions already in `_migrations`. When the second PR merges, its migration file is silently skipped — the feature's DB table is never created." The consequence: if this PR merges as-is, the four new columns (`hooks_frozen`, `retry_count`, `classifier_thrash`, `rule_name`) will never be added to `uow_registry` because migration 0009 is already marked as applied. The hooks system will fail silently at runtime (column not found) or fall back to the `except` handlers.

The learnings.md entry for this failure explicitly states: "When two PRs are in concurrent oracle review, the oracle should flag migration number conflicts as a NEEDS_CHANGES blocker regardless of which merges first, since merge order cannot be guaranteed." The migration must be renumbered to 0027 (the next available after the current highest, 0026).

Resolution: Rename the migration file to `0027_wos_phase3_classifier_hooks.sql` (or the correct next number in sequence) and ensure the migration runner references the new name.

**Gap 3: Raw string literals in SQL for status exclusion — advisory**

In `classify_intake.py`'s `get_active_summary()`:

```python
NON_TERMINAL_STATUSES = ("done", "failed", "expired")
placeholders = ",".join(f"'{s}'" for s in NON_TERMINAL_STATUSES)
```

This tuple uses raw string literals for enum-backed `UoWStatus` values, and then interpolates them directly into SQL. This violates the StrEnum golden pattern (golden-patterns.md, 2026-04-24): "WHERE status = 'active' is a latent bug; WHERE status = UoWStatus.ACTIVE is correct." Additionally, the `UoWStatus` enum has additional terminal values: `UoWStatus.CANCELLED`. The `NON_TERMINAL_STATUSES` tuple omits "cancelled" from its exclusion list, meaning cancelled UoWs will appear in the active summary alongside genuinely active UoWs. The existing `UoWStatus.is_terminal()` method already encodes the correct terminal set including CANCELLED — this function should use that method or the enum directly rather than a local raw-string tuple.

This is advisory rather than a blocker because `get_active_summary()` is a read-only query path with no production caller yet, but it will produce incorrect results when it is called.

Resolution: Import `UoWStatus` from `registry.py` and build the exclusion list from `UoWStatus.is_terminal()` or from the enum values directly. Use parameterized SQL (`WHERE status NOT IN (?, ?, ?, ?)`) rather than f-string interpolation of the status values.

**Gap 4: loop-guard fires but does not suppress the retry-on-failure hook's requeue action — advisory**

In `apply_hooks()` in `hooks.py`, when loop-guard fires (count >= 3), `_freeze_hooks()` is called to set `hooks_frozen=True` in the DB. However, at this point, `_hook_retry_on_failure()` has already been called and may have already called `_requeue_uow()` to set status back to 'proposed'. The sequence in `apply_hooks()` is:

1. `_hook_retry_on_failure(uow_id, event, db_path)` — this increments `retry_count` AND calls `_requeue_uow()` if `new_count < _MAX_RETRIES`
2. `_hook_loop_guard(...)` — this checks count AFTER step 1's side effects, then freezes

So the retry requeue has already happened before loop-guard freezes. Loop-guard prevents future hook firings but cannot undo the requeue that just occurred. This means a UoW that triggers loop-guard can still be requeued one additional time during the loop-guard-triggering cycle, effectively allowing `_MAX_RETRIES + 1` requeues before freezing.

This is advisory because the test (`test_loop_guard`) seeds the DB with 3 occurrences of `retry-on-failure` in `hooks_applied` and then calls `apply_hooks` — but because `_increment_retry_count` reads from `retry_count` (a separate integer column), not from `hooks_applied`, the test's `hook_count=3` in `hooks_applied` doesn't actually exercise the `new_count >= _MAX_RETRIES` branch. The test passes but doesn't verify whether the off-by-one requeue issue exists at `retry_count` level.

**Encoded Orientation check (OODA constraint-3):**

The hook system introduces durable behavioral defaults: `retry-on-failure` will re-queue failed UoWs up to 3 times, `loop-guard` will freeze hook evaluation. These are Encoded Orientation decisions — the system will act without Dan's explicit input. Checking for a prior logged decision: no prior in `oracle/verdicts/` or `meta/premise-review.md` specifically authorizing a retry-on-failure hook with a hardcoded cap of 3. The closest anchor is vision.yaml principle-1 ("Proactive resilience over reactive recovery") but the specific behavioral default (re-queue on failure up to 3 times) is not logged. Gap 1 (duplicate classifier, no production wiring) means this hook system has no production effect yet, so the urgency is lower — but if merged and wired, this would be an Encoded Orientation decision without a logged prior.

**Patterns introduced:**

- The dual-classifier pattern (two modules doing the same thing from the same YAML) will propagate if not resolved — future contributors will not know which module is authoritative.

The seam-first pattern from golden-patterns.md requires the abstraction to be placed at the existing call site, not deferred to a future caller.
