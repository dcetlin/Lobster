## Stage 1: Vision Alignment

**Reviewed before seeing implementation.**

**Theory of change:** The vision's `core.inviolable_constraints.constraint-4` states "minimize metabolic cost of cybernetic engagement." A subagent running 202 turns is a direct, concrete metabolic cost violation. GitHub issue #742 (authored by Dan) explicitly names the behavioral gap ("No max_turns constraint on subagents dispatched for exploratory or open-ended work") and the goal ("Fail fast with a partial result rather than running to exhaustion"). The direction of this work — bounded turn caps per executor type, with per-artifact override — is directly traceable to constraint-4 as the vision anchor.

**What would have to be true for this work to be wrong?** If the real problem is Steward prescription quality rather than missing turn caps, bounding agents at the dispatch layer would mask the symptom (runaway sessions) without addressing the cause (poorly scoped prescriptions). This is a genuine possibility: a prescription that says "explore all of X" will still exhaust 30 turns and exit with a partial result, which may or may not be useful. However, the PR explicitly acknowledges this boundary — Steward generation logic is untouched, and the Steward can embed explicit `max_turns` values when needed. This is a transparent two-stage rollout, not a claim that caps solve the underlying prescription problem.

**What does this foreclose?** Nothing. The override path (`artifact.max_turns`) preserves full flexibility for any executor type. The per-type defaults are a safety net, not a ceiling.

**Alignment verdict: Confirmed.** The work serves constraint-4 directly, is authorized by a Dan-authored issue, and does not close off any future direction.

**Learnings.md prior-pattern check:**
- Mirror-constant check (PR #1116, #1408 learning): `TestExecutorMaxTurnsResolution` in the test file re-implements the resolution expression inline rather than calling through a helper. However, the constants (`_DEFAULT_MAX_TURNS`, `_FALLBACK_MAX_TURNS`) are imported from production — not re-declared locally. The inline expression is the same conditional as the production code, testing the logic without a function abstraction to import. This is on the edge but acceptable: the constants are correctly imported; only the expression form is repeated. The pattern is not the same severity as declaring local constant values that could diverge.
- Encoded Orientation check (constraint-3): `_DEFAULT_MAX_TURNS` establishes durable per-type defaults that gate dispatch behavior without Dan's per-dispatch input. No entry exists in `oracle/decisions.md` or `data/decisions-ledger.md` for this behavioral change. Mitigating factors: (a) issue #742 is a Dan-authored explicit authorization for the behavioral goal; (b) the `frontier-writer` and `design-review` types with new defaults are stub dispatchers with no active production UoWs; (c) constraint-4 is the traceable vision anchor. The strict constraint-3 reading requires a decisions file entry, not only a GitHub issue. This is noted below as a named gap — not a blocker given the mitigating factors, but the decision record is absent.

## Stage 2: Quality Review

**Mode: VERIFICATION — code with tests and an external standard (pytest, ruff).**

**Test results:**
- `test_max_turns_cap.py`: 30/30 passed
- `test_executor_subprocess.py` (excluding pre-existing failure): 17/17 passed

**Structural correctness:**

The `to_frontmatter` / `from_frontmatter` round-trip is correct. `max_turns` is omitted from the envelope when `None` or absent — backward-compatible with existing artifact files that have no `max_turns` key.

`from_json` adds `"max_turns"` to the `known` set correctly. Existing artifact files without the field deserialize cleanly.

`_parse_workflow_artifact` in steward.py handles empty string, missing field, and non-integer values by returning `None` — correct fallback behavior.

The `try/except TypeError` in `_run_execution` for inbox dispatchers is appropriate: it handles the deferred wiring case without breaking production behavior. The fallback is explicit and the comment explains why.

`_dispatch_via_claude_p` and `_dispatch_via_stub` both default to `_FALLBACK_MAX_TURNS` when `max_turns=None` is passed. This is correct — the caller passes `None` when the artifact has no explicit cap and the type-default resolution happens before the call.

`wos-write-artifact.py`: CLI arg priority over parsed prescription value is the correct precedence order. The `effective_max_turns` variable is clean and readable.

**Named gap: Missing decisions file entry for `_DEFAULT_MAX_TURNS` behavioral default change.**

The `_DEFAULT_MAX_TURNS` dict encoding 30-turn defaults for `frontier-writer` and `design-review` is a durable behavioral default change that satisfies the Encoded Orientation conditions under constraint-3 (acts without Dan's real-time per-dispatch input; changes a durable default in the dispatch pipeline). The strongest mitigating factors are: (a) issue #742 is a Dan-authored explicit authorization; (b) both affected types are stub dispatchers with no active production UoWs today; (c) constraint-4 is the traceable vision anchor. On balance, the decision to approve without a decisions file entry is defensible given (a) and (b). However, the strict constraint-3 path requires a logged prior in `oracle/decisions.md` or `data/decisions-ledger.md`. The gap should be addressed as a follow-on in the same day (add an ADR entry) rather than a NEEDS_CHANGES blocker.

**Decision:** Approve as-is. The missing ADR is technical debt, not a correctness issue — the behavioral change is authorized by Dan's issue and affects stub-only dispatch paths today. Escalating to NEEDS_CHANGES for this gap would require a decision record round-trip without adding material safety for production.

**Patterns introduced:**
- `_OPTIONAL_SCALAR_ENVELOPE_FIELDS` as a separate tuple from `_CHAIN_ENVELOPE_FIELDS` in `workflow_artifact.py` — clean extension point for future scalar fields.
- `_DEFAULT_MAX_TURNS` / `_FALLBACK_MAX_TURNS` as named module-level constants — importable by tests, no magic numbers at dispatch sites.
- `try/except TypeError` at the dispatcher call site as a forward-compatibility shim — explicit and documented.

**What this makes easier:**
- Prescriptions can now embed explicit turn caps for known-expensive UoWs.
- Future per-type tightening only requires an entry in `_DEFAULT_MAX_TURNS`, not a grep-and-replace across dispatch sites.
- The `--max-turns` CLI arg on `wos-write-artifact.py` enables operator-level override without code changes.

**What this makes harder:**
- Nothing. The override path preserves full flexibility.
