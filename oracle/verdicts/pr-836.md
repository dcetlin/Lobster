## Stage 2: Implementation Quality

### Blocker: Migration number collision

The PR adds migrations labeled "Migration 83" and "Migration 84." Both numbers are already taken on `main`:

- Migration 83 on main: adds cron entries for `wos-health-check` and `wos-metabolic-digest` (line 2900 of upgrade.sh)
- Migration 84 on main: registers the `wos-execute-gate.py` PostToolUse hook (line 2923 of upgrade.sh)

The current highest migration on main is **Migration 122**. The PR branch was cut from a state where these numbers were available (committed 2026-04-22), but main has since advanced by ~40 migrations.

This is the exact failure mode documented in learnings.md (PR #1000 and PR #1105): when two PRs claim the same migration number, the later-arriving migration is silently skipped by the migration runner. The backwards-compatibility `try/except` pattern in upgrade.sh makes the skip undetectable at runtime — no crash, no log, the crontab entries never get rewritten, the feature is permanently disabled with no signal.

The PR description explicitly notes this is a "large PR (1000+ lines)" but the diff is only 178 additions — the underlying stale-branch reality is that the functional content is small but the merge base is very old. The merge state is `CONFLICTING` (confirmed via `gh pr view --json mergeable,mergeStateStatus`). This is a rebase requirement, not a code defect.

**Required fix:** Rebase onto current main and renumber the two migrations to the next available numbers after Migration 122 (i.e., 123 and 124). Verify after rebase that no open PR claims those numbers.

### Secondary finding: Migration 84 is a stub — numbered but empty

Migration 84 in the PR is entirely commented out. Its function is to document a deferred Phase 3 step. A commented-out migration body is correct design (the PR description explains this clearly), but if the migration runner has a counter that checks "did migrated increment," a stub with no `migrated=$((migrated + 1))` will silently count as skipped rather than counted. This is cosmetic — the stub's purpose is documentation — but the numbered migration slot is occupied by content that produces zero observable effect on upgrade. After renumbering, consider whether this stub warrants its own migration number or can be documented as a comment within Migration 123's body.
