**Prior entering review:** This implementation is solving the wrong problem, or solving the right problem in a direction that forecloses better paths.

The foundational question is whether teaching the health daemon about `quota_wait` as a suppression-worthy state is the structurally correct fix, or whether the real fix is a different architecture (e.g., the health daemon should query quota state rather than enumerate lifecycle states).

Evidence that this is the right problem: `quota_wait` was already a first-class state in the health daemon's main `case` block (line 2131), where it correctly suppresses all restart logic. The heartbeat suppression elif at lines 2284–2289 is a separate control-flow gate that runs after the main case and was simply not updated when `quota_wait` was added to the system. This is a narrow oversight in a list-based guard — not a fundamental design gap. Adding `quota_wait` to that list is the minimal structurally correct fix. A different architecture (querying quota state differently) would be a premature generalization for a single-line omission.

## Stage 2 — Quality Review

elif [[ "$lobster_mode" == "starting"    || "$lobster_mode" == "restarting" || \

        "$lobster_mode" == "stopped"     || "$lobster_mode" == "quota_wait" ]]; then

Whitespace padding is cosmetic alignment, not functional. The trailing spaces before `||` are consistent with the pre-existing style in this elif. No syntax risk.

### Exact mode string match

**Pass.** `claude-persistent.sh` line 722 writes `write_state "quota_wait" "..."` verbatim. The health check reads this via `read_lobster_mode()`. The string `"quota_wait"` in the elif matches exactly. No underscore/hyphen confusion, no case mismatch.

### Mirror-constant risk

**Pre-existing, not new.** The test file `test-health-check-dispatcher-heartbeat.sh` declares `DISPATCHER_HEARTBEAT_STALE_SECONDS=1800` on line 58 rather than sourcing it from the script. This is a structurally independent copy — if someone changes the script constant without updating the test, the boundary tests (Tests 2, 3, 7, 8) will pass against the wrong threshold. The named golden pattern (2026-06-03: "named display cap with aggregate-preserving header" / "named constants dict") calls this out as a risk. However:

1. This structure predates the PR (line 58 previously said 1200).
2. The PR updated both copies consistently to 1800.
3. The pre-existing risk is the same as it was before.

This is a known structural debt, not a new defect introduced by this PR. No NEEDS_CHANGES warranted.

### The circular revert comment

**Observation, not a blocker.** The threshold comment reads: "Revert to 1200s once quota_wait mode correctly suppresses heartbeat checks in production."

This condition is satisfied by this same PR. Once it merges, the revert condition is immediately met. A maintainer reading this comment 6 months post-merge will be confused about what they're waiting for. The comment should say "Revert to 1200s — this buffer is no longer structurally needed now that quota_wait suppression is in place. Kept as observational margin pending confirmation in first quota_wait event post-deploy." But this is a low-severity documentation imprecision, not a correctness issue. The comment's date stamp (2026-06-05) gives it a decay signal.

Filed as a documentation observation, not a blocker. The threshold itself is correct: 1800s covers the Jun 4-5 observed worst-case compaction + catchup window.

### Masking risk — could `quota_wait` suppress detection of a genuinely-hung dispatcher?

**No new risk.** The main `case` block at line 2131 already suppresses ALL restart logic when mode is `quota_wait`. The PR's change to the heartbeat elif is a catch in a downstream code path that runs after the case block. Any scenario where `quota_wait` masks a genuinely-hung dispatcher was already possible via the main case block — and was presumably accepted when that block was added. The elif suppression is additive, not a new architectural decision.

The specific scenario: state file shows `quota_wait` but dispatcher is genuinely hung (state file stale/corrupt). In this scenario: (1) all checks are already suppressed by the main case block — process checks, inbox drain, everything; (2) the heartbeat check was the only check that leaked through; (3) this PR closes that leak. The net effect: a genuinely-hung dispatcher in `quota_wait` state would previously have produced one RED (heartbeat stale), which was the source of 27 spurious false-positives. The Jun 5 event demonstrates the alert was a false-positive in production. The residual masking scenario (real hang + `quota_wait` state) is a legitimate theoretical concern but not new.

### Coverage of the actual false-positive scenario

No test directly exercises "mode=quota_wait AND stale heartbeat → suppressed" as an end-to-end path — this would require running `main()` in a full test environment — but the unit-level coverage of the individual components is sufficient for the scope of this change.
