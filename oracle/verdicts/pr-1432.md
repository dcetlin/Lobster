## Stage 1: Vision Alignment

**Prior entering this review:** This implementation is solving the wrong problem, or solving the right problem in a direction that forecloses better paths.

**Adversarial question:** Is a status guard the correct fix, or is the real defect that the router re-emits to the inbox at all?

The root cause as reported: the router calls `_dispatch_via_inbox(executor.py)` which WRITES A NEW `wos_execute` message to the inbox. This is by design — `_dispatch_via_inbox` is the canonical dispatch path for subagent spawning, and the router's job is to receive `wos_execute` messages and dispatch them by calling `_dispatch_via_inbox`. The re-emission is not a bug in the dispatch path; it is an intended side effect of correct dispatch. The bug is that the router has no awareness of whether the UoW is already being handled.

The question "should dispatch not round-trip through the inbox at all?" is a valid structural question — but answering it would require a larger architectural change: the router would need to use a direct subagent spawn rather than the inbox-write dispatch path, or the executor-heartbeat would need to directly spawn rather than writing to the inbox. These are larger changes that carry higher risk at a moment when WOS execution is paused and the substrate is being stabilized. vision.yaml principle-1 ("proactive resilience over reactive recovery") and principle-2 ("ergonomics over shortcuts") both favor the targeted guard over an architectural rewrite here. The current_focus constraint ("Do not resume execution_enabled until Stage 1/2 work is confirmed stable") supports a minimal, reversible fix rather than structural restructuring.

Does the status guard foreclose the "eliminate the inbox round-trip" path? No — it is additive. A future PR can remove the inbox-round-trip architecture and the status guard becomes redundant but not harmful.

Does the status guard address the loop's actual driver? Yes. The loop driver is: router dispatches already-executing UoWs because it has no registry awareness. The guard adds registry awareness. The fix is correctly targeted.

**Alignment verdict: Confirmed.** This is the right problem; the guard approach is the appropriate scope of intervention given the current operational constraint (WOS paused, substrate stabilizing).

**Patterns from oracle vocabulary that constrained this Stage 1:**

The "seam-first abstraction" golden pattern (2026-03-30) was consulted. The guard is placed precisely at the seam where the router's pure-file-I/O loop meets the registry's state. The three functions (`_DISPATCHABLE_STATUSES`, `_uow_status_allows_dispatch`, `_discard_inbox_message`) are named abstractions at that seam. This is the pattern applied correctly. It did not change my verdict but confirmed the structural choice is sound.

The "proactive resilience over reactive recovery" (vision.yaml principle-1) was the active prior that settled the architectural question. Without it, the right answer might be "fix the architecture." With it, the right answer is "add the guard now; the architecture can evolve." This constrained my Stage 1 toward confirming alignment rather than questioning it.

## Stage 2: Quality Review

### Does it do what it claims to do?

Yes. The guard fires before the claim step in `_route_single_message`. A UoW with status `executing` (or any non-`{active, ready-for-executor}` status) causes the message to be moved directly to `processed/` without dispatching. The implementation is structurally correct.

### `_DISPATCHABLE_STATUSES` correctness analysis

The set is `{UoWStatus.ACTIVE, UoWStatus.READY_FOR_EXECUTOR}`.

`READY_FOR_EXECUTOR`: Correct. This is the normal initial state when a `wos_execute` message is first written by the executor-heartbeat. First dispatch is legitimate.

`ACTIVE`: Requires careful analysis. The executor's dispatch sequence is:
1. Executor-heartbeat claims UoW: status `ready-for-executor` → `active` (SQL UPDATE)
2. Executor calls `_dispatch_via_inbox()` which writes the `wos_execute` message to inbox (Step 4, line ~948)
3. Executor calls `transition_to_executing()`: status `active` → `executing` (Step 8, line 992)

Steps 2 and 3 are sequential in the executor. The `wos_execute` message lands in the inbox while the status is still `active`. The router polls every 30 seconds. If the router's poll cycle happens in the window between step 2 and step 3, the status will be `active` — correctly permitted by the guard.

**Race window analysis:** The `active` window is the time between `_dispatch_via_inbox()` returning and `transition_to_executing()` completing — likely milliseconds on the executor side. The router's 30-second polling interval makes it extremely unlikely for the router to process the message during this window. If it does, the router dispatches, `_dispatch_via_inbox` writes another `wos_execute`, the executor then transitions to `executing`, and 30 seconds later the new message is blocked by the guard (status=`executing`). This is a worst-case double-dispatch for one UoW in an extremely narrow race window. Given the 30-second polling interval and the millisecond-scale `active` window, this race is acceptable — and the existing TTL/sweep recovery path handles any resulting duplicate subagent correctly.

Not including `ACTIVE` would create a correctness defect: the legitimate initial dispatch of a newly-claimed UoW would be blocked if the router happened to process the message before the executor completed `transition_to_executing`. Including `ACTIVE` is correct.

### Fail-open on DB error

The PR chooses fail-open (allow dispatch on registry read error) with this rationale: "a false-positive dispatch (re-routing an in-flight UoW) is visible and recoverable via the existing TTL/sweep path; a false-negative (suppressing a legitimate dispatch) would silently stall the UoW with no recovery signal."

This is internally consistent and correctly motivated. The TTL/sweep path (`reset_expired_claims` → `ready-for-steward`) handles the duplicate-dispatch case. A suppressed legitimate dispatch has no equivalent recovery — the UoW sits in `ready-for-executor` with its `wos_execute` message permanently discarded and no retry trigger.

**Does fail-open re-open the loop under DB trouble?** If the DB is persistently down (not a transient hiccup), every poll cycle will produce a DB error and the guard will pass through, dispatching repeatedly and writing new `wos_execute` messages — re-establishing the loop condition. However: (a) persistent DB failure is a systemic outage, not the scenario the guard is designed to survive; (b) at that point the entire WOS pipeline is broken, not just the router; (c) the warning log at each DB error provides a visible signal. This is an acceptable trade-off, and the existing fail-open design for the MAX_AGENTS_GATE establishes that fail-open is the established posture in this codebase for transient errors.

### `_discard_inbox_message` dropping legitimately-claimed messages

The function moves a message directly from `inbox/` to `processed/`. It runs BEFORE the claim step (`_claim_message`). This is correctly stated in the code comments ("The guard runs BEFORE claim so the message file is never moved to processing/ for duplicate messages"). The `src.exists()` check handles the case where another process has already claimed the message — it logs and returns without raising. If the file was claimed between the guard check and the discard, the `src.rename()` will fail with `FileNotFoundError` (on most filesystems, `rename` to a destination across different directories can raise `OSError` on certain conditions) or silently move the wrong thing — but this is caught by the `except OSError as exc` handler which logs a warning. The pre-claim ordering makes this function structurally safe.

One note: `Path.rename()` on Linux is atomic for same-filesystem moves. Since `inbox/` and `processed/` are both under `~/messages/`, they are on the same filesystem in all normal configurations. Atomic rename is the correct tool. This is consistent with how `_claim_message` works.

### Interaction with TTL/sweep recovery

TTL/sweep recovery fires in the executor-heartbeat via `reset_expired_claims()`, which resets UoWs from `executing` to `ready-for-steward`. This path is entirely independent of the `wos_execute` inbox message machinery — it queries the registry directly. The guard does not touch this path, and the TTL/sweep path does not interact with the inbox message queue. The PR's claim that TTL/sweep recovery is untouched is correct.

### Race between executor setting status=executing and router's read

Analyzed above in the `ACTIVE` status section. The race window is narrow (executor step 2 → step 3 is milliseconds); the 30-second router poll interval makes the race extremely unlikely; and the outcome of the race (double dispatch) is recoverable via TTL/sweep. This is not a blocker.

The tests cover:

- `test_executing_uow_message_discarded_not_dispatched`: integration test confirming the message moves to `processed/` and `_dispatch` is not called
- `test_executing_uow_does_not_write_alert`: confirms no spurious alert is generated
- `test_ready_for_executor_uow_is_dispatched`: confirms the legitimate dispatch path still works
- `test_mixed_inbox_only_executing_skipped`: confirms per-message discrimination in a mixed inbox

- `test_unknown_uow_blocks_dispatch`: covers the fail-closed for unknown UoW

**Gap:** There is no direct test of the `ACTIVE` status dispatch path in the loop integration tests (`TestStatusGuardInPollLoop`). The unit test `test_active_status_permits_dispatch` covers the guard function directly, and the `_uow_status_allows_dispatch` mock in `router` fixtures defaults to `True` for all statuses. But `test_mixed_inbox_only_executing_skipped` uses a side-effect that distinguishes by UoW ID rather than status, so it does not directly exercise the `active`-status-permits-dispatch path in the poll loop context. This is a minor coverage gap — the unit test covers it, and the poll loop integration test with `_uow_status_allows_dispatch.return_value = True` indirectly confirms dispatch proceeds. Not a blocker.

**Encoded Orientation check (constraint-3):** This PR adds a behavioral gate to the router — it changes which UoWs get dispatched. However, this is a bug-fix constraint (preventing dispatch of already-executing UoWs), not a new behavioral orientation. The OODA register is Reactive: the guard is a direct response to an observed failure mode (the loop), the fix is traceable to the empirical observation ("all three UoWs are status=executing"), and it changes behavior only in the failure state. The existing `execution_enabled` gate is the relevant Encoded Orientation decision; this guard operates within that gate (execution_enabled must be True for any dispatch to occur). Constraint-3 is satisfied.

### Patterns introduced

The PR introduces a clean instance of the "module-scope frozenset for status dispatch gating" pattern (established in golden-patterns.md 2026-04-26 for `ORPHAN_REASONS`). The three-function structure (`_DISPATCHABLE_STATUSES` / `_uow_status_allows_dispatch` / `_discard_inbox_message`) is a well-named triad at a clear seam. No patterns are introduced that would propagate problematically.

### What this makes easier / harder

**Easier:** Adding new non-dispatchable statuses requires only updating `_DISPATCHABLE_STATUSES` — one named frozenset at module scope, importable by tests. The seam is explicit and well-placed.

**Harder:** If a future PR changes when `transition_to_executing` is called relative to `_dispatch_via_inbox` (e.g., calling it before writing the inbox message), the `ACTIVE` entry in `_DISPATCHABLE_STATUSES` would become incorrect. This is a structural coupling between executor.py and the router's guard that is not documented. A code comment in `_DISPATCHABLE_STATUSES` noting "ACTIVE is included because executor.py calls _dispatch_via_inbox before transition_to_executing (step 4 before step 8)" would make this coupling visible and maintainable. This is advisory, not a blocker.
