## Stage 1 — Vision Alignment (written before seeing diff)

**Adversarial prior:** This implementation is solving the wrong problem, or solving the right problem in a direction that forecloses better paths.

**What the PR claims to address:** Oracle advisory S3P2-E from PR #708 — `outcome='retry'` and `dispatch_attempt>1` appear in schema definitions and docstrings but no code path ever produces these values. The PR opts for Option A: annotate the dead enum values as reserved rather than implement the retry loop.

**Theory of change interrogation:**

The PR title says "mark outcome='retry' as reserved in dispatch-boundary schema." The question entering Stage 1: is annotating dead schema values a valid path, or is it papering over a design gap that should be addressed by actually implementing the retry loop or by removing the reserved values entirely?

Three things would have to be true for annotation to be the right path:

1. The retry loop is genuinely deferred (not simply unimplemented due to oversight).
2. The schema should signal "this is coming" rather than silently accepting a narrower contract.
3. Annotating does not introduce misleading operational behavior — consumers querying for `outcome='retry'` would get zero results either way, so the annotation is cosmetic correctness, not behavioral.

All three hold given the PR context. The retry loop was specified in the original S3P2-E success criterion but not implemented — the PR's implementation note in the success criterion is an honest acknowledgment, not evasion. The schema documents what was specified; the annotation makes what was delivered explicit without deleting the future extensibility point. This is not papering over — it is the correct engineering posture for a deferred feature with a known gap.

The registry.py change (adding `issue_number is None` guard and converting the hardcoded NOT IN list to use `_TERMINAL_STATUSES_FOR_ISSUE_CHECK`) resolves the "declared-but-not-used synchronization frozenset" pattern named in learnings.md for PR #1003. This is a separate correctness fix bundled with the documentation update. The question is whether this bundling is the feature-bundling failure mode named in learnings.md (#1148).

**Pattern check — feature-bundling (learnings.md 2026-05-14, #1148):**

The PR description names two concerns: (1) schema annotation for `retry`/`dispatch_attempt`; (2) registry.py dedup fixes (`issue_number is None` guard + `_TERMINAL_STATUSES_FOR_ISSUE_CHECK` consolidation). These are from different workstreams conceptually — schema documentation vs. registry correctness — but the calibration note from #1161 applies: the bundling threshold is "distinct UoW workstreams" and "behavioral vs. non-behavioral." The registry fix IS behavioral (prevents duplicate UoWs from being created for `issue_number=None` callers), and it IS in a different concern space from the schema annotation. However, both are classified under the same WOS UoW reference (`uow_20260428_c36be3`) per the PR description. I will flag this for Stage 2 evaluation but the bundling is not severe enough to block on its own given the UoW reference.

**Encoded Orientation check:** This PR does not change behavioral defaults, agent identity, system constraints, or decision-making rules in a durable way. The executor and registry changes are correctness fixes and documentation updates. The Encoded Orientation gate does not fire.

**Vision alignment verdict:** Confirmed. ## Stage 2 — Quality Review (written after reading diff)

### What the PR does

**docs/wos-dispatch-failure-modes.md:** Schema table updated — `dispatch_attempt` documented as always 1 with values >1 reserved; `outcome` narrowed to `success|failure` with `retry` marked reserved. `failure_reason` description trimmed to remove the "or retry" clause.

**docs/wos-sprint3-part2-design.md:** Implementation note appended to the S3P2-E success criterion inline — acknowledges `retry` was specified but not implemented, with a pointer to the schema doc.

**src/orchestration/executor.py:** `_log_dispatch_boundary` and `_dispatch_via_inbox` docstrings updated to reflect actual contract — `outcome` is `success|failure` only; `retry` is reserved.

**src/orchestration/registry.py:**
- Adds `issue_number is None → ValueError` guard at the top of `_upsert_typed`, with an explanation of why: `WHERE source_issue_number = ?` silently returns no rows for NULL in SQLite, allowing duplicate UoW rows for the same issue.
- Converts the hardcoded `NOT IN ('done', 'failed', 'expired', 'cancelled', 'closed')` to use `_TERMINAL_STATUSES_FOR_ISSUE_CHECK` — the class-level frozenset that was previously declared but not referenced in this function (PR #1003 named pattern: "declared-but-not-used synchronization frozenset").

**tests/unit/test_orchestration/test_registry.py:** Two new regression tests covering the dedup scenarios.

### Correctness evaluation

**Schema documentation:** Correct and accurate. The changes in `wos-dispatch-failure-modes.md` precisely reflect what the code does. The removal of "or retry" from `failure_reason` description is consistent.

**executor.py docstrings:** Accurate. The `_log_dispatch_boundary` docstring now correctly describes the `dispatch_attempt` and `outcome` parameters. The note that `retry` is reserved and no code path produces it is verifiable — the PR completion check includes a grep to confirm this.

**registry.py — issue_number guard:** The ValueError guard is correct in intent. `WHERE source_issue_number = ?` with NULL in SQLite uses NULL semantics — the comparison `NULL = NULL` is NULL (not TRUE), so no rows are returned regardless of existing data. The guard prevents this silent dedup failure by failing loudly at the caller rather than silently succeeding with incorrect behavior. The error message is clear and cites the exact cause.

**registry.py — _TERMINAL_STATUSES_FOR_ISSUE_CHECK consolidation:** This fixes the PR #1003 named pattern. The `_upsert_typed` function previously had its own hardcoded `NOT IN` list that could drift from `_TERMINAL_STATUSES_FOR_ISSUE_CHECK`. The diff converts it to use the class-level constant. The comment is explicit: "single source of truth shared with has_active_uow_for_issue." This is the correct fix.

**Pattern application — StrEnum golden pattern (golden-patterns.md 2026-04-24):** `_TERMINAL_STATUSES_FOR_ISSUE_CHECK` is a frozenset of raw strings, not a StrEnum. However, the raw strings are used both in SQL queries (as parameters, not embedded in the query string — correct) and as a centralized constant. The StrEnum pattern would apply if there were an enum for UoW terminal statuses, but the codebase uses a frozenset in multiple places consistently. The consolidation to a single frozenset is the correct improvement available within the current design.

**Tests:** The two new tests are correct. `test_repropose_active_issue_returns_upsert_skipped` verifies the dedup path by inserting a UoW, transitioning it to `ready-for-steward` (non-terminal), and asserting a second upsert returns `UpsertSkipped`. `test_repropose_terminal_issue_creates_new_uow` verifies that terminal statuses (`done`, `closed` via direct SQL) allow re-proposal.

One observation on the test approach: both tests use direct SQL (`conn.execute("UPDATE uow_registry SET status=..."`) to set status rather than the registry API. This is the correct approach for testing dedup behavior across status transitions where the registry API might not expose direct status writes. This matches the existing test patterns in the file.

**No test for issue_number=None guard:** The PR adds a `ValueError` guard for `issue_number is None` in `_upsert_typed` but adds no test that exercises this guard. This is a minor omission — the guard is simple and the error message is clear, but a test for `registry.upsert(issue_number=None, ...)` would close the gap structurally.
