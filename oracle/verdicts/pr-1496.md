## Stage 1 — Vision alignment

**Prior:** this PR is solving the wrong problem, or the right problem in a way that forecloses better paths.

`get_conversation_history` backs context recovery for several scheduled jobs (epistemic-drift-sweep, deep-work, briefing, compact-catchup) — i.e. it is part of the substrate the system uses to know its own recent history. Per `vision.yaml`'s `fundamental_intent`, Lobster is meant to function as "a semantic mirror and cognitive extension... structural access to my intent, not just a prose reconstruction of it." A tool that silently serves five rows of 2026-05-22 test-fixture data instead of real history is a structural-access failure in exactly the domain the vision cares about — it degrades the system's own self-model, not just a downstream feature. Confirmed independently twice (`epistemic-drift-sweep`, `weekly-epistemic-retro`) per the linked issues (#1486, #1493), so this is not a hypothetical bug.

Root cause is a genuine flag/gate mismatch, not a deeper architectural problem: the write path was already correctly gated behind `LOBSTER_USE_DB`; the read path was not gated on the same condition, so a one-time non-empty seed permanently masked the filesystem fallback because the fallback trigger was `total_count == 0`, which a stale-but-nonempty table never satisfies. Reusing the *same* flag for the read gate (rather than inventing a second flag, or a staleness/freshness heuristic based on row timestamps) is the correct move: write-liveness and read-trustworthiness are the same invariant here ("is messages.db being kept current"), not two conflated concerns that need independently different values for different callers — this is different from the golden-pattern case (PR #1489, "split a conflated directory-role parameter") where a single parameter genuinely needed two different values for two different callers. Here one flag correctly captures one invariant for both readers and writers, and avoids introducing a second config surface that could itself drift out of sync with `LOBSTER_USE_DB` (the "mirror-constant" failure class named repeatedly in this codebase's own learnings.md, e.g. PR #1032, #839).

`_db_writes_enabled()` is a pure predicate — a field/env check with no branching semantics beyond the boolean read — which is a direct instance of `vision.yaml` operating-principle-3 ("if-then logic and field checks are code, not LLM instructions"). No LLM judgment was used or needed to resolve this; the fix is fully deterministic and testable, which is exactly the register this class of bug should be fixed at.

Scope: the PR explicitly declines to touch `handle_get_message_by_telegram_id` and the `handle_get_stats` DB-augmentation section, both of which share the same theoretical gap (DB queried without a writes-enabled check). I traced both:
- `handle_get_stats`'s DB section is additive and explicitly labeled ("**messages.db Totals:**") alongside — not instead of — the authoritative filesystem-derived counters above it. A stale total shown under a labeled DB section is misleading in a much narrower, lower-severity way than #1471's failure mode (which fully replaced the answer to "give me history" with fixture data with no visible label distinguishing it as such).
- `handle_get_message_by_telegram_id` is a specific-key lookup (`telegram_message_id`), not a broad "give me recent history" query. For the same masking failure to occur, a caller would have to look up a `telegram_message_id` that happens to collide with one of the five fixture rows — vanishingly unlikely in practice, and the blast radius of a hit (one wrong message returned) is qualitatively smaller than #1471 (an entire tool silently returning synthetic content for months).

Given this, leaving the other two handlers untouched is a defensible, disclosed scope decision that keeps blast radius proportional to the reported symptom — consistent with the PR's own stated reasoning. The one gap: no follow-up GitHub issue was filed to track closing the theoretical gap in those two handlers. This is a minor process note, not a blocker — the PR body discloses the decision explicitly rather than silently narrowing scope, and the risk in both deferred cases is low enough that a "not filed yet" is acceptable for a first-round fix. Recommend filing a small follow-up issue as a fast-follow, but not gating this PR on it.

**Cheaper-test check:** a staleness-timestamp heuristic (e.g. "trust the DB only if its newest row is within N hours") was an available alternative and would have been *more* complex and introduced a new magic threshold with no existing precedent in this codebase, versus reusing the flag the write path already defines. The flag-gate is the cheaper, more correct fix.

**Alignment verdict: Confirmed.** This is squarely infrastructure-hygiene work restoring correctness in existing substrate, not a new architectural direction. It does not touch anything in `what_not_to_touch` (WOS Stage 1/2 substrate, cron Phase 2/3, user model v2 Phase 3, new detection/classification rules) and fits under `current_focus.secondary` ("hygiene pass on accumulated WOS issues"/OODA-adjacent correctness work) without competing for attention with the paused-executor priorities.

## Stage 2 — Quality review

**Correctness of `_db_writes_enabled()` and the gate condition (lines ~6402–6406):** Verified by direct code trace against the running handler (`sed -n '6369,6470p' src/mcp/inbox_server.py` on the PR branch). `_db_writes_enabled()` reads `os.environ.get("LOBSTER_USE_DB", "0") == "1"` at *call time*, not at module-import time — this matters because this codebase's own learnings.md documents the opposite failure mode repeatedly (PR #839, #823: "module-level constant computed from env var at import time is not overridable by monkeypatch.setenv"). Because the read happens inside the function body on every call, `patch.dict(os.environ, ...)` in tests correctly takes effect; there is no frozen-at-import trap here. The gate is added as a third `and`-clause to the existing `if _db_get_conversation_history is not None and _db_count_conversation_history is not None:` condition, so when `LOBSTER_USE_DB=1`, the branch is byte-identical to pre-PR behavior (verified: `_open_messages_db_conn()` is only called inside the gated block, so it is also skipped entirely — not just deferred — when writes are disabled, avoiding an unnecessary DB-file-existence check and connection attempt on every call in the common case). The downstream `if not used_db or (total_count == 0 and offset == 0):` fallback check is unmodified and correctly fires whenever `used_db` stays `False` (which it now does whenever `_db_writes_enabled()` is `False`, since the DB-query block that sets `used_db = True` is never entered).

**Do the 7 edited pre-existing tests preserve original intent?** Yes for all 7: each adds `patch.dict(os.environ, {"LOBSTER_USE_DB": "1"})` to restore the exact DB-primary code path the test was originally written to exercise, and the docstrings were updated to name the new precondition. Independently re-ran all three touched test files (116 tests) — all pass. This is legitimate test maintenance, not masking: the tests still assert the same production behavior, under an explicit and now-necessary precondition.

**Does the new regression test reproduce #1471?** Yes, and it is a strong test. `test_skips_db_and_uses_filesystem_when_db_writes_disabled` mocks stale, non-empty fixture rows (mirroring the real fixture's shape: `chat_id 123456`, `TestUser`, `2026-05-22` timestamp) returned by `_db_get_conversation_history`/`_db_count_conversation_history`, explicitly clears `LOBSTER_USE_DB` from the environment (reconstructing the deployment's actual unset state rather than assuming a clean test env), and asserts both that the real filesystem message is present *and* that none of the fixture's identifying content (`"Hello Lobster!"`, `"TestUser"`) leaks into the output. This directly reproduces the reported symptom and would have failed on pre-PR code.
