## Stage 1: Vision Alignment

**Epistemic prior entering review:** This implementation is solving the wrong problem, or solving the right problem in a direction that forecloses better paths.

**What would have to be true for this work to be the wrong path?**
- If the real fix belongs in `heartbeat_sidecar` (the primary fix in issue #1253), then adding a second path at the dispatcher level is redundant infrastructure. However: the primary fix and secondary fix address different failure modes. The heartbeat_sidecar fix prevents the masking window from being refreshed. The dispatcher fix routes the UoW immediately on kill notification. They are complementary, not redundant.
- If `agent_failed` messages are unreliable (not always emitted, or emitted without the `wos-uow_` prefix), the fast-path becomes a false safety net. The code handles this correctly: non-matching task_ids produce a no-op, and exceptions produce `mark_processed` without state change.
- If routing to `ready-for-steward` on every `agent_failed` is premature (the agent might have completed normally and `agent_failed` is a false positive), this creates unnecessary steward load. However: the optimistic lock (`WHERE status = 'executing'`) means the transition is a no-op if the UoW has already been transitioned by another path — the `rows=0` race path is explicitly handled.

**Cheaper test of the assumption?** No — the bug is structural (message type unhandled), and the fix is structural (add handler). There is no lighter test.

**What does this foreclose?** Nothing. The handler is additive — it does not change behavior for any other message type, and the fast-path placement before the spawn-gate is correct because `handle_agent_failed` legitimately returns `mark_processed` rather than `spawn_subagent`.

**Alignment verdict: Confirmed.**

**Pattern citation:** "Proactive resilience over reactive recovery" (principle-1) — adds an immediate transition path rather than relying on the startup_sweep staleness detection (reactive). Matches the principle directionally.
